# Public data feeds and API conventions

P2.4. PaddySpeaks publishes a small set of **static, read-only JSON feeds**
of data that is already public on the site. There is no server-side API for
this data, no key and no rate limit. The files are regenerated by
`python3 scripts/platform_build/build.py api` and checked in CI.

## What is published (`/api/v1/`)

| Endpoint | Contents | Derived from |
|---|---|---|
| `/api/v1/index.json` | List of the endpoints below | — |
| `/api/v1/articles.json` | Every essay: slug, title, subtitle, category, published date, read time, URL, image, series | `article_metadata.json` |
| `/api/v1/sacred-texts.json` | Each study app: id, name, language, tradition, URL, provenance status and a link to its full provenance record | `data/platform/catalog.json`, `data/provenance/` |
| `/api/v1/changelog.json` | The curated platform changelog | `data/changelog.json` |
| `/api/v1/corrections.json` | The public corrections log | `data/corrections.json` |
| `/api/v1/interview-categories.json` | Interview Studio tracks, question topics with counts, companies with counts | `interview/data/`, catalog |
| `/api/v1/registry.json` | The site registry: every public count | `data/site-registry.json` |

Also public, with their own formats:

| Resource | Notes |
|---|---|
| `/feed.xml`, `/feeds/<category>.xml`, `/changelog.xml` | RSS 2.0 |
| `/data/provenance/<id>.json` | Full provenance record; schema `data/provenance/schema.json` |
| `/data/search/*.json` | The search index shards (internal format; may change without notice) |
| `/data/graph.json` | The knowledge graph (internal format; may change without notice) |
| `/jobs/data/stats.json` | JobSignal's live summary, rewritten every four hours by the pipeline. Individual listings are summaries of employers' own postings, so link to the employer, not to us. |

## Conventions

- **Envelope.** Every `/api/v1/` file is
  `{"api": {"version", "kind", "source", "docs", "license"}, "data": …}`.
  `source` names the repository file it was derived from.
- **Versioning.** The version is in the path. Within `v1`, fields may be
  **added** but never removed or renamed. A breaking change ships as `/api/v2/`
  alongside `v1` for at least 90 days, with a changelog entry.
- **Naming.** camelCase keys, ISO 8601 dates (`YYYY-MM-DD`), absolute URLs.
- **Determinism.** Output is sorted and has no build timestamps, so a file
  changes only when its data does, and `ETag`/`If-None-Match` caching works.
- **Freshness.** Static files update when `main` deploys. JobSignal numbers are
  never copied into `/api/v1/`; read `/jobs/data/stats.json` directly.
- **Licensing.** See `/copyright/`. The data describes the site's content.
  It is not a licence to republish the content itself.

## What is never exposed

- Anything from the D1 databases: analytics, leaderboard entries,
  testimonials (pending or approved, beyond what the testimonials page shows),
  contact logs, rate-limit state.
- Anything from visitors' browsers: saved jobs, prep progress, Continue history.
- Worker internals, secrets, admin routes.
- The community-questions Google Sheet.

## Possible future endpoints (not built)

| Candidate | Why not yet |
|---|---|
| `GET /api/v1/verses/<work>/<chapter>.<verse>.json` | Useful for apps citing verses, but it needs per-work provenance to be `verified` first, so as not to spread unverified text. |
| `GET /api/v1/jobs?family=…` (Worker) | JobSignal's data is employer-sourced and changes hourly. A server endpoint needs caching and abuse limits, and should respect employers' terms. |
| `GET /api/v1/search?q=` (Worker) | The static index already gives clients everything. A server search only makes sense once the corpus outgrows the browser. |

## Crawlers

`robots.txt` disallows `/*.json$` for crawlers. That is unchanged and
deliberate: these feeds are for programs that ask for them, and the HTML
pages are what should be indexed.
