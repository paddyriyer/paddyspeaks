# The Invisible Engine — production plan, scene inventory and claim ledger

`/invisible-engine/` is an interactive lesson built from Paddy's master prompt
(`COMPLETE_INVISIBLE_TECHNOLOGY_MASTER_PROMPT.md`, 2026-10-22). It travels from a
battery-less contactless card to a whispering tracker, to waves that cancel, to
quantum computers and the CISO's response — one story, five reader levels.

**Decisions (Paddy, 2026-10-22):** a new lesson section, not an expansion of
*From Tap to Trace*; delivered **in phases**, one reviewable PR per phase. Where a
scene overlaps the article, the lesson goes deeper or links to it, never repeats it.

## 1. Titles

**The Invisible Engine** — *From a powerless credit card to a whispering tracker,
from waves that cancel to quantum computers that challenge cryptographic trust.*

Alternatives:
1. What Moves When You Tap
2. Energy, Waves, Keys: How the Invisible World Works
3. The Card Without a Battery
4. Whisper, Relay, Decrypt
5. From Coil to Qubit
6. Nothing You Can See

**Thesis.** The same invisible world can power a contactless card, help recover a
suitcase, expose a person's whereabouts and force us to rethink encryption. Most
public explanations fuse four different things into one glowing arrow: energy,
signals, data and promises about who may read the data. Pull them apart and the
magic becomes engineering, the risks become specific, and the quantum threat
becomes a scheduling problem instead of a headline.

## 2. How the lesson is built

| Path | What it is |
| --- | --- |
| `invisible-engine/index.html` | Lesson home: thesis, child-level synopsis, contents with reader paths, legend, module status |
| `invisible-engine/mNN.html` | One page per module; each scene is `<section class="scene" id="sNN">` |
| `scripts/invisible_engine/scenes/moduleNN.py` | **Source** of every scene diagram, built from shared illustrated components in `art.py` (terminal, card, phone, tag, bank, chip, coil…) and `svgkit.py` (frames, arrows, legend) |
| `invisible-engine/scenes/sNN.svg` | GENERATED by `python3 scripts/invisible_engine/build.py` (CI: `--check`). Editable SVG; frames are `<g data-f="n">` layers. Never hand-edit |
| `invisible-engine/scenes/png/sNN.png` | Still PNG, GENERATED by `IE_DEPS=… node scripts/invisible_engine/render.mjs` (playwright) |
| `invisible-engine/art/` | Paddy's illustrations used in the lesson (WebP) |
| `invisible-engine/lesson.css`, `lesson.js` | Shared styles; level switch, frame stepper, SVG inlining |
| `invisible-engine/demos/*.js` | Interactive demos (A–L); pure model functions exported for tests |
| `invisible-engine/tests/` | `check.py` (scene contract, SVG validity, legend, levels, frame captions, sources), `demos.mjs` (demo maths). Both run in Validate Content |

**Reader levels.** Every scene carries five panels: **A** child (10), **B** curious
adult, **C** engineering student, **D** security architect, **E** CISO. The level
switch shows one level at a time (stored in `localStorage` as `ie.level`, registered
in `data/platform/state-keys.json`); "All levels" shows all five. Without JavaScript,
all five are shown.

**Frames.** A scene's SVG reveals its layers one frame at a time through Back / Next
buttons and a frame list. Nothing plays by itself; with reduced motion, transitions
are off. Without JavaScript the `<img>` shows the complete final state, and each
frame's caption is in the page text.

**Arrow and line semantics (every SVG, with a legend on every page):**

| Mark | Meaning |
| --- | --- |
| Orange solid arrow | Energy / power transfer |
| Blue solid arrow | Radio signal or physical wave (labelled with band and direction) |
| Green solid arrow | Plaintext or locally available information |
| Purple solid arrow | Encrypted payload, cryptographic operation or protected credential |
| Grey dashed arrow | Registration, consent, authorisation or administrative relationship — never a data transfer |
| Red dashed outline | Attacker-controlled zone or privacy hazard |
| Thick box boundary | Trust, hardware, account or organisational boundary |

Field drawings carry the label *illustrative field visualisation, not literal visible
waves*. Crossings are drawn as crossings, never junctions.

**Evidence labels (prose and figure notes):** Specification · Manufacturer documented ·
Independently demonstrated · Conceptual example · Illustrative value · Not publicly
disclosed.

**Visual style (Paddy, 2026-10-22):** every scene is an illustration, not a box
diagram — recognisable objects (terminal, card cutaway, phone, tag, bank), numbered
step badges and coloured step panels, a 40 px title and a one-line subtitle, in the
manner of Paddy's reference images. The arrow semantics and legend above still apply
inside every illustration. New scenes reuse the components in `art.py`.

**Editing workflow:** change `scenes/moduleNN.py` or `content/mNN.py` →
`python3 scripts/invisible_engine/build.py` (or `build.py module04 m04` for one module) →
render PNGs (`render.mjs s23 s24 …`) → look at every changed PNG before committing
(overlaps are the common failure) → `python3 invisible-engine/tests/check.py` and
`node invisible-engine/tests/demos.mjs`.

**The pages are GENERATED** (since phase 2) by `scripts/invisible_engine/pages.py` from
`scripts/invisible_engine/content/`: `mNN.py` holds a module's text (`M`: scenes with
frames, the five levels, notes, red-team checks and sources; optional `BEFORE`,
`INSERTS` for demos placed after a scene, `SCRIPTS`), `home.py` the lesson home, and
`inserts.py` the demos' static HTML. A module becomes "available" (nav, home card, pager)
when its `content/mNN.py` exists. Scene alt text is the SVG's `<desc>`. Never hand-edit
`invisible-engine/*.html`; CI (`build.py --check`) fails when it is stale.

**Demos D and E** keep their facts in `invisible-engine/demos/lost.json` and
`connections.json`: the static, no-JavaScript HTML is written from the same JSON the
scripts and `demos.mjs` read, so the words cannot drift from the tests. Demo C
(`whisper.js`) is a pure, tested model like demo A.

Reading notes shown with `nfc.png`: “backscatter” is the UHF term (HF uses load
modulation); the 1.8–3.3 V range is illustrative; the card proves itself mainly to the
issuer, not the terminal; short range is not an authorisation control.

Corrections needed before the held images can be used:

- **nfc1.png** — (1) “Main privacy protection: dynamic one-time cryptogram (prevents
  replay *and tracking*)” is wrong: a plastic card sends a static card number, which links
  payments; the cryptogram prevents replay only. (2) Real Visa, Mastercard and American
  Express logos: replace with a generic “Card network”. (3) The flow omits the acquirer
  (merchant's bank). (4) Wallet row “Issuer … maps the token” — the network's token
  service maps tokens. (5) American Express is usually both network and issuer, so the
  generic flow does not fit it.
- **airtag.png** — (1) “Every few seconds it wakes” is an unverified interval: say “at
  intervals” or label illustrative. (2) “Up to about a year” contradicts Apple's “more
  than a year”. (3) The PCB layout is invented: label “illustrative, not a teardown”.
  (4) “Sends the AirTag's secure ID, its own location and a timestamp, all encrypted”:
  the lookup value (a hash of the public key) is not encrypted; location and time are.
- **airtag1.png** — (1) Precision Finding: “iPhone 11 and later” excludes iPhone SE
  models (no UWB). (2) “relays the location… over an encrypted connection” undersells it:
  the report is end-to-end encrypted, not only sent over TLS. (3) Apple logo and Find My
  screens: acceptable as product depiction, but avoid implying Apple produced the image.
- **quantum.png** — (1) Shor “breaks widely used public-key cryptography”: say “would
  break … on a large fault-tolerant quantum computer, which does not yet exist”.
  (2) Post-quantum “being standardized by NIST”: ML-KEM, ML-DSA and SLH-DSA were
  standardised in August 2024 (FIPS 203/204/205). (3) Grover “halves the security level
  for keys and hashes”: add “in an idealised model; collision resistance differs”.

## 6. Rules for every phase

- Never fuse energy, signal, data and security promise into one arrow.
- Never type an unverifiable engineering number; mark it **illustrative** or source it by model.
- Never claim a card or wallet is anonymous to issuer, network or merchant; tokenisation is scoped to supported wallets.
- No fraud, cloning, relay or stalking instructions; threats are explained only to the depth a defender needs.
- Apple's Find My key details are documented for the Find My family; never present them as verified internals of a specific AirTag generation.
- Quantum: no "tries all answers at once"; global phase is unobservable; no claim that deployed devices are quantum-broken.
- Every scene: five levels, frame captions, SVG with `<title>`/`<desc>`, sources with dates, an accuracy note. `tests/check.py` enforces the contract.
