# Platform data: one source of truth

Every public statistic on PaddySpeaks ("1,527 interview questions", "23 sacred
texts", the homepage filter counts) comes from **one** place, and that place
is derived from the content itself. Typing a number into a page is how the
site ended up saying both 1511 and 1527 on the same homepage.

## The three layers

| Layer | File | Who writes it |
|---|---|---|
| **Catalog**: what exists and where | `data/platform/catalog.json` | Hand-authored. Journeys, article categories, sacred texts, Interview Studio tracks, demos, job products, tools, utility pages. **No counts.** |
| **Registry**: how many | `data/site-registry.json` | Generated by `scripts/platform_build/build.py registry`. Never edit it by hand. |
| **Surfaces**: where numbers show | any HTML page | `<span data-ps-stat="key">N</span>`, stamped by `build.py stamp` |

Counts are computed from the real data:

| Registry value | Counted from |
|---|---|
| `articles.*` | `article_metadata.json` |
| `homepage_deck.*` | the `.deck-card` elements in `index.html` (these drive the filter buttons) |
| `interview.questions`, `.by_language`, `.companies` | `interview/data/questions.json`, `companies.json` |
| `interview.skill_check.*` | `interview.app/evaluate/data/<section>.json` |
| `interview.data_model_scenarios` | the `h-sc-*` scenario ids in `interview.app/design/data-modeling.html` |
| `interview.design_problems` | `interview.app/design/the-*-problem.html` |
| `interview.tracks`, `sacred_texts.*`, `demos.*` | `data/platform/catalog.json` |

**Live JobSignal numbers are deliberately not in the registry.** They change
every four hours; pages read them at runtime from `/jobs/data/stats.json`.

## Stamping a number into a page

```html
<span data-ps-stat="interview.questions">1527</span> real questions
<span data-ps-stat="interview.questions" data-ps-format="comma">1,527</span>
```

`build.py stamp` rewrites only the digits between the tags of an element
carrying `data-ps-stat`. It touches nothing else, so it is safe on the
hand-crafted `index.html`. Unknown keys and non-numeric contents are errors.
The list of keys is `stats()` in `scripts/platform_build/registry.py`.

Strings that cannot hold an element (`<title>`, meta descriptions, JSON-LD)
are kept honest by `interview/scripts/update_counts.py`, which now recounts
`questions.json` itself and has a `--check` mode.

## Commands

```bash
python3 scripts/platform_build/build.py all      # regenerate everything
python3 scripts/platform_build/build.py check    # what CI runs; writes nothing
python3 scripts/platform_build/build.py registry stamp   # counts only
```

## What CI enforces (`build.py check`, in Validate Content)

- `data/site-registry.json` matches a fresh derivation.
- Every `data-ps-stat` span shows the registry value.
- Every `path` in the catalog exists; catalog ids are unique.
- Every homepage deck card for `articles/*` has an `article_metadata.json`
  entry with the same category, and every metadata entry has a deck card.
- The homepage filter counts are stamped spans, not typed numbers.
- `update_counts.py --check` has nothing left to rewrite.
- The later generators (search index, graph, feeds, API, rendered pages) are
  current.

The question bots (`weekly-questions.yml`, `ingest-submissions.yml`) run
`build.py registry stamp` after they add questions, and commit the result
in the same commit, so a bot run never leaves drift for the next PR.

## Known exceptions (deliberate)

- **Resumes** (`Paddy_Iyer_Resume*.html`, `.pdf`, `.docx`) are dated personal
  documents, not live surfaces. Their numbers are a snapshot and are not
  stamped. Listed in the backlog under "Requires decision".
- `careeros/js/data/profiles.js` is mock profile data inside a prototype.
- `interview.app/js/app.js` shows a "1400+" placeholder only in the instant
  before the question bank loads.

## Search

`build.py search` writes `data/search/`:

| Shard | Loaded | Contents |
|---|---|---|
| `core.json` | when search opens (~55 KB gzipped) | essays, sacred texts and Gita chapters, devotional music, Interview Studio tracks, design problems and data models, question topics, companies, demos, tools, site pages, concepts, journeys |
| `verses.json` | first keystroke | 697 Bhagavad Gita verses: translation, transliteration, word list |
| `names.json` | first keystroke | 2,007 Vishnu and Lalitha Sahasranama names and meanings |
| `questions.json` | first keystroke | 1,527 Interview Studio question titles |
| `manifest.json` | never (for people and tools) | counts, sizes, schema |

The document schema is `{id, type, title, subtitle, text, tags, category, url,
updated, source}`. Big shards hoist shared fields into `defaults`, which the
client merges back. Sacred data is read from the apps' own `data.js` files
by `extract_sacred.mjs`, evaluated in an empty Node `vm` sandbox, so nothing
is copied by hand.

**Live JobSignal roles are never indexed.** The client reads
`/jobs/data/companies.json` at query time and hands role searches to
`/jobs/search/?q=`, JobSignal's own family-gated ranker.

Ranking (`lib/ps-search.js`, pure and tested by `lib/tests/search.mjs`):

- whole-word and word-prefix title matches outrank tag, subtitle and body matches;
- light stemming ("attachment" matches "attached");
- diacritic-insensitive matching ("karmani" matches "karmaṇi");
- an exact verse reference ("Gita 2.47", "bg 18.66") wins outright;
- a company is a result only when the query names it;
- per-type weights, and in the All view at most 5 results of one type unless nothing else matched.

## Design language (P1.8)

`lib/ps-platform.css` is the shared layer. The products keep their own
palettes (journal ink-blue, sacred-text saffron and parchment, Interview
Studio night-sky, JobSignal's product chrome, the light demo dashboards).
What they now share:

| Token / component | Purpose |
|---|---|
| `--ps-radius-*`, `--ps-space-*`, `--ps-font-*` | Radius, spacing and type scale for platform components |
| `:focus-visible` ring | One focus treatment everywhere (low specificity, so products can refine it) |
| `.ps-badge[data-type]` | Content-type labels: Essay, Sacred text, Verse, Interview prep, Company, Demo, Concept … the same colour for the same kind everywhere |
| `.ps-badge[data-status]` | Status labels: source noted, not recorded, under review, verified, open |
| `.ps-panel` | Collapsed disclosure (Sources & Verification, data flow) |
| `.ps-state[data-kind]` | Empty, loading and error states |
| `.ps-btn`, `.ps-chip` | Buttons and filter chips, with `aria-pressed` styling |
| `.ps-footer-legal` | The site-information footer row |
| `.ps-doc`, `.ps-callout`, `.ps-entry`, `.ps-toc` | Document pages (legal, corrections, changelog) |
| Reduced-motion guard | Site-wide |

Components inherit colour from their context (`currentColor` and
`color-mix`), so the same panel looks native on every product. They were
audited with axe for contrast (WCAG AA) and target size (24px).
