# Confluent · Loop 4 — evaluator notes (hidden from candidates)

## CFL-L4-01

**Reference architecture (one defensible design; score others on the criteria).**
- **Two tiers, one log**: each partition's log is the local tier (active segment plus recent closed segments, kept for about {{local_hours}} hours) and the remote tier (older closed segments in object storage). Offsets are unchanged; a read for an offset below the local log's start goes to the remote tier.
- **Eligibility and uploader**: only the partition leader uploads, and only closed segments whose records are all below the high watermark (this exercise's rule). The upload includes the segment, its offset and time indexes, and the leader-epoch history for its range. Object keys include a unique upload id, so a retried or concurrent upload never overwrites another object.
- **Remote metadata**: per partition, an ordered list of remote segment entries `(start_offset, end_offset, max_timestamp, leader_epoch_range, object_key, size, state)` with states `copy_started → copy_finished → delete_started → deleted`. Kept in a replicated, compacted metadata topic or store, partitioned like the data. Readers trust only `copy_finished` entries; local deletion of a segment is allowed only after its entry is `copy_finished`. A new leader reads the metadata, checks the leader-epoch lineage against its own log, and resumes uploading from the highest `copy_finished` end offset; entries a fenced leader left in `copy_started` are cleaned up as orphans after a grace period.
- **Historical read path**: fetches below the local start offset are handed to a separate remote-read thread pool with its own bounded queue, so request handler threads never block on object storage. Reads are by byte range using the offset index; a broker-local read-through cache (memory plus a bounded local disk area) holds recently fetched chunks with prefetch of the next chunk for sequential readers, so several consumers replaying the same range share fetches. Per-client and per-broker quotas on remote-read bytes protect tail traffic. Consumers that must replay large ranges can be directed to read from a follower replica if the platform supports it, spreading the load.
- **Retention**: total retention ({{retention_days}} days, or bytes) is enforced from the metadata: entries whose `max_timestamp` is older than the horizon move to `delete_started`, the objects are deleted, then the entry is marked `deleted`. Local retention removes local copies only once uploaded. A retention decrease is applied by the same loop; a periodic reconciler lists the object store prefix against the metadata and removes unreferenced objects older than a grace period.
- **Object store failure**: uploads back off with jitter; local segments are kept past the local retention target (the local tier grows), with alerts on disk headroom in hours left at the current ingest; as a last resort, produce quotas or partition moves to brokers with headroom. Historical reads fail with retriable errors; tail traffic is unaffected.
- **Not tiered**: compacted topics in this exercise (compaction rewrites closed segments, so immutable remote copies would need re-upload or remote compaction), and topics with very short retention where the cost is all request overhead.
- **Cost model**: stored bytes per day ≈ daily ingest × retention days (one remote copy, not three) plus local disks for {{local_hours}} hours × replication factor; PUTs per day ≈ ingest ÷ segment size (plus index files); GETs from replays ≈ bytes replayed ÷ chunk size; cross-zone or egress charges if brokers fetch from another zone. Strong candidates notice that one remote copy instead of three replicas on disks is usually the main saving.

**Competing designs to accept.** Remote metadata in a separate consistent store instead of a topic. Followers building their remote view from the metadata rather than uploading. Larger segments for fewer requests, with the trade-off of a staler remote tier. A dedicated fleet of read-only "replay" brokers or serving nodes for historical reads. Remote reads served directly by clients from object storage, if the candidate addresses access control and offsets.

**Bottlenecks and failure modes.** Request-handler threads blocked on remote I/O; duplicate or orphaned uploads after leader changes; local disks filling while uploads fail; metadata growth on high-partition clusters; per-prefix rate limits when many partitions upload at once; retention lag in the remote tier; unbounded remote-read cache.

**Incident guidance.**
- *80 replaying consumers raise producer p99 to 900 ms*: remote reads are running on (or blocking) the request path. Immediately apply a remote-read quota for the replaying clients and spread them (consumer count, read from followers where supported). Fix: a separate remote-read thread pool and queue, a bounded read-through cache with prefetch, per-broker remote-read limits. Prevention: a load test of a full-history replay with produce-latency SLOs.
- *Object store errors for 50 minutes*: uploads back off; local segments stay; disk fills at ingest ÷ brokers per hour. Track hours of headroom, extend local retention automatically, and if a broker approaches full, throttle producers to it or move partitions; never delete un-uploaded segments. Afterwards, uploads drain with a rate limit to avoid a request storm.
- *Bill 1.7 times the expected*: orphaned objects from uploads started by leaders that were then fenced. Run the reconciler that diffs object listings against `copy_finished` entries and deletes unreferenced objects past a grace period; make object keys unique per upload attempt and record `copy_started` before writing so orphans are always findable.
- *Retention cut, data still there a week later*: remote deletion was not driven by the topic's new configuration, or deletion is stuck. Show remote bytes per topic against retention-implied bytes, alert on the gap, and make the retention loop re-read configuration and process `delete_started` entries to completion.

**Follow-up guidance.** Push on how the new leader decides what is already uploaded (metadata plus epochs, not object listings); how the cache is bounded; and the request-count arithmetic. At Very Hard, ask for the remote tier's consistency with the local log after an unclean election (entries from a divergent epoch must not be served).

**Rubric anchors.** 2: "copy old files to object storage" with no metadata, no single uploader, local deletion without confirmation, reads on the request path. 3: leader uploads closed segments, metadata with states, delete-after-confirm, separate historical read path, retention in both tiers, basic cost. 4: also epoch fencing and orphan reconciliation, bounded cache with prefetch and quotas, explicit object-store-outage behaviour with headroom alerts, request-count costing, and crisp handling of every incident.

**Strong signals.** Asks which reads are sequential and how many consumers replay at once; does the cost arithmetic unprompted; treats remote metadata as the source of truth. **Red flags.** Deleting local segments on a timer; every replica uploading; blocking request threads on object storage; ignoring compacted topics.

## CFL-L4-02

**Reference architecture (one defensible design; score others on the criteria).**
- **Topology**: active-passive for the critical topics: producers write to the first region; asynchronous replication copies records, topic configurations, schema registry entries (with the same schema ids, by replicating the registry's own storage or running it in a primary/follower mode), and access rules to the second region. Lag is measured as the age of the newest replicated record (time) per partition, not only offsets.
- **Offsets**: with an offset-preserving tool the consumer group's committed offsets can be replicated and used as-is; the destination may be behind, so a consumer's committed offset may be beyond the destination's end for a short time and must be clamped to the end, which means it waits rather than skips. With a translating tool, checkpoints map a group's committed source offset to a destination offset at intervals; a consumer starts from the last checkpoint, which is never ahead of what it processed, so it reprocesses up to one checkpoint interval plus lag. Idempotent consumers (upsert by key) accept that; non-idempotent ones need their own dedup by a record id carried in a header or the key.
- **Failover**: a human-gated decision with a runbook and automation behind it (automatic detection, one command to fail over), because asynchronous replication means failover loses up to the lag and a false positive creates two primaries. Steps: confirm the first region is unreachable or fence it (revoke producer credentials or block at the network), stop replication into the second region, make destination topics writable, switch clients (bootstrap DNS or a client-side config service with short TTLs), start consumers from preserved or translated positions. Time each step against {{rto_minutes}} minutes.
- **Failback**: do not simply reverse replication over the old topics. Replicate the second region's new writes back to the first (or rebuild it from the second), identify the records the first region holds that never reached the second (the unreplicated tail, about the lag at failure), and reconcile them by business rules (replay as new events, or discard with an audit). Fail back during a planned window with the same runbook.
- **Active-active**: only for topics whose keys have a home region (each key written in one region) or for append-only streams where order across regions does not matter. Each region writes its own topic; replication copies it to the other region under a prefixed name (or origin header), so nothing replicates back; consumers read both local and remote topics and must not assume order across them. For keyed state such as inventory, use per-key home regions or a conflict-resolution rule decided up front.
- **Proof**: weekly drills that fail over a canary topic set and measure recovery point (time of last replicated record) and recovery time; a continuous synthetic producer whose records' replicated age is the lag SLO.

**Competing designs to accept.** A stretch cluster across nearby zones for critical topics (synchronous) if the candidate recognises it does not span distant regions. Dual writes from producers to both regions with consumer-side dedup (complexity and divergence acknowledged). Fully automatic failover with a quorum witness in a third location.

**Bottlenecks and failure modes.** Lag measured in records hiding time lag on quiet topics; checkpoint interval causing large reprocessing; clients caching broker addresses; schema ids differing between regions; replication loops; split brain from automated failover; unreconciled tail on failback.

**Incident guidance.**
- *90 seconds behind, 40,000 duplicate notifications*: the translated positions are only as fresh as the last checkpoint. Stop the notification consumer, dedup by notification id against a store of sent ids, and resume. Fix: shorter checkpoint interval for critical groups, idempotency (a sent-id store) in every non-idempotent consumer, or an offset-preserving tool for those topics. Classify consumers by duplicate tolerance before the next drill.
- *Records cycling between regions*: two flows with identity topic names and no origin filter form a loop. Stop one flow immediately, delete or truncate the duplicated range, and dedup downstream by record id. Prevention: prefixes or an origin header with a filter, and a validation check that rejects any replication topology with a cycle.
- *Unreplicated tail on failback*: about {{rpo_seconds}} seconds of records exist only in the first region. Export them, compare with the second region by key and id, replay non-conflicting ones as new events, and send conflicts for business review; never overwrite the second region's newer state. Prevention: a documented reconciliation procedure exercised in drills.
- *2,000 records looks healthy, is 9 minutes old*: change the SLO to replicated record age (time), use heartbeat records on quiet topics so lag is measurable, and alert on time against {{rpo_seconds}} seconds.

**Follow-up guidance.** Push on what a consumer does if its committed offset is ahead of the destination's end; on how fencing of the old region is done in practice; and at Very Hard on keeping per-key order when a key's home region changes.

**Rubric anchors.** 2: "mirror the topics and point clients at the other region", no offsets story, no failback. 3: offsets preserved or translated with consequences, runbook failover with fencing, lag in time, active-passive versus active-active with loop prevention. 4: also failback reconciliation of the unreplicated tail, consumer classification by duplicate tolerance, per-key ownership for active-active, regular measured drills, and crisp handling of every incident.

**Strong signals.** Starts from the recovery objectives; asks which consumers are idempotent; distinguishes data, configuration and schema replication. **Red flags.** Claims of zero data loss with asynchronous replication; automatic failover with no split-brain protection; active-active with two writers per key and no conflict rule.

## CFL-L4-03

**Reference architecture (one defensible design; score others on the criteria).**
- **Input duplicates**: clients retry with the same click id. The processor keys by click id (repartitioning if needed) and keeps a dedup store of seen ids for the duplicate window (10 minutes for nearly all, 1 hour for the rest; a time-bounded windowed store) backed by a changelog topic, so state moves with the partition. Late duplicates beyond the window are caught by a daily reconciliation.
- **Producer retries**: the processor's producer is idempotent, so a retried send in the same session is written once.
- **Processing atomicity**: consume-transform-produce in one transaction per commit interval: output records, changelog updates for state, and the input consumer positions are committed together (sending offsets to the transaction). A crash before commit aborts everything; the replacement resumes from the last committed positions with the matching state, so nothing is double counted or skipped.
- **Zombie fencing**: each instance's transactional id is stable for its input partitions (or the consumer-group-aware fencing in newer clients); when a replacement initialises, the epoch increases and the old instance's sends and commits fail with a fencing error. It must then shut down rather than retry.
- **Downstream consumers**: the billing ledger reader and every consumer of the output topic use `read_committed`. Those that do not may see results of aborted transactions, which is double billing; publish that requirement and, until all comply, have them dedup by result key. The last stable offset is held back by any open transaction, so the transaction timeout and commit interval bound how stale read_committed readers can be.
- **Sink**: each result has a deterministic key `(advertiser_id, minute)` and a version (the window's latest revision); writes are upserts by key, or the sink stores the input partition and offset per row and the writer skips anything already applied. For an HTTP API with no idempotency key: a dedup ledger (a table keyed by result key and revision, written before the call and marked complete after, with a reconciliation path for calls whose outcome is unknown), or batching results into a daily file the partner loads once; accept "at least once with a reconciliation" if the candidate is explicit about the residual risk.
- **Commit interval**: {{commit_ms}} ms trades latency (results are visible to read_committed consumers only after commit) against overhead (transaction markers per partition, coordinator load). Must be well under the 30-second visibility requirement.
- **Reconciliation**: count clicks in per minute and billed clicks out per minute by advertiser; the ledger is checked daily against the raw click topic.

**Competing designs to accept.** Writing directly to a transactional database with input positions stored in the same database transaction (no output topic transaction needed for that sink). Dedup at ingest instead of in the processor. A different stream processing framework, if its exactly-once mechanism is explained.

**Bottlenecks and failure modes.** Dedup state size at {{events_per_sec}} events per second (ids × window); open transactions holding the last stable offset; zombie instances; sinks with insert-only writes; non-read_committed consumers; commit interval too long for downstream pacing.

**Incident guidance.**
- *90-second pause, longer than the transaction timeout*: the coordinator aborts the transaction; the replacement's initialisation bumps the epoch; the old instance's sends and commit are rejected as fenced. Verify that the instance exits on the fencing error (not retries as a new producer), and that no output from the aborted transaction is visible to read_committed readers. Prevention: GC tuning, a liveness check that stops an instance before its session expires.
- *Transaction open for 15 minutes*: the last stable offset is stuck, so read_committed consumers stop advancing on those partitions. Find the producer, abort (restart it so the timeout or fencing ends the transaction), and lower the transaction timeout so a stuck transaction cannot hold the partition for long. Alert on last stable offset lag behind the high watermark.
- *Sink written twice after an outage*: the writer replays from the last committed positions and inserts again. Remove duplicates by key, switch to upserts by the deterministic key (or store applied offsets in the sink), and add a test that replays a range twice.
- *Commit interval raised to 60 seconds*: results become visible in one-minute steps, breaking pacing. Restore the interval; set a configuration guard that keeps it under the visibility objective; give pacing its own lower-latency signal if needed.

**Follow-up guidance.** Push on the difference between the idempotent producer (one session, broker-side) and end-to-end dedup by click id; ask what happens if a recomputed window changes a result already sent to the sink (versions and upserts).

**Rubric anchors.** 2: "turn on exactly-once" and stop there; no sink story; no input dedup. 3: input dedup by id, transactional consume-transform-produce with offsets, read_committed consumers, idempotent sink writes. 4: also fencing explained, last stable offset consequences, a sound approach for the non-idempotent API with stated residual risk, reconciliation, commit interval reasoning, and crisp handling of every incident.

**Strong signals.** Says exactly-once is an end-to-end property; distinguishes three sources of duplicates; asks about consumers they do not control. **Red flags.** Believing broker transactions extend to the sink; at-least-once with no dedup; ignoring zombies.

## CFL-L4-04

**Reference architecture (one defensible design; score others on the criteria).**
- **Control plane**: an API stores each connector's desired state (configuration, plugin version, max tasks, running or paused) in a versioned config store; secrets go to a secrets manager and configurations hold only references. The connector's plugin computes task configurations; a scheduler assigns tasks to workers; a reconciler compares desired and observed state continuously and acts.
- **Data plane**: workers run tasks; each task's positions (source offsets or sink consumer positions) are stored outside the worker (an offsets topic or store, or consumer group offsets for sinks), so a task can move by restarting elsewhere.
- **Placement and isolation**: workers are grouped into pools; small tenants share pools, with per-task resource limits (process or container memory and CPU caps); risky or partner plugins run in separate processes so a leak or crash affects only that process; large or sensitive tenants get dedicated pools. Assignment is incremental: when a worker joins or leaves, only its tasks move; changing one connector changes only its tasks.
- **Restarts**: exponential backoff with jitter per task, a failure budget (for example five failures in ten minutes), then a terminal `FAILED` state with the last error, shown to the customer; external-system outages detected and shown as such rather than crash-looping.
- **Health**: liveness (process alive) plus progress (records processed, positions advancing, time since last successful write) and error rate; a task with no progress while upstream has data is marked degraded and the customer is told.
- **Status**: workers publish task state changes to a status stream; the API reads a projection; latency within {{status_seconds}} seconds.
- **Plugin rollout**: versioned plugin artifacts; canary on a small share of tasks per plugin, watch error rate, memory growth, throughput per task, widen in stages, roll back by pinning the previous version.
- **Secrets**: an error-message sanitiser on every path to logs and status (patterns for connection strings, tokens), plus plugin guidelines and tests.
- **Capacity**: bin-pack tasks by measured resource use; headroom per pool so a worker loss can be absorbed; scale pools on utilisation; move a tenant to a dedicated pool by size or noisy history.

**Competing designs to accept.** One container per task with an orchestrator (simple isolation, higher cost at {{tasks}} tasks, with packing considered). One worker group per tenant (strong isolation, many groups to manage). A shared worker group with sticky, incremental rebalancing and per-task process isolation.

**Bottlenecks and failure modes.** Group membership churn that pauses unrelated tasks; crash loops amplifying load on external systems; correlated failures from a bad plugin version; tasks alive but stuck; secrets in error text; status lag.

**Incident guidance.**
- *400 crash-looping tasks pause other tenants*: membership churn from restarts is triggering rebalances. Stop the loop (pause the tenant's connector or set the tasks to backoff), and decouple task restarts from worker membership (restart tasks inside a worker without leaving the group; incremental assignment). Show the customer "source unreachable" rather than restarting forever.
- *Memory leak in a plugin version*: correlated failure; tasks moving together spread it. Roll back the plugin version fleet-wide, cap per-task memory so a leak kills one task not the worker, and add memory growth to canary criteria.
- *Running but writing nothing*: liveness without progress. Add a progress check (time since last successful write while input exists) that marks the task degraded and alerts the customer, with a timeout on sink operations so a lock wait ends in a retriable error.
- *Password in error message*: purge the logs and status history that hold it, tell the customer to rotate the credential, and add a sanitiser on every error path, with a test that scans error output for secret patterns.

**Follow-up guidance.** Push on what exactly moves when a worker restarts in their design; on what "failed" means and who is told; and on cost per task at {{tasks}} tasks.

**Rubric anchors.** 2: run tasks on a pool of workers and restart on failure; no isolation, no progress signal. 3: desired-state control plane, external positions, isolation by blast radius, backoff with a terminal state, progress-based health, staged plugin rollout. 4: also incremental assignment that keeps unrelated tasks running, sanitised errors, capacity and cost reasoning, and crisp handling of every incident.

**Strong signals.** Treats plugins as untrusted code; separates desired from observed state; defines failure precisely. **Red flags.** Restarting forever; one shared group where any change pauses everything; status that only reflects liveness.

## CFL-L4-05

**Reference architecture (one defensible design; score others on the criteria).**
- **Model**: per broker: disk used and capacity, network bytes in and out, leader count, replica count, rack. Per partition: size, bytes in (applies to every replica), bytes out (mostly from the leader, to consumers), replica list and leader. Measured over a window (for example the busiest hour of the last week), not a snapshot.
- **Objective and constraints**: hard: one replica per rack where possible, disk headroom (for example below 80% after the move, counting the temporary extra replica), never reduce a partition's in-sync count below its minimum, a move's copy rate must exceed the partition's bytes-in rate under the throttle. Soft: minimise the spread of disk, network and leader load across brokers, weighted, per byte moved.
- **Planner**: a greedy or local-search heuristic over candidate moves (move one replica from a hot broker to a cool one, or swap two replicas), scored by load improvement per byte moved, rejecting moves that break constraints; leader moves considered first because they move no data. At {{partitions}} replicas a full solver is usually too slow to re-run often; local search with a time budget is the norm.
- **Executor**: batches of moves with a concurrency limit per broker (in and out), throttle at {{throttle_mb}} MB/s per broker on the copying traffic only; each move adds the new replica, waits until it is in sync, optionally transfers leadership, then removes the old replica. Progress = bytes copied versus bytes planned, per batch. Pause on rising producer latency, under-replicated partitions or broker failure; abort cancels the batch's pending moves and restores replica lists for moves that had not completed.
- **Duration estimate**: total bytes ÷ (throttle × number of brokers receiving in parallel, limited by concurrency and by the slowest broker), plus catch-up for data arriving during the copy. 14 TB at {{throttle_mb}} MB/s per new broker across {{new_brokers}} new brokers gives a lower bound; strong candidates compute it.
- **Leaders**: preferred leader balancing in small steps, watching outbound network on the receiving brokers.
- **Continuous balancing**: run with thresholds and hysteresis (act only if imbalance exceeds a band for a sustained time), a cap on bytes moved per day, and an operator lock that suspends it during manual work.

**Competing designs to accept.** Moving whole partitions versus swapping replicas; a mixed-integer or constraint solver for small clusters or offline planning; balancing on a single metric (disk) with leaders balanced separately, if the candidate shows when that fails.

**Bottlenecks and failure modes.** Partitions that can never catch up under the throttle; temporary replica growth filling disks; broker failure mid-move; leader moves saturating networks; throttle too high hurting producers; planner and cluster drifting during long plans.

**Incident guidance.**
- *Twice the estimate, 40% done, three replicas never join*: the hot partitions' bytes-in exceeds their throttled copy rate. Exclude them from the throttle (or raise it only for them at a quiet time), move them during low traffic, or rebalance them by moving leaders and quieter partitions instead. Prevention: the catch-up condition as a hard constraint in the planner.
- *Broker fails mid-batch, not-enough-replicas errors*: partitions have a half-copied new replica and one surviving old one; with a minimum of two, producers using acks=all fail. Restore the failed broker if possible; otherwise prioritise catching up those new replicas (raise their throttle), or temporarily reassign to fully in-sync brokers; never lower the minimum silently. Prevention: limit concurrent moves per partition and avoid batches where one broker failure would leave a partition below its minimum.
- *Leaders moved in one step, one broker's network saturated*: move leadership back in part; then move leaders gradually with outbound network as a constraint, and account for consumers that fetch from leaders.
- *Throttle tripled, producer p99 up fourfold*: lower it; the source brokers' disks were serving copies and old-data consumer reads. Throttle by measured disk and network headroom (adaptive), not a fixed number, and schedule heavy moves at off-peak.

**Follow-up guidance.** Push for the duration arithmetic and the catch-up condition; ask how they prove the plan never reduces in-sync replicas below the minimum; at Very Hard ask how the planner handles cluster changes during a plan that runs for days.

**Rubric anchors.** 2: "move partitions to the new brokers" with no constraints, no estimate, no batching. 3: load model with racks and headroom, plan scored per byte moved, batched execution under the throttle with monitoring, leader moves separately, duration estimate. 4: also the catch-up condition, failure-safe batching that respects minimum in-sync replicas, adaptive throttling, continuous balancing with hysteresis, and crisp handling of every incident.

**Strong signals.** Computes duration before designing; notices that a replica cannot join if it copies slower than data arrives; balances leaders without moving data first. **Red flags.** Moving everything at once; ignoring racks; removing old replicas before new ones are in sync.
