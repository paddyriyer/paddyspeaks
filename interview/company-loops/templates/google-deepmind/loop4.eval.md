# Google DeepMind · Loop 4 — evaluator notes (hidden from candidates)

All figures in these scenarios are hypothetical and synthetic. Score designs on
the criteria, not on resemblance to the reference; none of the references
describes how any lab's systems are actually built, and none states or implies
a real research result, benchmark score, compute figure or partner arrangement.

## GDM-L4-01

**Reference architecture (one defensible design; score others on the criteria).**
- **Recipe capture at launch**: the launcher writes a manifest before the first step runs: the code tree hash of the working directory (the commit plus a stored copy of the uncommitted diff, itself content-addressed), the container image digest (never a tag), the resolved dependency lockfile, the data snapshot id, the fully resolved configuration after defaults, files and overrides (not only the overrides), every seed (initialisation, data order, dropout, sampling), the accelerator type, count and topology, the parallelism layout, the loader worker count and other settings that change numerics, the launch command and the launcher's own version. The manifest is hashed and written to an append-only store; the run record references the manifest hash. Capture runs locally and fast (hashing a diff and reading digests, not uploading the world); uploads of the diff and lockfile are content-addressed, so repeats cost nothing.
- **What cannot be pinned**: external downloads at run time (a tokenizer or file from a public URL) are either fetched through a caching proxy that stores them content-addressed, or recorded as "unpinned: URL, time, observed hash". Non-deterministic kernels are recorded as such (a determinism flag per run). A capture failure marks the run "partially pinned" with the missing parts listed; it never looks complete.
- **Retention by reachability**: images, diffs, lockfiles, data shards and chosen checkpoints are kept in content-addressed storage. A "keep" set (runs cited in papers or reviews, release runs, and a policy sample) roots retention for {{lookback}}; everything reachable from a kept manifest (including every shard a snapshot manifest references, not just the manifest) is protected from clean-up. Unkept runs age out on a shorter policy, and their reports say when inputs expired.
- **Re-run service**: resolves the manifest, pulls the image by digest, materialises the snapshot by manifest, applies the stored diff, sets the seeds and topology, and launches under a new run id linked to the original. It never writes to the original's records. Where the original hardware is retired, it uses the closest available type and marks the re-run "different hardware". For very large runs it supports partial reproduction: the first stretch of steps compared step by step, or resuming from a recorded checkpoint, each labelled as partial.
- **Comparison**: aligns metric curves by step, reports the first step where the re-run leaves a band around the original, and compares final metrics against {{tolerance}}. Outcome levels: bitwise identical; reproduced within tolerance; partial (what was reproduced); different hardware; not reproduced, with the reason (inputs expired, unpinned input changed, or pinned and still different). An early divergence points to a changed input; a late, slow drift points to accumulated non-determinism.
- **Tamper evidence**: manifests and final metrics are written once to an append-only log with hashes chained or anchored (signed daily digests), so a reviewer can verify that a manifest and its results existed at a date and were not changed.
- **Cost**: storage for kept images, snapshots and checkpoints over {{lookback}}, plus a re-run accelerator budget with a queue and priorities (paper review and release first).

**Competing designs to accept.** Forbidding uncommitted launches for kept runs (a run becomes "keepable" only from a clean tree), if the candidate handles the friction. Reproducing by re-executing from a recorded checkpoint by default and reserving full re-runs for sampled audits. Deterministic kernels by default only for small runs, with the cost stated. Using an existing experiment tracker plus a manifest convention, if pinning and retention are still solved.

**Bottlenecks and failure modes.** Image tags instead of digests; recording overrides but not the resolved configuration; garbage collection that protects manifests but not the shards they reference; external downloads at run time; numerics-affecting settings (worker count, parallel layout, mixed-precision mode) outside the recipe; re-runs that overwrite the original's records; "reproduced" asserted without a stated tolerance.

**Incident guidance.**
- *Image base layers deleted and 3% of snapshot shards collected*: retention walked only one level (manifest, not shards; tag, not layers). Recovery: report the run honestly as "not reproducible: inputs expired", listing what is missing; try rebuilding the image from the lockfile and recording the rebuild as different; if the shards came from registered sources, regenerate the snapshot only if the pipeline was deterministic and record it as a reconstruction. Prevention: reachability-based retention from kept manifests through every referenced object, image digests with layers pinned, and a periodic audit that resolves every kept manifest end to end.
- *Re-runs differ by twice {{tolerance}}; worker count drove the shuffle*: an unrecorded input. Recovery: add the worker count to the recipe, re-run with the original value where known (from logs), and reclassify the earlier reports. Prevention: treat every setting that can change numerics as part of the recipe, with a test that perturbs candidate settings in small runs and flags those that change curves; make the data order a pure function of the seed and step.
- *Configuration default changed by a library upgrade*: storing overrides only made the recipe depend on library defaults. Recovery: for affected runs, reconstruct the resolved configuration from the library version in the lockfile and mark it reconstructed; re-run with it. Prevention: store the fully resolved configuration at launch and diff it on re-run before any accelerator time is spent.

**Follow-up guidance.** For the uncommitted launch, look for the stored diff as a content-addressed object and the resolved configuration, not just "the commit hash". For the drifting curve, look for the first-divergence step and the reasoning about early versus late divergence. For retired hardware, the honest answer is that reproduction becomes "within tolerance on different hardware" at best, and the report must say so. For tamper evidence, credit append-only storage with hashes and anchoring, not "we restrict write access".

**Rubric anchors.** 2: "log the git hash and the config", no pinning of data or environment, no comparison rule. 3: a full manifest with digests and resolved configuration, content-addressed retention, a re-run service that compares against the tolerance, honest outcome levels. 4: also reachability-based retention with audits, unpinned inputs recorded, partial reproduction labelled, tamper evidence for reviewers, costs stated, and crisp handling of every incident.

**Strong signals.** Asks what counts as "the same result" before designing; distinguishes "could not be pinned" from "pinned but different". **Red flags.** Claiming bitwise reproducibility is always achievable; copying full datasets per run; letting a re-run update the original run's records.

## GDM-L4-02

**Reference architecture (one defensible design; score others on the criteria).**
- **Object layout**: every file is immutable and named by entry id and version (for example `.../{accession}-F{n}/v{model_version}/structure.cif`), or by content hash with a version manifest mapping names to hashes. Per-release manifests list every entry and file with checksums. Nothing under a versioned path is ever rewritten.
- **Latest pointers**: a small pointer table maps (accession, fragment) to its current version and status (current, withdrawn with date). Release switch = publish a new pointer table (versioned) and flip one global "current release" pointer; pages and the API resolve through it.
- **Caching**: immutable files get very long cache lifetimes at the edge and in browsers. The "latest" address is either a redirect to the versioned address (short-lived, cached for a bounded time such as minutes) or served with the version in a response header. Cache keys are normalised: unknown query strings are stripped or ignored so tracking parameters cannot bypass the cache. Pages embed versioned file URLs, so a page and its files always agree; the page itself is cached briefly and keyed by the release.
- **Release switch consistency**: because pages reference versioned files, the only inconsistency window is "old page or new page", never a mix. The switch is complete when the pointer cache lifetime has elapsed (bounded, well inside the hour); optionally purge pointers and pages by tag at switch time.
- **API**: lookups by accession return the current version plus links to versioned files; lookups by entry id and version are fully cacheable; batched lookups accept a bounded list. Responses carry the release id.
- **Abuse protection without logins**: per-client limits keyed on address ranges with generous thresholds for shared networks, plus an optional free key that raises limits; bulk users are steered to archives and mirrors (rejecting crawls of the API for whole organisms with a helpful message). Edge capacity absorbs spikes; the origin is shielded by a single regional cache tier (request collapsing).
- **Bulk delivery**: per-organism and per-release archives with stable names, a manifest with checksums, availability through a public cloud bucket and partner mirrors, resumable range requests, and a "changes since release N" manifest so mirrors fetch only added, changed and withdrawn entries.
- **Citation**: versioned entry ids are citable forever; the latest address of a withdrawn entry says withdrawn and links to the versions. Each release has a stable identifier and a release note. Old releases may move to cheaper storage but keep the same addresses.
- **Monitoring**: synthetic checks that fetch a page and its files and verify they share a version; cache hit ratio by path class; origin load; egress by client class against budget.

**Competing designs to accept.** Content-hash naming with a manifest instead of version paths. Serving latest directly (no redirect) with the version in a header and cache purge by tag at switch. Moving bulk delivery entirely to a requester-pays or partner-hosted bucket if the budget demands it, stated as a trade-off for users.

**Bottlenecks and failure modes.** Mutable files under unversioned paths; cache keys that include arbitrary query strings; pages and files with independent cache lifetimes; release switches done file by file; bulk users crawling the API; archives re-uploaded with new timestamps but no content change; removing old releases and breaking citations.

**Incident guidance.**
- *Tracking query strings bypass the cache*: normalise cache keys at the edge (ignore unknown parameters) immediately, enable request collapsing at the shield tier, and serve a cached page under load. Prevention: a cache-key policy that whitelists meaningful parameters, and an alert on hit-ratio drops by path class.
- *New structures coloured by old confidence values for forty minutes*: pages fetched unversioned confidence data, cached separately. Recovery: purge pages and pointers by release tag. Fix: pages reference versioned files only, so mixing is impossible by construction; a synthetic check after each switch verifies page and file versions agree.
- *Daily full re-download of {{archive_tb}} TB*: the client keyed on last-modified time. Recovery: contact the client, restore stable validators (strong ETags from content hashes), and rate-limit full archive pulls per client. Prevention: content-hash validators that survive re-uploads, a changes-since manifest, documented mirroring guidance, and egress monitoring per client class with alerts well before the budget.

**Follow-up guidance.** For the release-switch minute, the candidate should show the user seeing the old or the new version, never a mix, and say when every edge has converged. For the viral link, look for edge absorption and request collapsing. For the error correction, credit a new version (or a corrected release) with the faulty version still resolvable and clearly marked, never a silent overwrite.

**Rubric anchors.** 2: one database and file server behind a CDN with default caching, files overwritten per release. 3: immutable versioned files, short-lived pointers, normalised cache keys, versioned citations, archives with checksums. 4: also page and file consistency by construction, incremental mirror sync, abuse protection without logins that treats shared networks fairly, egress budgeting, monitoring of what users receive, and crisp handling of every incident.

**Strong signals.** Separates immutable content from mutable pointers in the first minutes; asks how bulk users behave. **Red flags.** Purging the whole CDN at every release as the main mechanism; requiring logins for public downloads; drawing medical conclusions from predictions.

## GDM-L4-03

**Reference architecture (one defensible design; score others on the criteria).**
- **Check path**: the file is received into memory or ephemeral storage that is wiped at request end; the detector is called; the response is returned; an outcome record is written with only the agreed fields (time bucketed to the hour, channel, content type, coarse size and duration buckets, detector version, outcome, confidence level, count of flagged segments, cohort, and a keyed hash for repeat detection). Logging, tracing and error paths are configured to exclude bodies, and a test submits marked synthetic files and asserts that the marker appears nowhere in logs or storage.
- **Repeat checks**: a keyed hash (HMAC with a key rotated every {{record_days}} days and destroyed afterwards) lets the pipeline count distinct files per day and collapse retries; once the key is destroyed, no one can test whether a given file was checked in that period.
- **Aggregation**: a daily job builds aggregates per (week, channel, content type, confidence level, outcome, detector version) with both "checks" and "distinct files" measures. Publication enforces the minimum cell of {{min_cell}} at the final output of every published table, after all splits; small cells are merged into an "other" row or suppressed with complementary suppression, so totals cannot be differenced to recover them (or totals are published only at levels where every child cell is publishable).
- **Rollouts**: version assignment by a stable hash of a per-request random id (not partner, not content type), at {{rollout_share}} and up. A mix check compares content type, channel and size distributions between cohorts each day and blocks interpretation when they differ beyond a threshold.
- **Disagreement**: a sampled share of live checks is run through both the current and the candidate versions while the content is in hand; only the pair of outcomes and confidence levels is recorded. The report is a confusion matrix per content type and confidence level, with counts and intervals, and the direction of change. The lab's own test set (owned synthetic files) is replayed through every version for calibrated comparisons and regression tests.
- **Reporting**: every report states which versions and dates it covers, separates cohorts, and shows mix alongside outcomes. Outcome records are deleted after {{record_days}} days; aggregates are kept.

**Competing designs to accept.** No hash at all, accepting inflated counts with a stated bias and client-side retry ids instead. Running the candidate version as a pure shadow (results never returned) until a threshold of agreement is met. Differential-privacy noise on partner-facing aggregates instead of, or in addition to, suppression, if explained.

**Bottlenecks and failure modes.** Content captured in request logs, crash dumps or queues; unkeyed hashes that let anyone test whether a file was checked; thresholds applied before a later split; cohorts assigned by partner or content type; comparing week-over-week shares across a version change without controlling for mix; any discussion of making detection fail.

**Incident guidance.**
- *Audio "not detected" up six points in the new cohort*: cohorts assigned by partner, so the cohort carried a different content mix (older recordings that never carried a watermark). Recovery: stop interpreting the comparison, re-assign by per-request hash, and use the dual-run disagreement data (same content, both versions) to judge the version. Prevention: assignment independent of partner and content type, daily mix checks, and a rule that version decisions use paired comparisons.
- *A cell of four checks published*: the threshold ran before the re-split. Recovery: withdraw the chart, notify the partner channel's owners through the proper process, and check other outputs for the same flaw. Prevention: enforce the threshold in the publication layer on final outputs, plus a test over every published table.
- *Retry bug fivefold*: counts of checks were used where distinct files were meant. Recovery: recompute aggregates with distinct-file counts per day via the keyed hash and republish with a note; tell the partner about the bug. Prevention: report both measures, alert on per-channel jumps, and collapse retries by request id at ingestion.

**Follow-up guidance.** For the video walk-through, look for exactly what exists at each step and how long (content seconds, record {{record_days}} days, aggregates longer). For "a single number that says better", a strong answer refuses one number and gives per-content-type disagreement with direction and intervals, plus test-set results. Redirect any candidate who drifts into how watermarks could be defeated: it is out of scope and should not be rewarded.

**Rubric anchors.** 2: store the files for debugging, dashboards over raw records, versions compared week over week. 3: outcome records without content, minimum cells at publication, hash-based cohorts, disagreement from dual runs. 4: also keyed and rotated hashes with a stated purpose, protection against differencing, mix checks, a test proving no content is kept, and crisp handling of every incident.

**Strong signals.** Notices early that "no content kept" means disagreement must be measured at request time. **Red flags.** Keeping a "small sample" of user content; plain hashes; describing ways to evade or weaken a watermark.

## GDM-L4-04

**Reference architecture (one defensible design; score others on the criteria).**
- **Inputs**: proposals with revisions (requested hours per month and accelerator type, milestones, substitutable types), panel scores with a "final" status, the pool per type and month, the reserve share ({{reserve}}), and the rule version. An allocation run first freezes these into a snapshot with an id and refuses to run unless every proposal has a final score.
- **Rule as code**: a pure, versioned function from snapshot to allocations (tiers by score, top tiers funded with documented trims, lower tiers pro rata on what remains, rounding to whole hours with a stated tie rule). Output stored with the snapshot id and the rule version; anyone with access can re-run it and get the same result. Explanations are generated from the same run: tier, score, the trim or pro-rata factor and the pool constraint that bound.
- **Ledger**: initial grants plus appended entries (trim, return, reserve draw, transfer, correction), each with amount per type and month, reason, requester and approver. Current allocation = sum. Invariant per type and month: sum of allocations + remaining reserve ≤ pool, checked on every write.
- **Usage**: daily per-project totals from the accounting feed, with a completeness watermark per project ("complete through date D"). Corrections update usage with history. Burn forecast per project from recent rate and the plan.
- **Checkpoint**: at week {{checkpoint_week}}, the rule evaluates only projects whose usage is complete through the checkpoint date; incomplete ones are deferred, not penalised. A returning project keeps its remaining plan plus a margin; returns go to the waitlist in score order, then to the reserve. Project leads get notice and a short appeal window before the return applies.
- **Reserve**: one request queue, a visible running balance, approvals by a named rota with limits per approver and per week, and a draw-down guideline (for example no more than a third of the reserve before mid-quarter without panel sign-off).
- **Scheduler interface**: allocations become per-project entitlements per type and month (a number and dates); the scheduler decides when jobs run and reports usage back. Over-use is visible and flagged; enforcement policy is the scheduler's and the panel's decision.

**Competing designs to accept.** An optimisation model instead of tiers, if its output is explainable and reproducible from the snapshot. Monthly allocations with automatic expiry instead of a single checkpoint. Allowing a small carry-over with a cap, if the rule is published.

**Bottlenecks and failure modes.** Running the rule on live tables; spreadsheets as the system of record; returns computed from incomplete usage; reserve approvals in chat; allocations edited in place; confusing allocation (entitlement) with scheduling (when jobs run).

**Incident guidance.**
- *Twelve proposals allocated on last quarter's scores*: the snapshot was taken before scores were final. Recovery: re-run the rule on a corrected snapshot, compare with the published allocations, and apply the differences as ledger corrections with an explanation; protect runs already started (adjust later months first) and have the panel approve the correction. Prevention: the run refuses to start unless every score is final and from the current cycle; a diff report before publication.
- *Hours taken from a project with stale usage*: the checkpoint used whatever had arrived. Recovery: reverse the return with a ledger correction, restoring hours from the reserve if they were already reassigned, and tell the project lead. Prevention: completeness watermarks and deferral of incomplete projects; an alert when the accounting feed lags.
- *Reserve exhausted by week three*: no shared queue or balance. Recovery: freeze reserve approvals, review the draws with the panel, and recover any unused draws. Prevention: one queue with a visible balance, approver limits and a draw-down guideline.

**Follow-up guidance.** For a disputed allocation, look for an explanation generated by the same run (tier, factor, binding constraint) and the ability to re-run on the snapshot. For the milestones question, a strong answer links allocations to milestones and reports outcomes, while saying plainly that usage cannot measure research value.

**Rubric anchors.** 2: a spreadsheet and a meeting, allocations edited in place, no reproducibility. 3: a frozen snapshot, a versioned rule, a ledger with reasons, usage against allocation, an explicit checkpoint rule. 4: also invariants on every write, completeness-aware checkpoint decisions, a governed reserve, readable explanations, a clean scheduler boundary, and crisp handling of every incident.

**Strong signals.** Separates allocation from scheduling and accounting without being told; treats the rule as code with tests. **Red flags.** Ranking researchers or teams by usage as a measure of worth; a black-box optimiser with no explanation; taking hours back on forecasts alone.

## GDM-L4-05

**Reference architecture (one defensible design; score others on the criteria).**
- **Data model**: `suite_version` (suite, version, item ids with item versions, an item-set hash); `scorer_version`; `run` (checkpoint, suite version, harness, prompt template version, sampling settings, samples per item, team, time); `output` (run, item, sample index, output reference) kept {{output_days}} days; `item_score` (run, item, scorer version, score); `result` (run, scorer version, aggregate, item count, interval, comparability key, result version, superseded_by).
- **Comparability key**: hash of item-set hash, scorer version, prompt template version and normalised sampling settings (temperature, samples per item, aggregation over samples, maximum length). Stored on every result and indexed. Two results are directly comparable when keys match; comparisons across differing suite versions are allowed only on the shared items, re-aggregated, and labelled.
- **Ingestion contract**: a versioned schema that requires the comparability fields as typed values (no free text), checkpoint and harness identifiers and per-item outputs and scores; validation rejects or quarantines runs that fail, with a message to the team. New results become queryable within the hour (append to per-item tables, compute aggregates incrementally).
- **Rescoring**: a new scorer version triggers a backfill that reads stored outputs and writes new item scores and new result versions linked to the old (the old stays visible, marked superseded). The backfill runs in a lower-priority lane with its own capacity so ingestion keeps its hour; the most-read results (recent checkpoints, dashboards) are rescored first. Results whose outputs have expired stay on the old scorer and are labelled; trend views either show only results with the new scorer or draw a marked break.
- **Comparison API**: given two results, computes the shared items, the paired per-item differences, their mean and an interval (paired bootstrap or normal approximation), and returns the shared-item count, what was excluded and why. It refuses comparisons where scorer, prompt template or sampling settings differ unless the caller explicitly asks for a labelled cross-configuration view.
- **Lineage**: every aggregate links to its run, scorer version, item scores and outputs; charts carry the keys.
- **Sizing**: per-item rows = checkpoints per week × suites run × items × samples; outputs dominate storage (long programs and essays), which is why their retention is bounded at {{output_days}} days.

**Competing designs to accept.** Storing only aggregates plus outputs and recomputing per-item scores on demand. A single canonical harness that all teams must use, if the candidate handles migration. Treating each suite version as a separate suite with explicit crosswalks of items.

**Bottlenecks and failure modes.** Aggregates without item-level data (no paired comparison, no rescoring); keys that omit sampling settings; in-place updates that destroy cited numbers; backfills that starve ingestion; trend charts across scorer or suite changes with no marks; free-text configuration fields.

**Incident guidance.**
- *Two-point gain from removed items*: the dashboard compared across item sets. Recovery: recompute the comparison on shared items and correct the dashboard with a note. Prevention: the comparison API refuses or re-aggregates on shared items by default, and dashboards use it rather than raw aggregates.
- *Backfill delays ingestion; trend chart mixes scorers*: Recovery: move the backfill to its own lane and throttle it; mark the trend chart's scorer boundary or restrict it to one scorer version. Prevention: priority lanes with capacity reserved for ingestion, scorer version as part of every chart's key, and a published policy for expired outputs.
- *Two harnesses, one key*: sampling settings were not in the key. Recovery: split the results by recovering the settings from each team's run metadata, relabel, and say which is comparable to what; neither is "official" by default. Prevention: typed sampling fields in the contract and in the key; a check that flags two results with the same key for the same checkpoint that differ beyond their intervals.

**Follow-up guidance.** For the 40 removed items, the right answer is a labelled comparison on the shared items or a refusal, never two raw averages. For the six-month trend, credit marking suite and scorer changes on the chart and offering a view restricted to one comparability key.

**Rubric anchors.** 2: a table of (checkpoint, suite, score), updated in place, compared freely. 3: per-item scores, a comparability key, immutable result versions, a rescoring backfill. 4: also paired comparisons with intervals on shared items, an enforced ingestion contract, priority lanes, explicit handling of expired outputs, lineage, and crisp handling of every incident.

**Strong signals.** Asks what makes two results comparable before drawing a schema; reports item counts with every delta. **Red flags.** "The latest score wins"; comparisons with no uncertainty; quoting real benchmark numbers for any model.
