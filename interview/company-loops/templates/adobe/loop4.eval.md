# Adobe · Loop 4 — evaluator notes (hidden from candidates)

## ADB-L4-01

**Reference architecture (one defensible design; score others on the criteria).**
- **Event contract**: a schema registry with one typed schema per event type (launch, heartbeat, feature_used, export, cloud_save, error, quit), versioned with compatibility rules (additive only; renames and removals through a new version). No free-text fields; enumerated values only, so no document content, file name or typed text can travel. Every event carries `event_id, install_id, user_pid, app_id, app_version, platform, client_ts, seq_no`, plus the client's upload time.
- **Collection**: apps batch events, buffer to disk while offline (bounded by the offline window and a size cap), and retry with the same event ids. The collector authenticates the app, validates against the registry (unknown or invalid events go to a quarantine table with counts per app version), stamps receive time, and writes to a durable log partitioned by `user_pid`.
- **Sharing setting**: the apps stop sending locally; the collector also holds an opted-out set fed by the privacy settings service and drops any event from an opted-out user whose `client_ts` is after the opt-out time (defence in depth against client bugs). Deletion: a tracked deletion job per opt-out removes identifiable rows from raw, cleaned, sessionised and per-user derived tables, and from backups by expiry or crypto-shredding (per-user or per-partition keys), with a completion record per request inside the deadline. Aggregates without user identifiers may stay; per-user derived tables (first export reached, adoption keyed by user) are rebuilt or have the user's rows deleted.
- **Cleaning**: dedup on `event_id` (and on `(install_id, seq_no)`); event time is `client_ts` validated against receive time (future or impossibly old times flagged and replaced by receive time, keeping both); gaps in `seq_no` measure loss per version.
- **Feature catalogue**: (app_id, app_version range, event name, parameters) → canonical feature id, with lineage for splits and merges (a split's two new ids both roll up to the parent feature). Owned jointly: an app's release pipeline fails if it emits event names absent from the catalogue. Metrics are computed on canonical ids.
- **Definitions**: an active user is a pseudonymous user with at least one foreground, user-initiated event (not background update launches) in the period; suite-level and per-app counts are reported separately. A session is a run of foreground activity per (install, app) ending after N minutes without activity, where activity is derived from user-action events, not heartbeats alone, so a heartbeat-interval change does not change session counts; desktop focus loss and mobile backgrounding are explicit events.
- **Storage and serving**: raw log → cleaned events (partitioned by event date, clustered by app) → sessions and daily per-user activity → aggregates (daily and weekly actives per app and feature, adoption by version, export funnel). Late events update the event date's partitions; daily metrics are provisional for the offline window and then final, with a "provisional" mark in dashboards.
- **Release comparison**: compare versions on the same users before and after updating (within-user change), or on cohorts matched by activity level before the update; report adoption curves by days since release; and flag metric definitions that depend on version-specific events.
- **Quality monitoring per release**: unmapped event names, schema rejections, volume per active user by version, sequence gaps, and any events received from opted-out users.

**Competing designs to accept.** Install-level counting with a user-level rollup where signed in, if the candidate states what product gets. Deletion by partition rewrite on a schedule versus per-user keys and crypto-shredding. Streaming sessionisation versus daily batch, given daily dashboards (a 6-hour release view can be a small streaming or micro-batch path). A semantic-layer metric store over the cleaned tables.

**Bottlenecks and failure modes.** Event renames silently breaking metrics; heartbeat-based sessions that shift with each release; late offline uploads counted on arrival day; opt-out enforced only on the client; deletion that misses derived tables and backups; early-adopter bias in release comparisons; hot users with very many events.

**Incident guidance.**
- *Tool event renamed, 40% "drop"*: a catalogue gate in the release pipeline would have blocked the unmapped name. Map the new name to the canonical feature id and recompute the affected days; add the release check and a monitor for feature-use shifts that coincide with a version rollout.
- *Mobile version sends after opt-out*: the server-side opted-out filter should have dropped them; if it did not exist, add it now, delete everything received after each user's opt-out time from every store, record the incident with the privacy owner, and block that version's events until fixed. Monitor: count of events from opted-out users per version (should be zero).
- *Heartbeat interval change*: sessions were defined on heartbeats. Redefine sessions on user-action events and an inactivity gap that does not depend on the heartbeat, recompute affected versions, and correct the team's conclusion in writing.
- *Buffered upload spike*: charts must group by event date, not arrival date. Recompute by event date, mark recent days provisional for the offline window, and alert on arrival-versus-event-date skew.

**Follow-up guidance.** Push on the session definition (what ends a desktop session that stays open all day?), on how a split feature is compared across versions, and on every store a user's rows live in for deletion. Strong answers name derived per-user tables and backups.

**Rubric anchors.** 2: one events table, counts by arrival day, opt-out only on the client, metrics on raw event names. 3: typed contract with no content, event-time attribution with dedup, a feature catalogue, server-side opt-out enforcement and a deletion process, clear active-user and session definitions. 4: also a release gate on unmapped events, heartbeat-independent sessions, deletion tracked across derived tables and backups within the deadline, fair release comparison, per-release quality monitors and crisp handling of every incident.

**Strong signals.** Defines the metrics before the pipeline; asks how features are named across versions. **Red flags.** Free-text event properties; "we filter opted-out users in the dashboard"; device ids treated as people without saying so; comparing early adopters with everyone else as a release's effect.

## ADB-L4-02

**Reference architecture (one defensible design; score others on the criteria).**
- **Event model**: the service emits typed lifecycle events keyed by `request_id`: `received` (account, plan, surface, feature, model version, region, client version, idempotency key if any), `input_moderation` (pass, or blocked with a category code), `generation_completed` or `failed` (error code from an enum, never a message), `output_moderation` per variant (pass or blocked with category code), `returned` (variant count, output format, credentials attached yes/no per variant), `cancelled`, and the server latencies for each stage. Clients send their own `first_image_shown` and `all_shown` times with the request id. The credit ledger emits `charged` and `refunded` events with the request id and amount.
- **Content exclusion by construction**: the event schemas allow only typed fields from an allowlist; error details are enum codes; the producing library cannot serialise strings outside allowlisted fields. Logs from the generation path go to a separate, short-retention store under the content controls, never to the analytics pipeline. A scanner on incoming events (length and entropy of string fields, unexpected fields) quarantines violations and alerts, and a purge procedure removes a field's history from raw storage and backups.
- **Request facts**: a stream job folds lifecycle events into one row per request with its final state (`blocked_input`, `succeeded_full`, `succeeded_partial`, `blocked_output_all`, `failed`, `timed_out`, `cancelled`). Retries: requests with the same idempotency key collapse into one; retries without one stay separate requests, and the charge is whatever the ledger says.
- **Metrics**: success rate = (full + partial successes) / (requests minus user cancellations), with partial shown separately; moderation rates per stage (input blocks / requests; output blocks / variants generated) by category, published only where the cell count ≥ the minimum (otherwise rolled up to "other" or a coarser grain); latency as mergeable sketches (t-digest, KLL or HDR histograms) per model version, surface, region and minute, merged for any rollup; client latency and server latency reported apart; credentials coverage = returned variants with credentials attached / returned variants, at return time from the service, and separately on export from apps' export events.
- **Credits**: analytics shows credits per account and month from the ledger's events, joined to request facts by request id; it never computes charges itself. A daily reconciliation compares charged requests with successful request facts and lists mismatches (charged but not successful, successful but not charged). Ledger corrections (refunds) flow as events and update the month's numbers with a "restated" mark.
- **Serving**: a streaming path for the dashboards within the freshness target (minute-level aggregates and sketches) and a batch path that recomputes daily from the request facts and is the record.
- **Comparisons**: new model versions roll out with a holdout or as a staged percentage on the same surface, and one change at a time (model or moderation threshold), so the effect of each is measurable; dashboards always split by model version and threshold version.

**Competing designs to accept.** A single warehouse fed by micro-batches if it meets the freshness target. Computing exact percentiles daily from per-request rows while sketches serve real time. Counting a partial block as a moderation event at variant grain only. Differential noise on small moderation cells instead of suppression, if justified.

**Bottlenecks and failure modes.** Free text leaking through error fields; retries double-counted against the ledger; averaged percentiles; two changes shipped together so effects cannot be separated; coverage metrics that measure the wrong point in the path; small moderation cells that re-identify accounts.

**Incident guidance.**
- *Prompt in error detail for 3 days*: stop it (block the field at the collector, roll back or patch the release), purge the field from raw storage, derived tables and backups, and record it with the privacy owner. Prevention: enum error codes only, schema allowlist in the producer library, and the scanner that quarantines long free-text strings.
- *Credits 4% above the ledger*: analytics computed charges itself. Switch to the ledger's events as the source of credits; collapse retries by idempotency key in request facts; reconcile daily and alert above a small threshold. Check whether users were actually charged twice (a ledger question) and refund if so.
- *Model and threshold shipped together*: separate them: roll one back on part of the traffic, or compare against the threshold's offline replay on stored moderation scores (no content needed if scores are logged) to attribute the change. Prevention: one change at a time per surface, with version fields on every event.
- *Coverage falls to 70%*: check the service's own attach events against returned variants to see whether credentials were attached; if they were, the metric's join or the event changed. Fix the side that broke and add a monitor that compares attach events with returned images directly.

**Follow-up guidance.** Ask for the exact counting of the four-variant, one-blocked request. Ask how they would prove no prompt reaches the warehouse; strong answers combine schema construction with a scanner and a purge plan. Probe retries without ids against the ledger.

**Rubric anchors.** 2: logs of requests with prompts "for debugging", averaged latency, credits computed in analytics. 3: typed schema with no content, request lifecycle facts, ledger as authority with reconciliation, sketches for percentiles, minimum cell sizes. 4: also producer-side enforcement plus scanner and purge, precise success and moderation definitions at the right grain, coverage measured at both points, one-change-at-a-time comparisons, and crisp handling of every incident.

**Strong signals.** Asks who owns credits before designing; says "enum, not message" for errors. **Red flags.** "We hash the prompt" as if that were safe; storing images "for quality"; one number for success that hides partial blocks; percentiles from averages.

## ADB-L4-03

**Reference architecture (one defensible design; score others on the criteria).**
- **Two products**: (1) the agreement audit trail, an append-only, per-agreement event log, owned by the e-signature service in the customer's region; (2) usage analytics, per-customer aggregates for reporting and invoicing.
- **Event schemas**: typed, with ids, types, statuses, timestamps, page counts, byte sizes, participant role and order; no file names, text or field values. Validation in the producing services' event library; a downstream scanner flags string fields with unexpected length or content and quarantines them. Logs from document workers stay in a separate, short-retention, access-controlled store, never in the reporting pipeline.
- **Audit trail**: the agreement's owning service assigns each event a per-agreement sequence number at the moment it applies the state change (the service's commit order is the true order; client and relay times are recorded but do not order). Each event stores the hash of the previous one (a chain per agreement); periodically, the heads of all chains in a time window are combined into a Merkle root written to an append-only store with separate access control (write-once storage, or a log whose roots are published to the customer or a third party), so rewriting a chain is detectable. Completeness: the agreement's state machine must explain every event (no "signed" without "sent to" that participant; terminal status reached), and sequence numbers must be gap-free before the final audit report is generated. Retention per the period, in the customer's region, with legal holds.
- **Usage analytics**: each billable operation has an `operation_id`; retries carry it, so the billable table counts each successful operation once (failed ones are recorded but not billable). Pages come from the converter's output metadata. One billable usage table per region feeds both the customer's report and the invoice, so they cannot differ; reports are generated from the same closed month.
- **Residency**: all customer-level data stays in region. The global platform dashboard receives only aggregates without customer identifiers (or with an opaque, region-local key), which the residency policy allows.
- **Isolation**: customer id on every row; access through a data-access layer that requires it; per-customer report exports; tests that try cross-customer reads.
- **Admin reports**: agreements waiting on a signer and completion times are projections of the audit trail per customer.

**Competing designs to accept.** A ledger database with built-in verification instead of a hand-built hash chain. Billing computed in a separate billing system if the usage report reads the same table. Global analytics with differentially private aggregates. Per-region warehouses federated for platform queries.

**Bottlenecks and failure modes.** Content leaking through logs and debug fields; double-counted retries; ordering by arrival across regions; audit trails issued while events are still in transit; regional pipeline outages; tenant leaks in shared report infrastructure; very long retention costs.

**Incident guidance.**
- *OCR text in a debug field*: stop the field at ingestion, purge it from the reporting pipeline, raw storage and backups, notify the privacy and security owners (and customers if the contract requires it). Prevention: typed schemas without free text, the scanner, and worker logs kept out of the reporting path.
- *12% page dispute*: dedupe by operation id, recompute the month, issue a corrected report and invoice credit, and tell the customer exactly why. Prevention: operation ids required on billable events, a reconciliation of billable rows against converter job records.
- *Signed before viewed*: order by the owning service's sequence number, not arrival; regenerate affected audit reports and tell affected customers which reports were reissued and why.
- *6-hour regional outage*: the services must buffer events durably and the final audit report must not be generated until the trail is complete (gap-free sequence, state machine satisfied). Regenerate the reports for the window, notify customers who downloaded incomplete ones, and add a completeness check before issuing.

**Follow-up guidance.** Ask what exactly makes the trail tamper-evident against an insider with database access (the anchoring outside their control). Ask how the invoice and report are guaranteed equal (same table). Probe residency for the global dashboard.

**Rubric anchors.** 2: one shared event table, ordering by timestamp, file names "for support", billing counted separately from reports. 3: separate audit trail and usage analytics, typed content-free schemas, operation ids for retries, per-region storage, sequence-ordered audit events. 4: also tamper evidence anchored outside the writers' control, completeness checks before final reports, one table for invoice and report, isolation enforced centrally, and crisp handling of every incident.

**Strong signals.** Treats file names as content; asks what "true order" means. **Red flags.** Reading document text "to classify usage"; audit trails assembled from analytics tables; a global warehouse with customer-level rows from every region.

## ADB-L4-04

**Reference architecture (one defensible design; score others on the criteria).**
- **Model**: components are immutable blobs addressed by hash (chunked for large components, so a changed layer uploads only changed chunks). A version is a manifest listing component hashes plus metadata (parent version id, device id, author, save type autosave or named, logical size). A document has a small mutable record: the current version id, plus any open conflict siblings.
- **Upload and commit**: the client asks which component hashes the server lacks, uploads those with resumable, chunked uploads, then commits the manifest. Commit is a conditional write: the server verifies every listed component exists, then sets current = new version only if current still equals the manifest's parent (compare-and-set). If current has moved, the commit still stores the version but records it as a sibling of the current one: a conflict.
- **Conflicts**: two versions with the same parent. Both are kept; the document shows the most recent commit as current with a visible "conflicting version from <device>" that the user can open side by side, keep, or save as a copy. Device clocks never decide; server commit order and parent pointers do. Edits to disjoint components (different layers or artboards) may be combined automatically if the apps support it; pixel edits to one layer are never merged.
- **Propagation**: on commit, a notification goes to the user's other online devices (a push channel per device); they fetch the manifest and then the components lazily or eagerly by document size and network. Offline or sleeping devices catch up by asking for changes since their last known version on wake.
- **Quota**: under the rule, used = sum of logical size of current versions + documents in trash; version history excluded. Kept as a counter per user updated transactionally with commits and deletes, and recomputed nightly from manifests to catch drift (with an alert, never a silent enforcement change). The check happens before upload begins (the client declares the new logical size), so a save is not refused after half its bytes arrived; in-flight saves started under quota complete.
- **Garbage collection**: reference counts or periodic mark-and-sweep from live versions (current, conflicts, history within 30 days, trash); a component is deleted only after it has been unreachable for a grace period, since an upload in progress may reference it before its manifest commits.
- **Sync latency**: measured per save from commit on the server to the other device's acknowledgement that it has the new version as current (and separately when bytes are downloaded), for every device of the user. Reported in two populations: devices online at commit (the target) and devices that were offline (time to catch up after waking), so asleep devices are visible, not dropped.

**Competing designs to accept.** Operation logs per document rather than whole manifests, if conflicts are still kept. Locking a document to one device while open, with an explicit takeover, if offline edits are handled. Polling instead of push at low scale. Deduplication only within a user's own documents for privacy reasons, with the cost argued.

**Bottlenecks and failure modes.** Manifests committed before components; clock-based conflict resolution losing work; GC deleting components referenced by in-flight uploads; quota drift; hot documents with many devices; latency metrics that hide the slow path.

**Incident guidance.**
- *Manifest before components*: server-side verification on commit should make this impossible; add it, mark the affected versions incomplete, restore from the uploading devices where they still have the data or roll the document's current pointer back to the last complete version, and fix the client ordering.
- *Edits vanish by device clock*: replace clock-based resolution with parent-pointer conflict detection; recover the lost version from storage (it was committed, just not current) and show it to affected users as a conflict copy; find every document resolved by clock in the window.
- *Backfill includes version history*: revert the usage counters to the pre-backfill values or recompute under the correct rule, re-allow saves, tell affected users, and require a diff report (users crossing the quota) before any recomputation is applied.
- *Latency metric hides minutes*: extend the metric to the other device's acknowledgement and report offline catch-up separately; set a target for both and investigate the wake-up path (push not delivered, catch-up poll interval).

**Follow-up guidance.** Make the candidate walk through commit order step by step and say what makes the pointer update safe. Ask how GC knows nothing needs a component. Probe whether their latency metric includes devices that were asleep.

**Rubric anchors.** 2: upload whole files, last write wins by timestamp, quota from storage bytes, latency to server commit. 3: content-addressed components with resumable uploads, verified atomic commit with compare-and-set, conflicts kept as siblings, quota under the stated rule checked before upload, reachability GC. 4: also grace periods for in-flight uploads, catch-up for sleeping devices, latency measured end to end in two populations, quota recomputation with drift alerts, and crisp handling of every incident.

**Strong signals.** Separates immutable content from the mutable pointer; asks what "visible" means. **Red flags.** Merging layered images automatically; deleting data when a user goes over quota; measuring only the easy part of latency.

## ADB-L4-05

**Reference architecture (one defensible design; score others on the criteria).**
- **Layers**: raw hits (immutable, partitioned by customer and received date, kept for the history window); processed hits per customer under a rule-set version, with the bot-rule version and time-zone setting recorded per day; reports built from processed hits through a customer-scoped view that points at one processed version for the whole history.
- **Classifications**: versioned lookup tables per customer. An upload is validated first (key normalisation such as trimming and case, duplicate keys, the share of keys that match keys seen in hits, and a diff against the previous version), shown to the customer, and then activated. Reports join processed hits to the active classification version at query time; for heavy, frequently used reports the join is materialised into aggregates keyed by classification version and rebuilt in the background, with the query-time join serving until it is ready.
- **Reprocessing**: a request becomes a job (customer, date range, new rule-set version). It replays raw hits for the range into a new processed version beside the live one, pinning everything else per day: the bot-rule version in force on that day, the time-zone setting in force, the same visit logic. When every partition is built and checked, the customer's view switches to the new version for the whole range in one metadata change; the old version is kept for a period for rollback. Jobs run on separate or fairly scheduled capacity with per-customer limits so today's processing is never delayed; jobs for one customer are serialised (or a later request supersedes an earlier one covering the same range).
- **Checks before switching**: invariants per day and site: total hits, page views and visits that the changed rule cannot affect must equal the live version exactly; the changed dimension's distribution is reported as a diff the customer can see.
- **Visits**: rules that alter visit-defining fields are either disallowed for reprocessing or reprocess whole visits (and so whole days, with visit boundaries crossing midnight handled).
- **Downstream**: scheduled reports and the daily data feeds carry the processed version id; after a restatement the feeds for the range are re-delivered as a new version with a manifest, and the customer is told. A change log per customer records every upload, rule change and reprocessing with time, range, author and before/after totals.
- **Cost**: replay cost is proportional to the range and the customer's volume; large customers are planned (estimated duration and capacity reserved) against the deadline.

**Competing designs to accept.** Recomputing aggregates only (not hit-level processed data) when rules touch only dimensions present in aggregates. Applying processing rules at query time for some simple rules, with the cost argued. Lakehouse table versions (time travel) as the versioning mechanism.

**Bottlenecks and failure modes.** In-place rewrites that leave mixed months; replays that use today's settings for other rules; classification files with formatting problems; large customers starving others; delivered feeds silently diverging from reports; overlapping jobs.

**Incident guidance.**
- *Trailing spaces in 8% of codes*: upload validation (normalise keys, report unmatched share) would have caught it. Re-activate the previous classification version immediately (classifications are versioned), fix or normalise the file, re-upload, and show the customer the unmatched-key report.
- *Reprocessing late, mixed months*: the switch must be atomic over the whole range; until it is, reports read the old version. Revert the view to the old version, finish the build beside it, then switch; tell the customer which reports in the 30 hours mixed versions. Prevention: plan large jobs against the deadline, and never write in place.
- *Totals moved 0.5%*: the replay used today's bot rules. Rebuild with the per-day bot-rule version, and make the invariant check (untouched totals equal) a gate before any switch.
- *Warehouse disagrees with reports*: re-deliver the feed for the restated range with a new version id and manifest, and tell the customer's analysts which version their warehouse holds and how to replace it.

**Follow-up guidance.** Ask what happens to reports during a long reprocessing; strong answers build beside and switch atomically. Ask how they know nothing but the changed rule moved. Probe the cost of the classification join and when to materialise.

**Rubric anchors.** 2: rewrite partitions in place with the new rules; classifications updated by overwriting; no notice to customers. 3: immutable raw, versioned processed data built beside the live one, atomic switch, versioned classifications joined at query time, isolation of reprocessing. 4: also everything else pinned per day with an invariant gate, upload validation for classifications, re-delivery of feeds with versions, a customer-visible change log, capacity planning against the deadline, and crisp handling of every incident.

**Strong signals.** Asks what else must stay fixed while one rule changes; treats a restatement as a new version. **Red flags.** "Just rerun the pipeline"; changing history without telling the customer; one customer's backfill sharing a queue with everyone's current-day processing.
