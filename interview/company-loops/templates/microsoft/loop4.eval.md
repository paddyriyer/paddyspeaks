# Microsoft · Loop 4 — evaluator notes (hidden from candidates)

## MSF-L4-01

**Reference architecture (one defensible design; score others on the criteria).**
- **Control plane**: a versioned store of rollout policy per update: the stages (share of eligible devices per stage and the health gates between them), holds (attribute-matching rules with a reason, an owner, created and released times), organisations' ring policies (pilot and broad rings with deferral days, read from the management service) and eligibility rules. Every change is an append-only, audited version. A compiler turns the current version into a compact rule set (for example a decision table indexed by model, driver and firmware attributes) and publishes it with a version number.
- **Data plane (update check)**: stateless services in every region hold the compiled rule set in memory and refresh it on publish (push plus a short poll as a backstop). Evaluation order for one device: eligibility (edition, hardware requirements) → organisation ring and deferral (managed devices) → holds (any matching hold blocks, unless an administrator explicitly overrode it, which is recorded) → stage membership. Stage membership is `hash(device_id, update_id) mod 10,000 < stage_share`, so a device stays in the same stage across checks and each stage is a uniform sample of every cohort. The response carries the decision, the rule-set version and the reason, and the decision is logged (device id, rule version, inputs digest, outcome) so any day's decision can be reproduced.
- **Health pipeline**: install outcomes, rollbacks, boot failures and post-install crash rates stream in with device attributes. Per cohort and update, compute rates over a window measured in device exposure (devices that have had the update long enough to report), compared with the same cohort on the previous update. Late reports are expected: a cohort is judged only when its reporting completeness (devices expected to report vs reported) passes a bar. Small cohorts use a statistical test against the baseline (for example a one-sided binomial or Bayesian test with a minimum count of failures), not a fixed percentage. A second detector looks for an attribute shared by failing devices across cohorts (driver version, firmware, a security product), so holds can be scoped to the real cause.
- **Holds**: created automatically for strong signals (boot failures, data loss) and proposed for review for weaker ones. A hold is a rule over attributes, as specific as the evidence supports; release is a narrowing operation (for example "model X with driver < v2 stays held") rather than deletion, and it is tested against the population it would release before it is applied.
- **Stage widening**: automatic only when every gate holds for the {{decision_window}} window and the health pipeline's freshness watermark covers that window; if the signal is late or missing, the controller pauses (fails closed) and alerts.
- **Audit**: from the decision log and rule versions the system can answer "why was device D not offered on Tuesday" (for example "held by rule H-17, model and driver matched, since 09:12").

**Competing designs to accept.** Per-device precomputed decisions pushed to a key-value store (fast reads, but large rewrites on every rule change; acceptable if the candidate sizes it). A rollout driven by organisation rings alone for managed devices, with vendor stages for consumers only. Cohort keys built from fewer attributes plus a separate attribute-mining detector. Human approval for every hold if the candidate shows the 15-minute target is still met for severe signals.

**Bottlenecks and failure modes.** Cohort keys that miss the causal attribute; small-sample false holds; health data lag read as health; hold release that over-releases; rule propagation to caches; non-representative stages (a stage that by chance has none of a rare cohort); offline devices whose bad outcomes arrive days later.

**Incident guidance.**
- *New driver, holds keyed on model*: the cross-cohort attribute detector should have found the shared driver; create a hold on (driver version, update) across models immediately, offer affected installed devices a rollback or a driver fix, and contact the partner. Prevention: include driver versions in hold rules, watch for new driver releases during a rollout as a risk event, and run the attribute detector continuously.
- *Pipeline 10 hours behind, stage widened*: stop widening, and roll the stage back to the previous share (newly offered devices that have not installed simply stop being offered). The controller must check the health pipeline's watermark and completeness before every gate; a missing signal is "unknown", which blocks widening.
- *Release removes the whole model*: re-create the hold for devices still on the old driver; give releases a dry run that lists how many devices they release and their attributes; express releases as narrowing the rule, reviewed for the fixed attribute.
- *Thousands of false holds in stage one*: switch to a statistical test with a minimum failure count and a baseline comparison; aggregate thin cohorts upward (model family) until there is enough data; review the false holds and release the healthy ones in a batch.

**Follow-up guidance.** Ask for the evaluation order and the stage-assignment function; push on what "healthy" means with 300 devices; ask how long a new hold takes to reach every region's cache. Strong candidates bring up reproducibility of decisions without prompting.

**Rubric anchors.** 2: a percentage flag per update and a dashboard that someone watches; holds are manual lists of models. 3: control plane and cached data plane, stable hash-based stages, organisation rings respected, per-cohort health against a baseline with minimum samples, attribute-based holds. 4: also fail-closed gating on the health watermark, cross-cohort attribute detection, safe narrowing release with dry runs, reproducible decision logs, and crisp handling of every incident.

**Strong signals.** Asks what a cohort is before designing detection; treats late data as unknown. **Red flags.** Widening on a timer; fixed percentage thresholds for every cohort size; holds deleted rather than narrowed; no audit of individual decisions.

## MSF-L4-02

**Reference architecture (one defensible design; score others on the criteria).**
- **Connections**: clients hold a long-lived connection to a gateway in the nearest region. The gateway forwards client events (activity, idle, call start and end, sign-out) with a per-connection sequence number to the person's presence owner and renews the client's lease on each heartbeat. A lease expires after about two to three missed heartbeats ({{heartbeat}} seconds each), which bounds the time to Offline.
- **Presence owner**: each person is homed in one region and partition (by user id); one owner process holds their state in memory with a durable log or replicated store behind it: per-client state (lease expiry, activity, in call), calendar state (from calendar change notifications) and set status with an expiry time. Presence is a pure function recomputed on every input change: set status (Do not disturb, appear away) or a call on any client first, then a calendar meeting, then the most active client (any active client → Available; all idle → Away), no live client → Offline. The rule is versioned so it can be tested.
- **Timers**: lease expiries and status expiries ("until 17:00" converted to an instant using the person's time zone at the time it is set) are server-side timers in the owner, persisted, so they fire even when no client is connected.
- **Fan-out**: watchers subscribe when a view opens (a chat, a roster, a contact list), with a lease of their own. Only visible-state changes are published; changes are coalesced for a short window (a few hundred ms) and debounced for transient states (idle then active within seconds) before publishing. The owner publishes to a per-person channel; gateways subscribe on behalf of their connected watchers, so a change is sent once per gateway, not once per watcher, across regions. For very large audiences (a company-wide meeting) watchers poll a batched presence snapshot every few seconds instead of subscribing individually, or the roster shows presence only for visible rows.
- **Sizing**: with {{online}} people and a {{heartbeat}}-second heartbeat, heartbeats alone are millions per second at the upper levels; they renew leases in memory and are not written to a database. Visible changes are far fewer, and fan-out is changes × active watchers.
- **Privacy**: organisations' external-visibility policy is applied at read and fan-out time, per watcher's organisation, so a policy change takes effect without rewriting state.
- **Reconnect storms**: on gateway restart, clients reconnect with jitter; leases have a grace period so a reconnect within it does not change visible presence; deployments drain connections gradually.

**Competing designs to accept.** Presence replicated to every region (fast reads everywhere, more write traffic, eventual consistency) instead of home-region ownership. A distributed cache with per-client keys and expiry instead of an in-memory owner, if the candidate handles expiry events reliably and computes presence atomically. Client-side aggregation rejected or accepted with reasons (clients cannot see each other).

**Bottlenecks and failure modes.** Fan-out for large audiences; heartbeat write amplification; flapping between Away and Available; mobile background suspension; timers that only run on client events; cross-region subscriptions; hot partitions for heavily watched people.

**Incident guidance.**
- *Gateway restart storm*: deploy by draining, reconnect with jittered backoff, a lease grace period so a reconnect is invisible to watchers, and coalescing at the owner. Recovery: rate-limit fan-out per tenant and prioritise current state over transitions. Prevention: a deployment rule that restarts at most a small share of connections per minute.
- *Away while in a call on the phone*: the precedence rule must take "in a call" from the calling service (which knows the call is live) rather than from the phone client's activity, and it must outrank idleness on other clients. Add a test case for each signal combination.
- *Statuses not expiring*: move expiry to server-side timers set when the status is created; backfill by scanning statuses past their expiry. Prevention: a monitor on the age of expired-but-active statuses.
- *60,000-person meeting*: switch large rosters to batched snapshot polling or presence for visible rows only; isolate the tenant's fan-out from other partitions (separate queue, per-tenant limits). Prevention: an audience-size threshold that selects the mode automatically.

**Follow-up guidance.** Ask for the precedence rule written as a function; ask for fan-out arithmetic at peak; push on how an expiry fires without any client. Strong answers distinguish internal state changes from visible presence changes.

**Rubric anchors.** 2: every heartbeat written to a database, clients poll everyone's presence, last update wins. 3: leases with stated offline bound, explicit precedence, change suppression, subscriptions per active view, home-region design. 4: also server-side timers in the person's time zone, coalescing and debouncing, large-audience mode, cross-region fan-out per gateway, privacy policy at read time, and crisp handling of every incident.

**Strong signals.** Computes write and fan-out rates before choosing stores; treats presence as a derived function. **Red flags.** "Last write wins" across devices; ignoring mobile background behaviour; one message per watcher per heartbeat.

## MSF-L4-03

**Reference architecture (one defensible design; score others on the criteria).**
- **Ingestion**: content changes, permission changes and deletions from the storage service and membership changes from the directory are consumed as ordered change streams per tenant (resumable from a checkpoint). Content changes produce chunks and embeddings; permission changes update only access data.
- **Index layout**: a logical index per tenant (physically, small tenants share shards with a tenant filter that is always applied; large tenants get their own shards). Each passage stores: document id, tenant id, text, embedding, keyword terms, and an access list of principals as granted (user ids, group ids, a site's permission scope id, link ids), not expanded members. Inherited permissions are represented by a reference to the scope (site or folder) whose access list lives in one place; a document that breaks inheritance has its own scope.
- **Query**: resolve the user's effective principals: their user id, all groups they belong to transitively (from a membership cache refreshed by the directory stream), and links they have redeemed. Search with the principal set as a filter inside the search (keyword and vector), so the top results are already permitted. If the filtered vector search returns too few results (selective filters reduce approximate-search recall), fall back to an exact search over the user's permitted subset, or to keyword search. Then verify the final few documents against the storage service's batch permission check before passages reach the model; drop any that fail and log the disagreement as an index-lag signal.
- **Permission change propagation**: a group membership change updates the membership cache only (one record), so removal takes effect within seconds. A scope's access list change updates one record; passages referencing the scope pick it up at query time. Only a document breaking or restoring inheritance requires rewriting its passages. Lag is measured as event time to applied time per stream, alerted against {{apply_within}}.
- **Deletion**: a deletion event tombstones the document id immediately (queries filter tombstoned ids), then removes passages, embeddings, keyword postings, any secondary or recent-changes index, and cache entries; a periodic reconciliation compares the index with the storage service's list of live documents.
- **Caching**: cache retrieval results only per user (or keyed by a hash of the effective principal set plus permission-data version), with short lifetimes; never share answers across users. Answers that cite documents are re-validated on read.
- **Audit**: each answer records the document ids used and the permission version checked, so a customer's security team can verify access after the fact.

**Competing designs to accept.** Flattening principals onto passages for small tenants (simpler filtering) with a separate path for large groups. Query-time permission checks against the storage service only (simpler correctness, more latency and recall loss), if the candidate retrieves enough candidates. Separate indexes per site. Any design is acceptable if removal and deletion meet {{apply_within}} and recall survives trimming.

**Bottlenecks and failure modes.** Rewriting millions of passages on a group change; recall collapse from post-filtering; caches keyed without permissions; deletion missing secondary copies; deeply nested groups expanding slowly; sharing links misread as organisation-wide access.

**Incident guidance.**
- *Six hours to apply a group removal*: immediately, revoke at query time by refreshing the membership cache and adding a verification check of final documents against the storage service; then migrate the index from flattened members to unexpanded principals. Notify the customer with the window and the answers given (from audit records). Prevention: a propagation-lag monitor per stream against the target.
- *Empty answer from trimming*: filter inside the search, or retrieve more candidates and run a second pass restricted to the user's permitted documents; measure recall on test queries with selective filters.
- *Shared answer cache*: disable sharing at once, purge the cache, identify affected users from logs and inform the customer. Key caches by user or effective permissions; add a test that two users with different access never share a cache entry.
- *Deleted document in a secondary index*: deletion must enumerate every store; tombstone filtering at query time covers stores that lag; reconciliation against the storage service's live list finds what was missed.

**Follow-up guidance.** Ask the candidate to count updates for a group change in their design; ask where every copy of a document's content lives; push on recall under selective filters. Strong answers include a final check against the source of truth and measure lag.

**Rubric anchors.** 2: one shared vector index, post-filter the top k, permissions copied as member lists and refreshed nightly. 3: per-tenant isolation, unexpanded principals with query-time expansion, filtering inside the search, change streams for permissions and deletions, per-user caches. 4: also recall-preserving fallback, a final source-of-truth verification, complete deletion with tombstones and reconciliation, lag monitoring against {{apply_within}}, audit evidence, and crisp handling of every incident.

**Strong signals.** Asks how permissions are inherited and how big groups are before designing; counts the cost of a group change. **Red flags.** Trusting the model to ignore restricted content; caching answers by question text; deletion that only removes the main index.

## MSF-L4-04

**Reference architecture (one defensible design; score others on the criteria).**
- **Event contract**: each event has an event id (device id + device sequence number), player, title, achievement id or progress (achievement id + current total), device timestamp and a signature from the device runtime. Games declare achievements (ids, points, unlock condition type, progress target) in a versioned title configuration; events for unknown ids are rejected.
- **Ingestion**: devices send events directly or from their offline queue in sequence order; the service verifies signatures and the title configuration, deduplicates by event id over the device's sequence range (a per-device high-water mark plus a short set for gaps), and appends accepted events to a durable log partitioned by player.
- **Source of truth**: an unlock ledger keyed by (player, title, achievement) with a conditional insert: the first accepted unlock wins; a later unlock for the same key is ignored, except that an earlier plausible earned time may replace a later one (earned time is min over plausible device timestamps, bounded below by the title's release date and the player's first launch). Progress is stored per (player, title, achievement) and merged with max; reaching the target creates the unlock.
- **Projections**: total points per player = sum over the ledger (updated idempotently by applying each ledger insert once, with the ledger sequence as the idempotency key); the friends feed as fan-out on read or on write from ledger inserts; rarity per achievement = unlocks / players who launched the title, recomputed incrementally with sharded counters (N sub-counters per hot achievement, summed periodically) or by periodic batch aggregation, since an hour of lag is allowed.
- **Tamper defence**: plausibility rules per title (minimum time between related unlocks, impossible orders, unlock rates per device and account), signature failures, devices seen across many accounts. Suspicious unlocks are held as pending, not shown in rarity; confirmed fraud revokes the ledger entries with a reason, and projections recompute from the ledger.
- **Rebuild**: every projection can be rebuilt from the ledger and the event log for one title.

**Competing designs to accept.** Event sourcing with projections rebuilt from the log versus a transactional store updating ledger and totals in one transaction per player. Rarity from a nightly batch instead of streaming counters, since lag is allowed. Latest device timestamp versus earliest plausible, if the choice is explained.

**Bottlenecks and failure modes.** Hot counters for launch-day achievements; double-counted points from replays; device clocks; offline queues that arrive out of order; modified clients; progress regressions after reinstall; feed fan-out for players with many friends.

**Incident guidance.**
- *Launch-day hot counter*: decouple rarity from the unlock path (unlock confirmation must not wait for the counter); switch to sharded counters or batch aggregation; the confirmations backlog clears once rarity updates are asynchronous.
- *Points added twice for already-unlocked achievements*: totals must be applied only when the ledger's conditional insert succeeds; recompute totals for affected players from the ledger and fix the projection's idempotency key.
- *Modified client unlocks everything*: hold the accounts' unlocks as pending by rule (all achievements in a second is implausible), exclude pending unlocks from rarity, revoke confirmed ones and recompute rarity; block the device ids and tighten the per-title plausibility rules.
- *Progress reset to zero*: progress merges with max, so a zero report must never lower stored progress; if the bug lowered it, restore from the event log; ask the publisher to fix the game and add a monitor on progress decreases per title.

**Follow-up guidance.** Ask for the ledger key and the conditional write; push on which timestamp is kept; ask how revocation reaches every projection. Strong candidates treat projections as rebuildable.

**Rubric anchors.** 2: counters incremented per event, no idempotency, device timestamps trusted. 3: unlock ledger with conditional inserts, deduplication by device sequence, monotonic progress, projections derived from the ledger, a hot-key plan for rarity. 4: also signed events with plausibility rules and pending state, revocation that recomputes projections, earned-time plausibility, full rebuild path, and crisp handling of every incident.

**Strong signals.** Separates the source of truth from derived views; asks how progress is reported. **Red flags.** "Exactly once" claimed without saying between which points; trusting client data on PC without checks; rarity updated synchronously on the unlock path.

## MSF-L4-05

**Reference architecture (one defensible design; score others on the criteria).**
- **Ingestion**: reports and heartbeats land in raw storage partitioned by arrival date and build; reports carry device id (pseudonymous), build, model, driver set, faulting module and version, exception code and raw stack addresses; each report also says whether it is a first-of-day report or a sampled later one.
- **Symbolisation**: a retried stage that maps addresses to module and function names using the build's symbols; reports that cannot be symbolised wait in a queue (with the raw data kept) and are re-processed when symbols arrive, then re-bucketed. "Unknown" is a temporary state with a monitor, not a bucket.
- **Bucketing**: a key from the failure type, the faulting module name (not version), exception code and the top few symbolised frames (function names, normalised: no offsets or addresses, inlined frames handled). Buckets have stable ids in a bucket table with first seen build, last seen build, owner and merge or split history; a merge maps old ids to a new one so history follows the bug.
- **Metrics**: per build × day × component × model: crashing devices (devices with ≥ 1 report for that bucket or component; first-of-day reports are always sent, so this is not affected by sampling) and estimated crashes (first reports + sampled later reports × the inverse of {{upload_rate}}). Denominator: device-days on that build from heartbeats (or usage hours). The alerted metric is crashing devices per thousand device-days, which a single crash-looping device cannot distort.
- **Completeness**: a build-day's rate is published only when heartbeats for that day reach a completeness watermark (for example 90% of devices expected from the previous days' patterns); before that, the dashboard shows the figure as provisional.
- **Regression detection**: compare the new build with the previous preview build on the same devices where possible (devices that ran both), or re-weight by model and driver mix; require minimum exposure (device-days) and a statistical test (for example a Poisson rate ratio with a confidence interval) per bucket and component; alert on new buckets that exceed a minimum count and on existing buckets whose rate rises. Compare with the released build to judge release readiness.
- **Interaction discovery**: per bucket, a lift analysis over device attributes (model, driver versions, firmware) finds over-represented combinations.
- **Routing and retention**: owner by faulting module from the ownership list, with a fallback triage queue; raw stacks for 30 days, bucket-level aggregates for years.

**Competing designs to accept.** Crashes per usage hour instead of per device-day. Fixed holdout groups of preview devices for comparison. A streaming pipeline for early signals plus a batch pipeline for the official metric. Bayesian rate models instead of frequentist tests.

**Bottlenecks and failure modes.** Missing symbols; offset-based keys; non-representative early populations; numerator arriving before the denominator; crash loops; sampling misapplied to counts; ownership gaps.

**Incident guidance.**
- *Symbol store down*: do not bucket unsymbolised reports as new bugs; queue them and re-symbolise when the store recovers, then re-bucket; mark that build-day's metrics provisional. Prevention: alert on the unsymbolised share per build and replicate the symbol store.
- *Offset in the key*: remove offsets and versions from the key; re-bucket the affected reports and merge the 300 new buckets into their existing ones; add a test that recompiling a module leaves bucket keys unchanged.
- *New hardware skews the first day*: compare the same devices across builds or re-weight by model; show the per-model breakdown in the alert so owners see that the driver, not the build, is the cause.
- *Morning spikes from late heartbeats*: publish rates only behind a completeness watermark, show provisional figures as such, and suppress alerts until exposure and completeness pass their minimums.

**Follow-up guidance.** Make the candidate write the rate definition; ask what the bucket key contains; push on statistical confidence at low exposure. Strong candidates distinguish crashing devices from crash counts without prompting.

**Rubric anchors.** 2: total crashes per build divided by installs, buckets by stack hash, alerts on fixed thresholds. 3: exposure denominators, crashing-devices metric, symbolised and stable bucket keys, minimum exposure with a statistical comparison, ownership routing. 4: also sampling estimation, completeness watermarks, like-for-like comparisons or re-weighting, re-symbolisation and bucket merges, attribute interaction discovery, and crisp handling of every incident.

**Strong signals.** Asks how the denominator is measured; worries about who updates first. **Red flags.** Comparing raw crash counts between builds with different populations; buckets keyed on raw addresses; alerts that fire every morning.
