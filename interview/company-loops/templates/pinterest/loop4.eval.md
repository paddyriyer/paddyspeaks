# Pinterest · Loop 4 — evaluator notes (hidden from candidates)

These notes describe general, published engineering techniques (versioned client
rules, idempotent event keys, catalogue diffs, rank keys for ordered lists,
distinct counting with thresholds, censored durations). Score the candidate on
whether they apply them correctly, never on whether they guess how any company
builds its feeds, search, ranking or storage. Ranking is always a scoring function
the candidate is given; a candidate who spends the session designing a ranking
model is off topic, so steer back to the data system. Nothing in these designs
infers a sensitive or protected attribute about a pinner, and pinner data reaches
other people only in aggregates.

## PIN-L4-01

**Reference architecture (one defensible design; score others on the criteria).**
- **Grid and slot ids**: the server issues a `grid_view_id` with each feed, search, related or board response and records the pins it returned in which slots (a served log). The client tracks each tile with `(grid_view_id, slot_id, pin_id)`; slot ids are stable for the life of the grid, independent of on-screen position, so a reflow or rotation does not create a new identity.
- **Client rule (versioned)**: the rendering layer computes, per tile, the fraction of the tile inside the visible viewport (not the laid-out area) and a dwell timer; when it holds ≥ {{visible_pct}}% for ≥ {{dwell_ms}} ms, it emits one impression with `impression_id` (a UUID or `hash(grid_view_id, slot_id, visit_no)`), `rule_version`, `client_version`, client timestamp and a monotonic sequence number. The client also applies the {{revisit_minutes}}-minute rule locally per grid view (cheap and it saves bandwidth), and the server re-applies it authoritatively.
- **Batching and upload**: impressions are written to a small on-disk queue (not only memory), flushed every few seconds or on backgrounding, retried with backoff, and capped in size; the server returns per-batch acknowledgements. No network call per impression.
- **Ingestion**: an HTTP collector stamps `server_received_at` and writes to a durable log partitioned by `grid_view_id` (so one grid's events meet in one place). A stream job deduplicates by `impression_id`, joins to the served log to validate (the pin was actually served in that grid; unknown grid ids or impossible sequences are invalid), applies the scroll-back rule by `(grid_view_id, pin_id)` within {{revisit_minutes}} minutes, and drops invalid traffic.
- **Time and late data**: estimate each device's clock offset per batch (`server_received_at − client send time`, using the batch header) and correct event times; events whose corrected time is implausible use receive time. A day's creator aggregates are updated as late events arrive; the billing day closes at +48 hours, and later events are recorded as adjustments to a later invoice rather than edits to the closed day.
- **Aggregates**: per (pin, surface, day) impressions, with closeups and saves alongside, for creator analytics (fast path, hours behind); a separate billing pipeline over the same deduplicated events, with reconciliation counts (events received, deduped, invalid, billed) per day and per client version. Reports show counts only.
- **Consistency across clients**: scripted scroll sessions run on each client in CI against a fake server (golden counts); in production, monitor impressions per closeup, per save and per served pin by client and version; new client versions roll out with a canary and a gate on those ratios.
- **Scale**: {{daily_impressions}} a day is hundreds of thousands to millions of events a second at peak; at ~100 bytes compressed per event, tens of TB per day of raw events, which the billing audit period multiplies; per-pin daily rows are far smaller (one row per pin shown that day).

**Competing designs to accept.** Server-side deduplication only (client sends every visibility episode) if they account for bandwidth. Using the served log as the denominator and client events as confirmations. A lambda-style split or a single streaming pipeline with a closed batch recompute for billing. Exact dedup by key in a state store versus a daily batch dedup for billing.

**Bottlenecks and failure modes.** Rule drift between clients; pre-rendering counted as visible; in-memory buffers lost on background kill; clock skew moving events between days; position-based keys double counting after reflows; retries duplicating batches; a closed billing day that keeps changing.

**Incident guidance.**
- *+35% on one app after pre-rendering*: correlate by client version; ratios of impressions to closeups and saves broke. Hotfix the client to measure the visible viewport; exclude or correct the affected version's impressions in billing with a recorded adjustment (served log plus corrected rule), and annotate creator analytics. Prevention: golden scroll tests and canary gates on ratios.
- *−12% from background kills*: the version's events are lost, not late. Ship a persistent queue and flush on backgrounding; be honest that lost impressions cannot be recovered for billing (under-billing is the advertiser-friendly error), and note the gap for creators. Prevention: per-version volume monitors relative to sessions.
- *Rotation double counts within {{revisit_minutes}} minutes*: the dedup key used position. Re-key on `(grid_view_id, pin_id)` with stable slot ids, recompute affected days from raw events before billing closes, and adjust closed days. Prevention: keys reviewed as part of the rule version; a test that rotates mid-scroll.
- *Clocks a day ahead*: day assignment must not trust the device; correct with the batch offset and fall back to receive time; move misplaced events into the right day (or into an adjustment if that day is closed). Prevention: monitor the share of events whose corrected time differs from receive time by more than an hour.

**Follow-up guidance.** Make them trace the scroll-back case precisely and say where each rule runs; push on the billing close and adjustments; ask for the numbers.

**Rubric anchors.** 2: "log an impression when the pin renders", one pipeline, client timestamps trusted, no dedup key. 3: client visibility rule with grid and slot ids, idempotent batching, server dedup and validation against the served log, late-data policy, separate creator and billing aggregates. 4: also versioned rules with cross-client golden tests and canary gates, clock-offset correction, closed-day adjustments, invalid-traffic filtering, volume and cost estimates, and crisp handling of every incident.

**Strong signals.** Asks what "seen" means before designing; distinguishes laid-out from visible; joins impressions to what the server actually served. **Red flags.** Counting renders; per-impression network calls; editing closed billing days; reports that list who saw a pin.

## PIN-L4-02

**Reference architecture (one defensible design; score others on the criteria).**
- **Catalogue ingestion**: each upload is parsed and validated (schema, currency, price ranges, image fetchability), then diffed against the merchant's last accepted catalogue by product id: added, removed, changed (price, availability, title, image). Guard rails quarantine suspicious uploads: more than a set share of products flipping to out of stock or removed, or mass id churn (many removals matched by many additions with the same titles and images). A quarantined upload alerts the merchant and keeps the last good catalogue, within the freshness constraint (if no good upload arrives within {{refresh_hours}} hours, prices are hidden rather than shown stale).
- **Offers store**: current price, currency and availability per (merchant, product), keyed for fast lookup, updated from accepted diffs, with `as_of` = upload time. The products panel resolves price and stock here at serving time, so price and stock freshness do not depend on re-matching. Removals propagate from the diff to the offers store within minutes, which meets the one-hour rule.
- **Embedding index**: product image embeddings per (product, image hash, model version); only added or changed images are embedded. An approximate nearest-neighbour index per category (or partitioned by category) supports incremental inserts and deletes, with periodic compaction. Each index is tagged with the embedding model version.
- **Detections and links**: pins are processed in priority order (by recent impressions); the given detector produces boxes and categories once per image (cached by image hash and detector version). For each detection, query vectors are compared against the same-version index; the given scoring function orders candidates. A link row stores `(pin_id, detection_id, candidate product ids, scores, detector_version, embedding_version, index_snapshot, created_at)`; merchant-tagged exact links are stored separately with higher trust.
- **Refresh**: when products are removed or go out of stock, affected links are found through an inverted index (product → links) and their candidate lists refilled from the index, lazily on read for long-tail pins and eagerly for popular pins. New products are matched into popular pins' detections by a periodic job, bounded by budget.
- **Model migration**: build the new-version index in full alongside the old (dual index), re-embed products and pins' detections, switch query and index together per category behind a flag after offline and online checks (outbound clicks per panel open, coverage), then retire the old index.
- **Click measurement**: outbound clicks go through a redirect that records `(click_id, pin_id, detection_id, product_id, merchant_id, link versions, served_at)`; dedup by click id, filter invalid traffic (rate limits per network and device, known bots, impossible sequences), aggregate per merchant, product, link version and day; promoted product pin billing reads the same filtered events, so merchant reports and bills agree. Merchants see aggregates only.
- **Evaluation of matching**: holdouts or interleaving between matching versions, measuring outbound clicks and saves per panel open; credit a version only for clicks on links it produced.

**Competing designs to accept.** On-demand matching at tap time with a fast vector index if they show the 300 ms budget holds and cache results. A single global index instead of per-category ones. Batch-only refresh if they still meet the one-hour removal rule through serving-time checks against the offers store.

**Bottlenecks and failure modes.** Full rebuilds that cannot keep up with uploads; mismatched embedding versions between query and index; trusting a broken upload; product id churn orphaning links; stale caches showing old prices; bot clicks inflating merchant reports and bills.

**Incident guidance.**
- *Whole catalogue marked out of stock*: should have been quarantined as a mass change. Restore the last good catalogue's availability, notify the merchant, and add the mass-change guard. If already applied, the offers store can be rolled back from the previous accepted version. Prevention: thresholds on per-upload change rates, with merchant confirmation for large changes.
- *Query-side model rolled ahead of the index*: comparing vectors from different spaces; roll the query side back immediately, then migrate with a dual index switched per category together. Prevention: version tags checked at query time (refuse cross-version comparisons) and an online guard on outbound clicks per panel open.
- *Product id change*: detect id churn by matching removed and added products on stable attributes (GTIN where present, image hash, title, link); map old ids to new ids and re-point links; contact the merchant. Prevention: id-churn detection in the diff and a quarantine.
- *Tenfold clicks from a few networks*: invalid traffic; filter it from merchant reports and bills (credit if already billed) and keep the raw record for audit. Prevention: real-time invalid-traffic rules and anomaly alerts per merchant.

**Follow-up guidance.** Push on the rate-of-change separation, how a removal reaches every link within the hour, and the dual-index migration; ask for the daily re-match cost at {{merchants}} merchants and {{refresh_hours}}-hour refreshes.

**Rubric anchors.** 2: rebuild everything nightly, prices stored inside links, no versioning, clicks counted raw. 3: validated catalogue diffs, an offers store resolved at serving time, incremental index updates, versioned links, deduplicated and filtered click measurement. 4: also quarantine for suspicious uploads, a safe embedding migration, product-to-link inverted index for targeted refresh, honest matching evaluation, merchant reports consistent with billing, and crisp handling of every incident.

**Strong signals.** Asks how often each piece changes before choosing stores; treats the merchant's upload as untrusted input. **Red flags.** Showing stale prices to avoid empty panels; comparing vectors from different model versions; reports that expose pinners.

## PIN-L4-03

**Reference architecture (one defensible design; score others on the criteria).**
- **Model**: `pin(pin_id, creator_id, original_pin_id, media, created_at)`, `board(board_id, owner_id, visibility, is_group, created_at)`, `section(section_id, board_id, rank)`, `board_member(board_id, pinner_id, role, added_at, removed_at)`, `save(save_id, board_id, section_id, pin_id, saver_id, rank_key, saved_at, deleted_at)`, `follow(follower_id, target_type, target_id, followed_at)`.
- **Source of truth and derived copies**: saves are stored partitioned by `board_id` (board pages are the dominant read and a board's pins live together); a derived index by `(saver_id, pin_id)` answers "already saved by me", and one by `pin_id` feeds public save counts. Derived copies are built from the save store's change stream (CDC or an outbox), which also carries `visibility` with every event. The saver's own board view reads the primary, so their write is visible at once.
- **Ordering**: each save has a `rank_key` (lexicographic, fractional indexing); newest-first boards assign keys that sort before the current first; a drag writes one new key between its neighbours. Keys grow when pins are repeatedly inserted between the same neighbours; a background job rebalances a board's keys (rewriting them evenly) when the longest key passes a length limit, with a board version so concurrent readers page consistently. Concurrent drags: last writer wins per pin, with a board version returned to clients so they refresh; a new save never conflicts with a reorder because it only takes a new key.
- **Counters**: public save count per pin and follower count per board or profile are aggregated from the derived streams in short windows (sharded counters or a stream aggregation with periodic flush), so a viral pin is one batched update a second, not thousands of row increments. Only events whose visibility is public contribute; a visibility change emits compensating events (subtract the board's saves from public counts when it turns secret, add them back when public).
- **Public surfaces from a public-only projection**: board pages for non-owners, profiles, search and related pins consume a projection containing only saves on public boards. When a board turns secret, one visibility event drives: removal from the projection, purge of cached board and profile pages (CDN purge by surrogate key such as `board:<id>`), deletion from the search and related-pins candidate stores, and compensating counter updates, all within {{visibility_minutes}} minutes, with a tracker that confirms each consumer has applied the change.
- **Permissions**: group board membership read from an authoritative store with short-lived caches invalidated by membership events; writes check membership at the server.
- **Scale**: {{saves}} saves at ~100 bytes is tens of TB before replicas and indexes; {{peak_saves}} saves a second are spread across board partitions; the hot spots are counters and viral pins, not boards.
- **Leak check**: a continuous job samples public surfaces (search results, cached board pages, related candidates) and checks every pin-board pair against current visibility, alerting on any secret pair.

**Competing designs to accept.** Partitioning by owner with boards co-located (good for profiles, worse for group boards); integer positions with gaps instead of string ranks if they handle renumbering; strongly consistent counters for small boards and aggregated ones only for hot items. Filtering visibility at read time in addition to a projection, as defence in depth.

**Bottlenecks and failure modes.** Hot counters on viral pins and popular boards; cache copies that outlive a visibility change; long rank keys; stale permission caches; consumers that miss a visibility event; counters that go down and up visibly.

**Incident guidance.**
- *Secret board still public after 40 minutes*: caches and the search index were not tied to the visibility event. Purge by surrogate key now, force a reindex of the board's pins, and confirm with the leak check. Prevention: one visibility event fanned out to every consumer with acknowledgements and a deadline alarm at {{visibility_minutes}} minutes.
- *Viral pin at 8,000 saves a second*: per-save increments on one row; stop synchronous counter writes, move to windowed aggregation or sharded counters, and drain retries with backoff. Prevention: counters off the save path by design.
- *Rank keys of hundreds of characters*: rebalance affected boards in the background with board versioning; add a key-length trigger. Prevention: rebalancing as routine, not as a repair.
- *Removed collaborator saving for 30 minutes*: the app's permission cache refreshed only at login. Enforce membership at the server on every write, invalidate caches on membership events, and audit saves made in the window (remove them if the owner wishes). Prevention: authorisation never decided by a client cache.

**Follow-up guidance.** Have them list every public surface for the secret-board question; push on the hot counter with numbers; make them write the rank keys for a drag between two pins.

**Rubric anchors.** 2: one table, `ORDER BY position` with renumbering, counts by `COUNT(*)`, visibility checked only on the board page. 3: board-partitioned saves with derived indexes, rank keys, aggregated counters excluding secret saves, visibility propagated through change events to public surfaces. 4: also rank-key rebalancing with a concurrency rule, compensating counter events, cache purge by surrogate key with acknowledgement tracking, server-side permission checks, a continuous leak check, numbers, and crisp handling of every incident.

**Strong signals.** Enumerates the public surfaces before designing; treats visibility as data in the stream. **Red flags.** Filtering secret saves only in the UI; counters updated synchronously per save; renumbering a whole board on every drag.

## PIN-L4-04

**Reference architecture (one defensible design; score others on the criteria).**
- **Inputs**: search events (normalised term: case-folded, punctuation and whitespace normalised, light stemming or a lemma, spelling variants mapped through a maintained dictionary; terms matching the exclusion lists dropped here) and save events mapped to topics through the given taxonomy. Region from coarse location at event time. Raw query text exists only inside the aggregation job and in a short-retention raw store.
- **Weekly aggregation**: per (term or topic, region, week), distinct pinners. Exact distinct counts (a set of pseudonymous pinner ids per cell within the job) for cells near the threshold; mergeable sketches (HyperLogLog) for large cells and for rollups across regions or weeks, which merge without double counting. Retain weekly cells (counts plus sketches for the allowed rollups) for {{years}} years; raw events for a short period only.
- **Thresholds and differencing**: a cell is shown only if distinct pinners ≥ {{min_pinners}}, decided on the exact count near the boundary. Users choose from fixed region and topic groupings; when a parent is shown and some children are suppressed, suppress enough siblings (or the complement) that no suppressed cell can be derived by subtraction. One threshold service is used by every consumer, so no other dashboard shows unsuppressed cells.
- **Normalised interest**: the interest index is distinct searching (or saving) pinners per million active pinners in that region and week, then scaled 0–100 over the displayed period, stated in the tool. Dividing by active pinners removes growth of the user base; per-series scaling makes small and large regions comparable in shape.
- **Week alignment**: weeks are Monday-start ISO weeks in each region's local time; year over year compares each week with the week exactly 364 days earlier, which keeps weekdays aligned and gives week 53 a defined comparison (whatever that earlier week's number is); the rule is stated in the tool. Known moving holidays are labelled on the chart, and the rising list uses a 364-day comparison plus a multi-week baseline.
- **Rising terms**: growth of the smoothed index this week versus the baseline (for example the last eight weeks and the same weeks last year), with a minimum volume floor well above the threshold and shrinkage of small counts (for example a lower confidence bound on the ratio), so 3 → 30 does not top the list.
- **Invalid traffic**: before aggregation, drop automated clients and cap contributions per pinner per term per week (one pinner counts once anyway); anomaly checks on searches per pinner per term flag farms.
- **Serving**: precompute the weekly cells and the common rollups into a columnar store or OLAP cube; queries over fixed groupings answer in well under 2 seconds. The rising list is computed once per week.
- **Scale**: {{terms}} terms × {{regions}} regions × 52 × {{years}} cells is the theoretical upper bound; most cells are empty or suppressed, so storage is dominated by the non-empty cells (store sparse).

**Competing designs to accept.** Differential privacy noise instead of (or in addition to) thresholds, if they explain the accuracy cost for small regions. Topic-only reporting with no free terms. Calendar-month reporting if they argue it for planning users, with the same alignment care.

**Bottlenecks and failure modes.** Counting events instead of pinners; differencing across overlapping groupings; week misalignment; taxonomy changes breaking series; raw query text leaking into downstream tables; inconsistent suppression across tools.

**Incident guidance.**
- *Everything +15% in January*: week 1 compared with a week covering different holidays and days. Switch to a 364-day comparison or explicit alignment, recompute the affected weeks, and annotate the chart. Prevention: a calendar table with ISO weeks, 53-week years and holiday flags used by every comparison, with a test for the year boundary.
- *Bot-driven rising term*: counts were of searches. Recompute with distinct pinners and invalid-traffic filtering, pull the term from the rising list, and explain the correction to users. Prevention: per-pinner caps, anomaly checks on searches per pinner, and the rising list built only from distinct-pinner cells.
- *Flickering cells and an unsuppressed second dashboard*: flicker near the threshold is expected; consider smoothing over several weeks or showing a "not enough data" marker instead of a gap. The second dashboard is a privacy incident: take it down, move it onto the shared threshold service, and review who accessed it. Prevention: one suppression service; no direct access to unsuppressed cells.
- *Taxonomy split*: series for new topics start from zero. Re-map history: re-classify the historical saves (if raw data still exists) or apportion the old topic's history by the post-split mix with a clear "estimated" label; keep the old topic's series available for comparison. Prevention: taxonomy versions with explicit mappings applied to history.

**Follow-up guidance.** Make them show a concrete differencing attack and its fix; push on the meaning of the number shown and on week 53.

**Rubric anchors.** 2: counts of searches per term and week, a threshold per cell, year over year by calendar week number. 3: distinct pinners, thresholds with fixed groupings, a normalised index with a stated meaning, a week rule that handles 53-week years, invalid-traffic filtering, a precomputed serving layer. 4: also complement suppression with one shared suppression service, exact counts near the threshold with sketches elsewhere, a robust rising measure with baselines and floors, taxonomy versioning with history mapping, raw text confinement, numbers, and crisp handling of every incident.

**Strong signals.** Asks what the number means to a planner before designing; raises differencing unprompted. **Red flags.** Breakdowns by inferred personal attributes; raw query text in long-lived tables; ranking terms by percent growth from tiny bases.

## PIN-L4-05

**Reference architecture (one defensible design; score others on the criteria).**
- **Events**: each stage emits `(pin_id, stage, attempt, status: started|finished|failed|queued_for_review, service_ts, emitted_seq)` asynchronously to a durable log; the upload service emits `created` with the server's receive time. The collector adds `ingest_ts`. Events carry no media.
- **Lifecycle table**: one row per pin, folded from events by a stream job: first `created`, first successful `finished` per stage (idempotent: a replayed or duplicate event cannot move a timestamp backwards or forwards once set, except by an explicit retry attempt), current stage, deletion time, segments (media type, size, creator size band, region, client). Eligibility is "all required stages finished"; first impression comes from the serving log as a separate field.
- **One timeline**: stage durations computed within the same clock where possible (each service reports `queued_at` and `finished_at` from its own clock, so the work time is clock-consistent), and cross-service waits from ordered ingest times; services' clock offsets estimated from paired events and alarmed; negative durations are counted and surfaced as a data-quality metric, never silently clipped.
- **Reporting**: hourly cohorts by upload hour: share eligible within {{target_minutes}} minutes, survival curves (Kaplan–Meier style, with unfinished pins censored at the current time and deleted pins censored at deletion), percentiles once a cohort is complete, and the stage breakdown (queue wait versus work time per stage). Segment by media type, creator size, region and review status; alert on any segment breaching target, not just the total.
- **Separate eligibility from distribution**: "time to eligibility" is the pipeline's goal; "time from eligibility to first impression" depends on demand and the given scoring function and is reported separately so pipeline work is not judged by it.
- **Pipeline changes**: from the queue-versus-work breakdown: per-creator fair queuing (a creator's bulk upload is processed in parallel but cannot take more than a share of a queue), priority lanes, autoscaling on queue age (not queue length), smaller batches in feature extraction so a pin is not held for a whole batch, and review staffing or automatic triage measured against the review segment. Prove impact with before-and-after survival curves per segment.
- **Creator view**: a creator sees their own pins' status (processing, in review, live) without stage internals.

**Competing designs to accept.** Distributed tracing with a trace per pin instead of a custom event stream (accept if they handle replays and long waits beyond typical trace retention). A batch hourly fold instead of streaming. Reporting medians plus "share stuck beyond N hours" instead of survival curves, if stuck pins are clearly counted.

**Bottlenecks and failure modes.** Clock skew between services; batch-stamped timestamps; replays double counting; survivorship bias in medians; a single creator's burst starving others; overall percentiles hiding segments.

**Incident guidance.**
- *Video p95 at four hours, overall near target*: the segment alert should fire; the transcoding queue is dominated by one creator's batch. Apply per-creator fair queuing, scale transcoding on queue age, and process the batch in parallel at a capped share. Prevention: per-segment alerting and fairness by design.
- *Negative durations after a deploy*: the service stamps batches, not pins. Roll back or fix to stamp each pin's finish; recompute affected rows from ingest times; keep the negative-duration metric as an alarm. Prevention: contract tests on stage events (finish after start for the same service).
- *Weekend review backlog and an improving median*: the median excludes unfinished pins. Switch the headline to share within target with censored pins counted; staff or triage the review queue. Prevention: survival-based reporting and an alert on queue age for review.
- *Indexing replay, pins eligible twice*: the fold must ignore a second `finished` for the same (pin, stage, attempt) and must not overwrite a first eligibility time; repair affected rows from the event log. Prevention: idempotent fold keyed by pin, stage and attempt, with tests that replay a day of events.

**Follow-up guidance.** Make them define the denominator (including deleted and stuck pins); push on queue time versus work time; ask how they would prove a change helped.

**Rubric anchors.** 2: one dashboard of median upload-to-impression for finished pins; timestamps from each service trusted. 3: stage events folded into an idempotent lifecycle table, eligibility separated from first impression, per-segment percentiles, stuck pins counted. 4: also a clock-consistent timeline with skew detection, censored-duration reporting, queue-versus-work breakdown driving fair queuing and autoscaling on queue age, before-and-after proof, and crisp handling of every incident.

**Strong signals.** Separates what the pipeline controls from what the scoring function decides; worries about pins that never finish. **Red flags.** Skipping policy checks to meet the target; medians over finished pins only; double counting replays.
