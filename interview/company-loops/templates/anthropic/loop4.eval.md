# Anthropic · Loop 4 — evaluator notes (hidden from candidates)

## ANT-L4-01

**Reference architecture (one defensible design; score others on the criteria).**
- **Edge summariser at the gateway.** The handler that owns the client connection runs a small per-stream state machine and, using the host's monotonic clock, records: request received; `message_start` flushed; first `content_block_delta` flushed (first content, split by block type: text, thinking, tool input); each content event's flush time folded into running statistics (count, bytes, maximum gap, number of gaps above the stall threshold, total stalled time; pings excluded from progress); how the stream ended (`message_stop`, `error` event with its type, server close, client close) and which side closed first; stop reason and output tokens from `message_delta`; model, region, organisation, workspace, API key id, request id, SDK user agent. On close it emits one compact summary record. Per-event timelines are kept only for a small sample (plus every stream that stalled or ended abnormally) for 7 days.
- **Server-side record.** The inference server emits its own summary keyed by request id: queue wait, prefill time, first token produced, tokens generated, server-side completion or error. Comparing "first token produced" with "first content flushed" isolates the gateway and network-buffering segment.
- **Join and aggregation.** Both streams of records go to a regional log keyed by request id. A stream job joins them with a bounded wait (for example a few minutes; streams can run long, so the gateway summary is emitted at close and the join waits for the later of the two), and emits a joined record; unmatched records after the bound are emitted alone and counted. Durations are computed within one host's monotonic clock (gateway durations from gateway timestamps, server durations from server timestamps), never by subtracting timestamps from different hosts. Aggregates per (model, region, organisation, minute) carry counts by end type, stall counts and mergeable latency sketches (time to first content, maximum gap) so regions and minutes merge without averaging percentiles.
- **Serving.** A real-time OLAP store for on-call (per model and region, {{freshness}} freshness) and an organisation-scoped view for enterprise admins with row-level security on organisation id; per-key and per-workspace breakdowns only inside the organisation. Summaries kept 90 days in columnar storage; sampled per-event detail 7 days.
- **Privacy.** The schema has no content fields; the summariser counts bytes and events but never copies payloads. A contract test fails the build on any new field not on the allow-list.
- **Client side (optional).** An SDK can report sampled client-side timings (time to first rendered token, client-observed stalls) keyed by request id. These are opt-in, sampled, treated as untrusted (clamped, outlier-filtered) and used to validate the gateway's view, not to replace it.

**Competing designs to accept.** Shipping every event to a stream processor and sessionising by request id with a gap window, if the candidate costs it (events per day = streams × deltas per stream) and handles the window end; doing the join in batch with a separate real-time path for on-call; eBPF or proxy-level socket timing instead of handler instrumentation. Any design that measures at the client-facing hop and defines stalls precisely is acceptable.

**Bottlenecks and failure modes.** Event volume if every delta is shipped; clock skew when durations cross hosts; long streams that outlive a session window; buffering between the generator and the socket hiding stalls or delays; overload errors mid-stream that client retries amplify; high-cardinality labels (per key) on the operational metrics path; mistaking client disconnects for server failures.

**Incident guidance.**
- *Idle timeout below the ping interval*: the gateway sees server-side close by the load balancer, or the client sees a reset with no error event; end-type counts show a rise in "closed without `message_stop` and without error" concentrated on long pre-first-delta waits. Recovery: restore the timeout above the ping interval with margin. Prevention: an alert on abnormal-end rate by end type, and a synthetic long-wait stream probe that runs through the real path.
- *Overload errors mid-stream*: per-region error-event rate after first content, and request-id retry chains (same organisation, similar input size, seconds apart). Recovery: shed earlier (reject before streaming starts, where an overloaded response is cheap to retry), return retry-after guidance, ensure SDK retries use backoff with jitter. Prevention: alert on error-after-content rate; capacity headroom per region.
- *64 KB flush buffer*: "first content flushed" minus "first token produced" jumps while server metrics are flat; short answers are worst affected. Roll back; add the flush-delay segment as a first-class metric with an alert, and a canary that compares flush timing before and after gateway deploys.
- *Clock drift*: negative cross-host durations are the symptom. Fix the design so durations use one host's monotonic clock; alert on host clock offset; quarantine records from drifting hosts rather than publishing false stalls.

**Follow-up guidance.** Push on the exact definition of a stall (gap between consecutive content events, pings excluded, threshold {{stall_threshold}}, measured at flush), on how a stream that outlives any window is finalised, and on how the candidate separates the client's departure from a server fault (who closed first, error event present or not, bytes the client acknowledged if available).

**Rubric anchors.** 2: reuses server-side TTFT and average latency, ships every event without costing it, no end-type classification. 3: gateway-side per-stream summaries, precise stall and end definitions, join by request id with bounded lateness, sketches for percentiles, no content in telemetry. 4: also single-clock durations, sampled per-event detail for abnormal streams, organisation-scoped views, optional client timings handled as untrusted, and crisp handling of every incident.

**Strong signals.** Asks which hop the customer actually sees; separates "first event" from "first content"; brings up retries amplifying overload. **Red flags.** Logging delta text for debugging; computing durations across hosts' wall clocks; averaging per-region p95 values.

## ANT-L4-02

**Reference architecture (one defensible design; score others on the criteria).**
- **Price catalogue.** Rows of (model, token class, batch flag, price per million tokens in fixed-point minor units with stated precision, effective_from, effective_to, version). Changes are reviewed, validated by invariants (cache-read price below ordinary input below cache-write; batch price below interactive) and loaded ahead of their effective time. Each priced record stores the catalogue version it used.
- **Usage records.** On completion, the serving layer emits one usage record per request id: organisation, workspace and key ids as of the request, model, batch flag, region, request time, the four token counts. Batch requests carry their completion time; per the stated policy they are attributed at completion.
- **Exact path (ledger).** A stream job prices each record with the catalogue version in force at the request's attribution time and upserts into a ledger keyed by request id (insert-if-absent), so redelivery cannot double-count. Daily cost per (organisation, workspace, key, model, day) is an aggregation of the ledger; late records (a region's backlog) land in their correct day, and published days are corrected by adjustment rows, never edited silently. The invoice is built from the same ledger, so reports reconcile by construction; rounding happens once, at a stated grain (for example per line item on the invoice), with sub-unit precision kept upstream.
- **Fast path (enforcement).** Each region keeps an in-memory counter per workspace fed by its own usage stream (priced with the same catalogue) and periodically synchronised from the ledger's authoritative month-to-date total. The global limit is split into regional allowances that rebalance every few seconds based on recent spend, so the request path only reads local state. Admission: if month-to-date spend plus the region's in-flight estimate is at or above the allowance, reject. For in-flight estimates, either reserve input cost plus a typical output estimate (not the maximum, which blocks too early) and release on completion, or accept a measured overshoot.
- **Overshoot bound.** Worst case ≈ (concurrent in-flight requests at the moment of crossing × maximum cost per request) + (spend rate × detection delay up to {{enforce_within}}). State it and shrink it with per-workspace concurrency caps near the limit, smaller rebalance intervals, and stricter reservations above 95%.
- **Failure policy.** If a region's counter store is unavailable: fail open for a bounded time with a conservative local cap derived from the last known headroom, and fail closed for workspaces already within a small margin of their limit. Alert, and record who absorbs any overshoot (policy decision with finance).
- **Admin view.** Daily cost per key and workspace from the ledger (with an "as of" time and a marker for days still receiving late usage); a reconciliation report that lists, per invoice line, the request ids behind it.

**Competing designs to accept.** A central strongly consistent counter in one region with regional caching, if the candidate keeps synchronous cross-region calls off the request path; pricing at the edge versus in the stream job; a token-bucket-style allowance per region. Any design that separates the exact ledger from the approximate counter and states the overshoot bound is acceptable.

**Bottlenecks and failure modes.** Double counting on redelivery; floating-point drift; price changes racing with lagging streams (price must follow request time, not processing time); key moves mis-attributed; counters drifting from the ledger after failover; hot workspaces concentrating counter updates; batch completions crossing month boundaries.

**Incident guidance.**
- *Swapped cache prices*: detect with catalogue invariants (should have blocked the load) and with a ledger check on effective price per token class. Recovery: correct the catalogue, reprice affected ledger records by catalogue version and time range, issue adjustment rows and customer credits where customers were overcharged, and decide with finance on undercharges. Prevention: invariant checks and a two-person review on price loads, plus a canary that compares priced totals before and after a catalogue change.
- *25-minute overspend*: per-region consumer lag and "counter freshness" (time since last update per workspace) should alert. Recovery: restart or rebalance the consumer, resync counters from the ledger. Prevention: alert on counter staleness beyond {{enforce_within}}; fail closed for workspaces near their limit when the counter is stale; decide and communicate whether the overspend is credited.
- *Batch crossing the month*: the stated policy (attributed at completion) explains it; the console should show batch cost by completion time and the batch id, and documentation should say so. If customers need it by creation month, offer a report view keyed by batch creation while keeping the invoice rule unchanged.
- *Key moves double-counted*: attribution must use the key's workspace as of each request, from a key-to-workspace history table (valid_from, valid_to), not a current-state join. Recompute the day, publish corrections, add a test with a mid-day move.

**Follow-up guidance.** Ask the candidate to compute the overshoot bound with numbers; probe on which clock (request time vs processing time) chooses the price; check whether they know that an approximate counter needs a source of truth to resync from.

**Rubric anchors.** 2: one counter used for both enforcement and invoices, float costs, no idempotency. 3: ledger keyed by request id, versioned prices, regional counters with a stated overshoot, attribution as of request time. 4: also regional allowance rebalancing, explicit fail-open/closed policy by headroom, reconciliation to invoice lines, correction model for late data, and clear handling of every incident including customer remediation.

**Strong signals.** Separates enforcement from billing correctness unprompted; prices by request time; asks how batch usage is attributed. **Red flags.** Synchronous cross-region calls per request; recomputing invoices from counters; silently editing published days.

## ANT-L4-03

**Reference architecture (one defensible design; score others on the criteria).**
- **Scoring.** Classifiers run asynchronously next to the request path (with only the most severe, low-latency checks inline if policy requires). Each emits a score record: request id, account ids (organisation, key or app user), category, classifier version, threshold version, score, flagged boolean, model version, time. Content is not in the score record. For flagged requests from organisations whose agreements allow it, the minimal flagged excerpt goes to an encrypted evidence store with a {{flag_retention}} expiry; for organisations whose agreements forbid storage, the content-retention rule is applied before anything is written (a check on the organisation flag at the writer, not a later cleanup).
- **Aggregation.** A stream job maintains per (account, category) windowed statistics (counts of scored and flagged requests over hours and days, rate, a sequential test or exponentially weighted rate against the category's base rate) so persistence is judged on rate and on enough evidence, not on raw count. A second job looks for cross-account spikes: per category, flag rate across all traffic per few minutes, plus grouping by shared features that are not content (new accounts, shared payment or signup attributes where policy allows, similar request shapes, the same flagged pattern id from a classifier).
- **Queue.** Cases are accounts or clusters, not single requests. Priority = severity of category × confidence (rate, evidence count, classifier precision at that threshold) × reach (traffic volume). The queue is capped to capacity: the top {{review_capacity}} per day are reviewed; the rest are aggregated, auto-expired or reviewed by sampling. A fixed small share of capacity reviews random samples of unflagged and just-below-threshold traffic to estimate recall and tune thresholds.
- **Reviewer evidence.** The minimal flagged turns with surrounding context, the account's aggregate history (counts, not content) and prior decisions. Escalation to more context requires a reason and is logged. Every access is logged with reviewer, case and reason; access reviews run periodically.
- **Feedback and classifier monitoring.** Review outcomes are labels keyed by classifier and threshold version, giving precision per category over time. Monitors: flag rate per classifier per model version, score distribution shift (compared with a frozen reference set scored by each new classifier version before deploy), and queue inflow vs capacity.
- **Retention.** Score records may be kept longer than content as metadata, per policy; evidence expires at {{flag_retention}} with a positive check that nothing older exists.

**Competing designs to accept.** Batch daily aggregation for persistence plus a separate streaming spike detector; a graph-based approach for coordinated activity; a rules engine on top of aggregates. Any design that normalises for volume, ranks by severity and confidence under capacity and keeps content handling minimal is acceptable.

**Bottlenecks and failure modes.** Raw-count thresholds favouring large accounts; queues that grow without bound; classifier changes shifting flag rates; coordinated misuse below per-account thresholds; late scores after windows have closed; evidence written for organisations whose agreements forbid it; reviewer over-access.

**Incident guidance.**
- *Score-scale change floods the queue*: classifier version is on every flag, so the jump is attributable; roll back or pin the old threshold until recalibrated; purge or deprioritise the flood by classifier version. Prevention: score each new classifier version on a frozen reference set before deploy and require the flag rate at the configured threshold to stay within a band; threshold tied to classifier version.
- *Content stored against an agreement*: stop the writer, delete the excerpts from the evidence store and every copy (caches, backups or by key destruction), audit who accessed them, notify per policy and contract. Prevention: enforce the organisation's retention flag at the writer with a test, and a daily canary that scans the evidence store for organisations on the no-storage list.
- *Coordinated pattern below per-account thresholds*: add cross-account detection on shared features and on category-level rate; review the cluster as one case. Backfill: rerun the detector over the two days of score records.
- *Late scores*: windows must handle late data (event-time windows with allowed lateness, or recompute affected windows when late data lands) and decisions taken on incomplete windows should be flagged for re-check. Alert on scoring lag.

**Follow-up guidance.** Look for normalisation (rates and evidence counts, not totals), a capacity-aware queue, and a credible recall estimate from sampling unflagged traffic. Probe privacy: what exactly is stored for unflagged traffic (ideally nothing beyond scores, per policy), and who can see excerpts.

**Rubric anchors.** 2: fixed count thresholds and a FIFO queue, stores all content "for later". 3: async scoring, versioned classifiers and thresholds, normalised aggregates, prioritised queue within capacity, minimal logged access, retention enforced. 4: also cross-account detection, recall estimation by sampling, classifier pre-deploy calibration checks, retention rules enforced at write time, and precise handling of every incident.

**Strong signals.** Treats reviewer time as the scarce resource; records classifier and threshold versions on every flag; distinguishes behaviour change from classifier change. **Red flags.** Fully automatic enforcement; storing all content; evaluating classifiers only on flagged cases.

## ANT-L4-04

**Reference architecture (one defensible design; score others on the criteria).**
- **Per-request telemetry from the serving layer.** Organisation, workspace, key, model, region, time, request id; billed token counts by class (ordinary input, cache write, cache read) exactly as billed; for each breakpoint: position (token offset), cumulative salted prefix hash, outcome (read, written, below minimum, miss) and, for misses, a reason when known (no entry, expired recently, evicted). The salted hash is computed per block cumulatively (hash of the previous block's hash plus this block), salted with a per-organisation secret, so two prompts that diverge at block k share hashes up to k − 1 and differ after.
- **Miss attribution.** A stream job keeps per-organisation state keyed by breakpoint hash: last seen time, last outcome. For a miss: if the same hash was seen within the lifetime window and still missed, the cause is eviction or capacity; if it was seen but longer ago than the lifetime, "expired"; if the prefix hash is new but the previous block hashes match a recently seen prefix, "prefix changed after block k" (with the divergence position, which points customers at timestamps or reordered tools); if the prefix length is under the minimum, "below minimum"; otherwise "first use". Labels carry a confidence and an "unknown" bucket. State is regional; for organisations served in several regions, merge attribution in a second stage or accept regional scope and say so.
- **Money.** Per request: counterfactual cost = all input tokens at ordinary price; actual cost = priced token classes; savings = difference (may be negative). Wasted write spend = write tokens whose prefix hash is never read within its lifetime (finalised after the lifetime passes). Aggregate per (organisation, workspace, key, model, hour) in an OLAP store; billed token totals are reconciled with the billing ledger daily, and late usage triggers re-aggregation of the affected hours.
- **Console.** Organisation-scoped: hit rate, savings, wasted writes, miss reasons, top prefix ids by waste with the divergence block position, and an estimate of savings from a fix (for example, simulating a stable prefix by treating "prefix changed after block k" misses as reads of the first k blocks).
- **Capacity.** The same per-prefix state gives working-set size over time (distinct live prefixes × size), and the distribution of inter-arrival times per prefix tells capacity how many more prefixes a longer lifetime would keep alive.
- **Privacy.** Per-organisation salts held in a key management system, never exported; hashes are opaque ids in the console; cross-organisation comparison is impossible without salts; analysts query aggregates, and access to the salt service is restricted and audited.

**Competing designs to accept.** Attributing miss reasons inside the serving layer (it already knows the cache state) rather than downstream, if the candidate keeps what is needed; batch hourly computation instead of streaming, given the {{freshness}} target; sampling per-breakpoint detail while keeping token totals exact.

**Bottlenecks and failure modes.** High-cardinality per-prefix state; cross-region prefixes; late usage breaking exactness; salt rotation resetting identities; mislabelled reasons when the expired-prefix memory is short; hit rate misleading when write costs dominate.

**Incident guidance.**
- *Framework inserts the time*: divergence at block 0 or 1 across many organisations with the same SDK user agent; publish guidance, contact the framework maintainers, and surface "prefix changed at the first block" prominently in the console. Prevention: an alert on organisation-wide falls in cache-read share, grouped by user agent.
- *Shortened expired-prefix memory*: the reason mix shifts overnight from "expired" to "never written" with no change in traffic; roll back, relabel affected hours as "unknown" rather than wrong, and add a deploy check on the reason distribution.
- *2% below invoice*: late-arriving usage needs re-aggregation; fix the pipeline to recompute hours when late data lands and mark hours provisional until the lateness bound passes; add a daily reconciliation against billing with an alert threshold.
- *Salt rotation*: keep the old salt during an overlap and publish a mapping from old to new opaque ids inside each organisation (computed in the restricted service), or rotate only on schedule with notice; explain in the console.

**Follow-up guidance.** Push on why hit rate alone misleads (a write costs more than ordinary input), on cumulative hashing to find divergence without content, and on which numbers must be exact (token totals) versus estimates (savings from a hypothetical fix).

**Rubric anchors.** 2: hit rate per key from billed tokens only, no reasons, raw prompt hashes unsalted. 3: per-breakpoint salted hashes, counterfactual savings, reasons for misses, exact token totals reconciled with billing. 4: also divergence position via cumulative hashes, unread-write waste, cross-region state handled, salt rotation planned, capacity working-set estimates, and crisp handling of every incident.

**Strong signals.** Notices that savings can be negative; asks whether the server can distinguish expiry from first use. **Red flags.** Storing prompt prefixes to debug; one global unsalted hash; sampled totals shown as billing.

## ANT-L4-05

**Reference architecture (one defensible design; score others on the criteria).**
- **Scope and sampling.** A policy filter selects in-scope conversations (excluding enterprise and API traffic, and conversations whose users' settings exclude this use) and drops any conversation already deleted. Stratified sampling by language and, if available, product surface, with known inclusion probabilities, so estimates for small languages have usable precision; weights correct the strata in reporting; confidence intervals shown on shares.
- **Restricted extraction.** A model runs inside a restricted environment with no human access to inputs. Instructions ask for facets that omit identifying details (no names, contact details, locations below country, rare specifics). Outputs are short, structured, versioned by extractor prompt and model. Stage is idempotent: keyed by (conversation id, extractor version), so retries never re-extract.
- **Clustering.** Embed facet summaries, cluster (for example k-means at several granularities or hierarchical), then a model writes a short description of each cluster from a sample of its facets, again instructed to omit identifying details.
- **Privacy layers.** (1) Extraction instructions; (2) distinct-account threshold of {{min_accounts}} per cluster, computed after every allowed filter, on the exact population shown; (3) a final model-based or rules-based privacy check on every description, blocking any that name individuals or small organisations; (4) a fixed set of approved filter dimensions with coarse buckets, no free-form filters, and a policy that overlapping queries are served from a fixed weekly release, which limits differencing. Optionally add noise to published counts (differential privacy) if the candidate can explain the budget across releases and the effect on small clusters.
- **Storage and retention.** Raw conversations never leave the restricted environment; facets and embeddings expire at {{retention_days}} days with a positive check that none older exist anywhere (including copies registered in a catalogue; unregistered copies are blocked by access controls); published aggregates keep only cluster descriptions, counts and shares. Deletions: a deleted conversation id is removed from any remaining facets and embeddings; aggregates that already passed the threshold are not recomputed (they hold no per-conversation data), though the next run naturally excludes it.
- **Evaluation.** Synthetic conversations with known topic distribution and planted identifiers measure (a) extraction leakage rate (identifiers in facets), (b) description leakage, (c) cluster accuracy. Acceptance bars are set before launch and checked on every extractor or model change.
- **Cost.** Model calls dominate: extraction per sampled conversation plus descriptions per cluster; the sample size is chosen against the weekly budget and precision targets; idempotent keys prevent re-spending.

**Competing designs to accept.** Rule-based topic classification instead of model-extracted facets (cheaper, less flexible); differential privacy instead of or alongside thresholds; monthly rather than weekly runs. Any design where every stage is a measured privacy layer and the threshold applies after filtering is acceptable.

**Bottlenecks and failure modes.** Extractor drift leaking identifiers; thresholds checked before filters; differencing between overlapping reports; cluster churn across weeks; uncontrolled copies; retries that re-spend budget; biased samples misrepresenting small languages; comparisons across releases confounded by product changes or mix shifts.

**Incident guidance.**
- *Extractor leaks names*: pull the report, delete the affected facets and descriptions, roll back the extractor prompt, and re-run with the old version. Prevention: the synthetic leakage test runs on every extractor change with a hard bar; the final description check blocks proper names of individuals and small organisations.
- *Sub-threshold cluster shown*: the filter was applied after the threshold; fix the order so the threshold is applied to the exact population displayed; remove the cluster; add a test that every displayed cell meets the threshold; review who saw it.
- *Spend doubles*: retries ignored the (conversation, extractor version) key; make the stage idempotent, cap per-run spend with a budget guard that halts the run, and alert on spend per sampled conversation.
- *Auditor asks for proof*: show the retention job's run records and the positive check (oldest facet age per store); the debugging copy shows a gap: delete it, find others by scanning for the facet schema, and block unregistered copies by access policy.

**Follow-up guidance.** Look for the threshold applied after filtering, for measured (not assumed) leakage rates, and for an honest account of what comparing two releases can and cannot show (mix shifts, seasonality, product launches, sampling error).

**Rubric anchors.** 2: run a model over conversations and show clusters, threshold on conversation counts, keep everything. 3: restricted extraction, distinct-account threshold after filters, retention and deletion of intermediates, privacy check on descriptions, sampling with uncertainty. 4: also synthetic evaluation with acceptance bars, differencing defences, idempotent budgeted stages, cluster tracking across weeks without identifiers, and precise handling of every incident.

**Strong signals.** Counts accounts, not conversations; tests privacy on synthetic data with planted identifiers. **Red flags.** "Analysts can spot-check raw conversations"; free-form filters; no plan for deletions.
