# Databricks · Loop 4 — evaluator notes (hidden from candidates)

## DBX-L4-01

**Reference architecture (one defensible design; score others on the criteria).**
- **Log layout**: commits are files named by zero-padded version (`…/_log/00000000000000051204.json`), each holding actions: `add` (path, partition values, size, row count, per-column min/max/null counts, a `dataChange` flag), `remove` (path, deletion time, `dataChange`), `metadata` (schema, partitioning, properties), `protocol` (minimum reader and writer versions or feature list) and `txn` (application id, batch version) plus commit info for audit. State at version N = replay of the latest checkpoint at or below N plus the commits after it.
- **Commit protocol (optimistic)**: a writer records the snapshot version v it read, writes all new data files (invisible until referenced), then tries to create log entry v+1 with an atomic create-if-absent. On a store with that primitive, the store is the arbiter. On a store without it, every writer of the table goes through the same commit coordinator (a small service or a table in a strongly consistent key-value store keyed by (table, version) with a conditional insert), then writes the log file; readers treat a version as committed once the coordinator says so and backfill the file if a writer crashed after the conditional insert. Mixing mechanisms on one table breaks mutual exclusion; the mechanism is part of the table's configuration.
- **Conflict detection on loss**: the loser reads commits v+1..w and checks them against its own read set and write set. A blind append conflicts only with metadata or protocol changes. A MERGE/UPDATE/DELETE conflicts if a winner removed any file it read or rewrote, or (for serialisable writes) added files whose rows could match its read predicate in the partitions it scanned. Compaction conflicts only if a winner removed one of the files it is compacting. With no logical conflict, the loser re-commits at w+1 with the same data files; with a conflict it aborts (and the job may re-run from scratch). Partition-scoped predicates and row-level change markers (deletion vectors) reduce false conflicts.
- **Checkpoints**: every {{checkpoint_every}} commits a writer (or a background service) writes the full state at that version as columnar files, possibly in several parts, then updates a `_last_checkpoint` pointer with the version and part count. Readers validate that all parts exist before using it and otherwise fall back to the previous checkpoint. Checkpoint health is monitored per table (versions since last checkpoint).
- **Snapshot construction**: read the pointer, read the checkpoint (columnar, so only needed columns), list commits after it, replay. Long-lived services cache snapshots and apply new commits incrementally. File statistics in `add` actions drive data skipping.
- **Idempotent streaming writes**: each streaming writer commits a `txn` action with (application id, batch version) in the same commit as its data. On restart it reads the latest batch version for its id from the snapshot and skips batches already committed.
- **Cleanup**: log entries older than the log retention are deleted only below a checkpoint, so state stays reconstructible from the oldest retained checkpoint. Data files are deleted only if they are not referenced by the current version and were removed more than {{retention_days}} days ago; a minimum retention check refuses shorter settings unless explicitly overridden, and long-running readers either finish within the retention or pin a version. Untracked files from failed writes older than the retention are also removed.
- **Compaction**: rewrites small files of a partition into target-size files and commits remove+add with `dataChange=false`, so change-stream readers skip it. Run per partition in small batches so each commit touches few files and conflicts cost little; schedule it in quieter windows for hot partitions, or give it priority by pausing the conflicting writer briefly. Writers can also produce better-sized files in the first place (optimised writes, auto-compaction after commit).

**Competing designs to accept.** A catalog-managed commit service for all tables (simpler cross-store semantics, a new dependency in the commit path). Row-level conflict detection instead of file-level. Checkpoints written by a dedicated maintenance service instead of by writers. Snapshot isolation for writers with an explicit statement of the anomalies it allows (write skew).

**Bottlenecks and failure modes.** Commit races on hot tables (each loss costs a re-read of winners); log replay length when checkpoints stop; listing cost on very long logs; large commits whose JSON is huge; compaction starvation; cleanup that outruns live readers; mixed commit mechanisms after a migration; clock-based retention decisions using the wrong clock.

**Incident guidance.**
- *Compaction loses five nights in a row; 900,000 small files*: compaction conflicts with the MERGE because both touch the same files. Run compaction per partition in small batches (each batch commits quickly), skip partitions the MERGE is rewriting right now, or briefly prioritise compaction for that table; enable writer-side file sizing so fewer small files are created. Monitor files per partition and compaction success per table.
- *Checkpoints silently failing for three days*: correctness held because checkpoints are an optimisation, but readers replay too much. Fix the permission, write a checkpoint immediately, and alert on "commits since last checkpoint" exceeding a multiple of {{checkpoint_every}}. Add the checkpoint path to the permission-change checklist.
- *Cleanup with one-hour retention*: files still referenced by a live query and by recent versions are gone. Stop the job; recover deleted objects from the store's versioning or soft-delete if enabled; tell the auditor which versions can no longer be reproduced (versions whose files were removed). Prevention: a hard minimum retention that requires an explicit override with a reason, and object-store versioning or soft delete on table paths.
- *Two writers claim version 51,204*: mutual exclusion broke, almost always because writers used different commit mechanisms after the migration (one assumed create-if-absent, the other used the coordinator, or one store did not honour the conditional write). The overwritten writer's data files exist but are unreferenced. Freeze writes, determine which commit file is the log's version, re-apply the lost writer's change as a new commit (its files can be re-added if no conflict), and enforce one commit mechanism per table recorded in the table's configuration; add a post-commit check that reads back the commit and compares its id.

**Follow-up guidance.** Make the candidate state what the loser rechecks; strong candidates distinguish logical conflicts from version races and keep data files on retry. Probe idempotent streaming (txn action in the same commit). Probe cleanup safety against live readers and time travel.

**Rubric anchors.** 2: a lock or central database for every write, no notion of replay or checkpoints, cleanup by age only. 3: optimistic commits with atomic create of the next version, read/write-set conflict detection with retry, checkpoints with a pointer, idempotent streaming commits, retention-bounded cleanup. 4: also a correct answer for stores without create-if-absent, partial-checkpoint safety, compaction that cannot starve, protection of live readers, and crisp handling of every incident.

**Strong signals.** Asks about the store's atomic primitives first; explains why blind appends rarely conflict. **Red flags.** Modifying data files in place; trusting directory listings of data files instead of the log; deleting files by age without checking references.

## DBX-L4-02

**Reference architecture (one defensible design; score others on the criteria).**
- **Per-cluster autoscaler**: driven by workload signals, not CPU: pending tasks and their expected durations per stage, task backlog trend, and executor slot utilisation. Scale up when the backlog would take longer than a target to drain at the current size (in steps, bounded by the customer's maximum and by the regional broker); scale down only after sustained idleness, with cooldowns and hysteresis to prevent oscillation.
- **Safe scale-down**: choose workers that hold no shuffle output and no cached blocks needed later (the engine tracks this), or decommission gracefully: stop scheduling on the worker, migrate its shuffle and cached blocks to remaining workers or to remote storage, then release it. Drivers run on on-demand by default; a customer may opt into spot drivers for short jobs.
- **Capacity broker (regional)**: receives node requests from all clusters, with tenant, priority (scheduled production job with a start-time target, interactive, backfill), instance-type flexibility and deadline. It allocates from spot across several instance types and zones, using observed reclaim rates and prices, and falls back to on-demand when spot is unavailable, when a job's deadline is at risk, or after a job has been reclaimed repeatedly. It respects per-account cloud quotas and launch-rate limits with a token bucket, jitter, and a global retry budget so failures do not turn into retry storms.
- **Fairness**: per-tenant shares of the region's quota and launch rate (weighted fair queuing), with headroom reserved for scheduled jobs whose start time is near; backfills are throttled to their share; a tenant's own limits cap how many nodes it can hold at once.
- **Reclaim handling**: on notice, the node stops accepting tasks, running tasks are marked for re-run elsewhere, and shuffle and cached blocks are migrated within the {{notice}} window (with 30 seconds little can move, so recompute must be cheap). Lost map outputs trigger re-running only the affected map tasks. For long shuffle-heavy jobs, the broker shifts toward on-demand or toward instance types with lower reclaim rates; jobs can checkpoint long lineages. A circuit breaker moves a cluster to on-demand if reclaims exceed a threshold.
- **Warm pools**: optional per-tenant or shared pools of pre-started nodes, sized from start-time demand curves; idle cost is charged to the pool owner, so pools pay for themselves in saved start minutes.
- **Reporting**: per job, node-hours by spot and on-demand, cost against an all-on-demand baseline, time lost to reclaims (recomputed task time), and start delay against target; feeds both customer reports and the broker's fallback rules.

**Competing designs to accept.** Fixed-size clusters plus a job queue (simpler, less elastic). Shuffle to a remote shuffle service so workers are stateless and reclaims lose little (more network, higher cost per byte, much better spot tolerance). Pools of pre-started nodes per tenant instead of a shared broker. Scaling on predicted demand from job history.

**Bottlenecks and failure modes.** Cloud launch-rate limits and quotas; correlated spot reclaims in one zone or instance type; shuffle loss and stage recompute cascades; oscillating autoscalers; top-of-hour start bursts; one tenant's backfill dominating shared quota; slow node start times.

**Incident guidance.**
- *40% of a zone's spot reclaimed in ten minutes*: diversify instance types and zones for spot; the broker should detect the reclaim spike and move long shuffle-heavy jobs to on-demand (cost-capped), and cap recompute (after N reclaims a job goes on-demand). Report to affected customers with the cost comparison; consider remote shuffle or checkpointing for jobs over a duration.
- *Launch rate limit at midnight*: retries amplified the limit. Add a global token bucket for launches, a retry budget with exponential backoff and jitter, priority for jobs with start-time targets, and spread starts (customers' "midnight" schedules can tolerate small jitter; warm pools absorb the peak).
- *Scale-down of workers holding shuffle files*: the autoscaler must consult shuffle and cache tracking before choosing workers to remove, use graceful decommissioning with block migration, and use a longer idle timeout for workers holding shuffle data. Add hysteresis and alert on scale-up/scale-down cycles per cluster.
- *6,000-job backfill takes the quota*: enforce per-tenant fair shares and caps on concurrent nodes for backfills; reserve headroom for scheduled jobs near their start; request higher quotas or alternative instance types for the region; tell the tenant how to schedule the backfill.

**Follow-up guidance.** Push on the scaling signal (CPU is a trap), on what is lost on reclaim and how much can move within the notice, and on fairness when demand exceeds quota.

**Rubric anchors.** 2: scale on CPU, all spot or all on-demand, no notion of shuffle loss. 3: workload-based scaling with cooldowns, shuffle-aware scale-down, a broker with spot diversification and on-demand fallback, rate limiting with jitter, per-tenant fairness. 4: also graceful decommissioning bounded by the notice window, recompute caps or remote shuffle for long jobs, deadline-aware fallback, cost reporting against a baseline, and crisp handling of every incident.

**Strong signals.** Separates per-cluster from regional decisions; quantifies what can move in {{notice}}. **Red flags.** Drivers on spot by default; retries with no budget against a rate-limited API; ignoring that removing workers can cost more than keeping them.

## DBX-L4-03

**Reference architecture (one defensible design; score others on the criteria).**
- **Capture**: an engine-side listener, after analysis and optimisation, walks the resolved plan of each executed statement and emits a lineage event: statement id, user, workspace, time, source (warehouse, notebook, job run, pipeline), inputs (stable table id, column ids), output (table id, column ids) and expression edges. It runs asynchronously, writes to a local buffer and a durable queue, and never fails or blocks the query; dropped events are counted.
- **Model**: nodes = tables and columns by stable id (names are time-versioned attributes), plus external nodes (dashboards, models, paths written directly). Edges = (source column → target column, kind ∈ {value, filter/join, opaque}, first_seen, last_seen, producing statement or job). Read-only queries create "read by" edges from columns to the reading entity (dashboard, user, job), for impact analysis. Table-level edges are derived from column edges.
- **Plan handling**: views are expanded in the resolved plan (record view → table edges too); `*` is resolved; MERGE emits value edges for each updated or inserted column from its source expressions, and filter/join edges from the ON and WHEN conditions; aggregations are value edges from the aggregated columns and filter/join edges from group keys used only for grouping (a choice; state it); streaming queries emit once per query definition and refresh last_seen per batch; opaque functions get edges from all their input columns to their output, marked opaque.
- **Storage and query**: an edge store partitioned by node id in both directions (upstream and downstream adjacency), with validity intervals, in a key-value or relational store; traversal service with depth and fan-out limits, pagination, and precomputed table-level and dashboard-level summaries for popular nodes; a lakehouse copy of all events for analytics and backfill.
- **Tags**: propagation rules by edge kind: personal-data tags propagate along value and opaque edges (conservative), not along filter/join edges; propagated tags are marked "inferred" with their path, and owners confirm or reject; rejections are remembered per edge so they do not reappear.
- **Visibility**: at query time, nodes the caller cannot access are shown as redacted placeholders (an opaque node with no name or schema), or the path is collapsed; edges never reveal names of inaccessible objects. Counts may still reveal that something exists; decide and document.
- **Freshness**: measured as the lag between statement end and edge visibility; surfaced in the UI and the API, so impact analysis says "lineage complete up to 10:42" rather than "no downstream readers".

**Competing designs to accept.** A graph database for the edge store, if the candidate bounds traversals and handles validity intervals. Parsing SQL text for external engines that do not expose plans, as a supplement. Table-level lineage first with column-level added for the most-used tables.

**Bottlenecks and failure modes.** High fan-out nodes; event spikes with ingestion lag; identity confusion on rename or recreate; opaque functions; external writers bypassing the engine; leaking names through lineage; tag over-propagation leading to tag fatigue.

**Incident guidance.**
- *Drop and recreate with the same name*: lineage keyed by name merged two different tables. Key by stable table id; the recreated table is a new node; reprocess the affected events with ids; show the old table as dropped with its history. Add a test for drop/recreate.
- *Email through a Python function, not tagged*: opaque edges must propagate personal-data tags conservatively from all inputs; re-run propagation over the affected period; mask the shared table and review who read it; owners confirm tags on opaque outputs.
- *Six-hour backlog, false "no downstream readers"*: scale ingestion (partitioned consumers by node id), but above all expose completeness: impact analysis shows the watermark of applied events and warns when it lags beyond {{freshness}}. Change workflows can require a fresh lineage check.
- *Finance table names visible*: enforce visibility at query time against current grants; redact placeholders; audit who viewed affected lineage; add tests for paths through inaccessible nodes.

**Follow-up guidance.** Probe the MERGE edge set and how opaque functions are represented. Ask how a high fan-out traversal stays fast, and what a user sees for a node they cannot access.

**Rubric anchors.** 2: parse SQL text, table-level only, name-keyed nodes, no permissions. 3: capture from resolved plans asynchronously, column edges with kinds, stable ids, bounded traversals, tag propagation and query-time visibility. 4: also validity intervals, opaque-edge handling with owner review, completeness watermarks in impact analysis, careful redaction semantics, and crisp handling of every incident.

**Strong signals.** Captures from the plan, not text; distinguishes value edges from filter edges. **Red flags.** Capture that can fail customer queries; lineage that reveals inaccessible table names; "no downstream" answered from stale lineage.

## DBX-L4-04

**Reference architecture (one defensible design; score others on the criteria).**
- **Model**: `job` (definition versioned: tasks, dependencies, conditions, retries, timeouts, cluster specs, schedule, max concurrent runs, catch-up policy), `run` (job_id, logical/scheduled time, trigger type, parameters, state), `task_run` (run_id, task_key, attempt, state, cluster, start, end, published values, error), with a unique key on (job_id, scheduled_time) for scheduled runs and on (run_id, task_key, attempt) for attempts.
- **Scheduler**: jobs are hashed into many shards; scheduler instances hold leases on shards (with fencing tokens, so a deposed instance's writes are rejected). For each due job, the instance inserts the run row with a conditional insert on (job_id, scheduled_time); only the winner proceeds. The next fire time is precomputed and indexed, so the top-of-hour scan reads only due jobs. On failover, the new leaseholder re-scans due times and conflicts on the unique key prevent duplicates.
- **State machine**: run and task transitions (pending → queued → running → succeeded/failed/timed_out/skipped/cancelled) are conditional updates in one durable store. A dispatcher moves ready tasks (all dependencies terminal and their conditions true) to a queue; workers acquire clusters through the cluster service with rate limits and launch tasks; heartbeats detect lost workers.
- **Retries and timeouts**: per-task retries with exponential backoff and jitter; a default timeout when none is set (and a warning to the customer); each attempt receives run_id, task_key and attempt number so tasks can write idempotently (for example overwrite the partition for the logical date, MERGE on a key, or commit with an idempotency id).
- **Repair runs**: a new repair attempt within the same run: the failed tasks and their downstream dependents are re-queued; successful tasks' outcomes and published values are reused from the original attempt; parameters, including the logical date, are the original run's. Because table data may have moved on, tasks should read by logical date (partitioned inputs) or by table version recorded at the original run; the orchestrator can record the input versions a task read and pass them on repair.
- **Shared clusters**: tasks on a shared cluster are isolated as far as the engine allows; a driver failure fails all attempts on it; the orchestrator recognises a cluster-level failure, restarts the cluster once, and re-runs the affected tasks without counting the first such failure against each task's own retry limit, but limits total cluster restarts. A task that repeatedly kills its cluster is moved to its own cluster on retry, or the run fails with a clear cause.
- **Outages and catch-up**: after a regional outage, missed runs are created according to each job's policy (all, latest only, skip) and released through a global rate limit and per-tenant fairness, oldest deadlines first.

**Competing designs to accept.** A single active scheduler with a hot standby and fencing (simpler; must show it handles the peak start rate). An existing open-source orchestrator extended for multi-tenancy, if the candidate addresses its scheduler limits. Event-driven triggers (file arrival, table update) alongside time schedules.

**Bottlenecks and failure modes.** Top-of-hour bursts; scheduler failover duplicates; cluster-service rate limits; shared-cluster blast radius; hung tasks; repair semantics on changed data; thundering herds after outages; the run-history store's growth.

**Incident guidance.**
- *Duplicate runs after failover*: the standby did not see the leader's inserts or there was no unique key. Add the (job_id, scheduled_time) uniqueness and fencing on leases; identify duplicate runs from history, cancel any still running, and tell affected customers which tables were loaded twice (and how to fix: re-run the logical date with overwrite semantics). Encourage idempotent task writes.
- *Repair reads Thursday's data for Tuesday*: the repair reused Tuesday's parameters but tasks read "latest". Record input table versions per task attempt and pass them (or the logical date) on repair; document the semantics; offer "repair as of original versions" where time travel retention allows.
- *Shared-cluster driver OOM, retries all fail*: classify the failure as cluster-level, identify the task that caused it (memory metrics per task), retry the others on a fresh cluster and isolate the offender on its own cluster; stagger retries; surface the cause to the customer.
- *14-hour hung task*: default timeouts, alerts on runs exceeding a multiple of their historical duration, and idle-cluster detection; refund or credit policy is a business decision, but the platform should make the cause clear.

**Follow-up guidance.** Make the candidate state the exactly-once guarantee for run creation and the at-least-once reality for task execution, and what that requires of tasks. Probe repair semantics on changed data.

**Rubric anchors.** 2: cron on one machine, retries that rerun everything, repair as "run the job again". 3: unique run identity with leases, durable state machine, retries with backoff and timeouts, repair as reuse of successful outcomes, idempotency guidance. 4: also sharded scheduling with fencing that handles the burst, cluster-level failure classification, input version capture for repair, catch-up policies with fairness, and crisp handling of every incident.

**Strong signals.** Identifies runs by (job, scheduled time); separates run creation (exactly once) from execution (at least once). **Red flags.** Relying on in-memory state in the scheduler; no default timeout; claiming exactly-once task execution.

## DBX-L4-05

**Reference architecture (one defensible design; score others on the criteria).**
- **Change capture**: a sync job reads the table's change feed from the last applied commit version (stored durably with the index), per micro-batch: inserts and update post-images become upserts; deletes and update pre-images whose key changed become deletes. Rows are keyed by primary key; within a batch only the latest change per key is applied (ordered by commit version).
- **Embedding**: a content hash of the embedded columns is stored per key; only rows whose hash changed are sent to the embedding endpoint (filter-column updates update metadata only). Requests are batched, rate-limited to the endpoint's capacity, retried with backoff, and costed (tokens per batch, per table). A backlog metric (rows waiting, oldest waiting commit time) drives freshness alerts and optional extra capacity.
- **Deletes**: applied on a fast path independent of the embedding queue: a tombstone set (or deletion bitmap) is updated immediately and every query excludes tombstoned keys, so a deleted row disappears from results within seconds even if index maintenance lags. Physical removal happens in compaction.
- **Index**: segment-based ANN index (for example HNSW per segment, or IVF with periodic re-clustering), with new upserts in a small mutable segment and periodic merges; the index records the source version it reflects (`synced_version`) and exposes freshness = now − commit time of the oldest unapplied change.
- **Model upgrades**: a new index is built side by side with the new model (full re-embedding at a controlled rate, then catch-up from the change feed from the version at which the build started), validated on relevance samples, then switched atomically; queries always embed with the model of the index they search; the old index is dropped after a rollback window.
- **Access control**: the row filter's predicate is evaluated per caller; search pre-filters on indexed filter columns where the filter can be expressed on them, or over-fetches and post-filters with a retry at larger k, never returning a row the caller could not read; results include source version for audit.
- **Monitoring**: recall@k against exact search on a sampled query set, latency, segment counts and tombstone ratio; maintenance merges segments and rebuilds when tombstones exceed a threshold.
- **Expired change feed**: if the needed version range has expired, fall back to a full comparison by key and content hash against the current table (re-embedding only changed rows), then resume incremental sync.

**Competing designs to accept.** Recomputing embeddings in the lakehouse as a column of the table (a materialised embedding table) and syncing vectors only, which makes re-embedding auditable. Filtering by partitioning the index per tenant or region when filters are coarse. Full nightly rebuilds for small tables, with the cost argued.

**Bottlenecks and failure modes.** Embedding throughput and cost; deletes stuck behind embeddings; mass rewrites that look like full changes; mixed vector spaces; recall decay; filtered search returning too few results; change feed retention gaps.

**Incident guidance.**
- *Throttled endpoint; deleted row returned for 30 hours*: deletes must not wait in the embedding queue. Apply tombstones from the change feed immediately; add an alert on delete latency separate from freshness; scale or buy endpoint capacity for the backlog; communicate the freshness breach.
- *Full overwrite triggers full re-embedding*: content hashes let the sync skip rows whose embedded columns are unchanged; also cap re-embedding spend per day with an approval step for spikes; tell the engineer which write modes produce row-level changes (MERGE or UPDATE) versus full rewrites.
- *Two models in one index*: never mix vector spaces. Roll back to the old model for queries, rebuild a new index side by side with the new model, and switch atomically; record the model version per vector and reject mixed indexes in validation.
- *Recall from 0.95 to 0.80*: tombstones and in-place updates degraded the graph. Merge segments and rebuild degraded ones off the serving path, then swap; schedule maintenance by tombstone ratio and measured recall; keep the recall monitor.

**Follow-up guidance.** Probe whether deletes are independent of embeddings, how a model upgrade avoids mixing spaces, and how filtering interacts with top-k.

**Rubric anchors.** 2: nightly full rebuild, deletes ignored or delayed, no notion of versions. 3: incremental sync from the change feed with checkpoints and idempotent upserts, content hashing, fast-path deletes, side-by-side model upgrades, query-time access control. 4: also freshness and recall measurement, segment maintenance, protection against mass rewrites, a fallback when the change feed has expired, and crisp handling of every incident.

**Strong signals.** Records the source version the index reflects; treats deletes as a privacy path. **Red flags.** Mixing embeddings from two models; post-filtering without over-fetch; full re-embedding as the only recovery.
