# Databricks · Loop 3 — evaluator notes (hidden from candidates)

## DBX-L3-01

**Reference architecture (one defensible design; score others on the criteria).**
- **Bronze (`bronze.click_events_raw`).** Append-only. Columns: `ingest_id` (file path + row number, or a generated id), `source` (web, ios, android), `app_version`, `received_at` (server), `ingested_at`, `source_file`, `ingest_date` (partition), the parsed columns of the declared schema where they parse, `_rescued_data` (values whose type or name did not match, kept as JSON), and optionally the raw payload string for full fidelity. Nothing is validated away here. New fields are added additively (automatic column addition is acceptable in bronze because nothing reads bronze by column name except silver).
- **Schema evolution rules.** Additive fields: allowed into bronze automatically; into silver only through a reviewed mapping (a contract change). Type changes (`duration` as string): the value lands in rescued data, silver casts from either the typed column or the rescued value with an explicit rule, and the cast failure is a quarantine reason, not a null. Renames (`event_type` → `type`): a deliberate mapping per app version in a small reference table (`field_map(app_version, source_field, target_field, transform)`), never two silver columns. Semantic changes (`price` in minor units): a per-version transform in the same table, caught by distribution checks (median price jumps ×100 for one version).
- **Silver (`silver.click_events`).** Grain: one row per event. Key: (`device_id`, `client_event_id`) or a hash of it; when one app version reused ids, add `first_received_at` bucket or install id to the key for that version, stated as an exception. Columns typed, `event_ts_utc` (client time, normalised), `client_ts_raw`, `received_at`, `clock_skew_s` (received − client), `event_date` (from client time, but clamped or flagged when skew exceeds a threshold), `app_version`, `ingest_id` of the winning copy. Deduplication: MERGE into silver on the key with "insert when not matched" only (first copy wins, deterministically by earliest `received_at` then `ingest_id` within a batch), so a replay of bronze changes nothing. Window: the key lookup is bounded by `event_date` ± {{late_days}} days for pruning; events older than the window are routed to quarantine with reason `too_late` (or accepted via a slower path) rather than silently duplicated.
- **Quarantine (`silver.click_events_quarantine`).** Columns: `ingest_id`, `received_at`, `app_version`, `reason_code` (missing_event_time, unknown_event_type, bad_user_id, cast_failed:<field>, too_late, …), `rule_version`, the raw or rescued payload, `quarantined_at`, `status` (open, reprocessed, discarded), `reprocessed_at`. Owned by the pipeline's team; the quarantine rate per reason and per app version is a monitored metric with an alert well above the normal {{invalid_share}}. Re-entry: after a rule fix, a reprocess job reads open quarantine rows, applies the new rule, and inserts into silver through the same idempotent MERGE; rows are marked reprocessed.
- **Gold.** `gold.sessions` (one row per session: user or device, session_start, session_end, events, first page, converted) built from silver with a sessionisation rule; `gold.daily_funnel` (date × source × app_version × step: users, events); attribution inputs (one row per conversion with touchpoints). Each run computes the set of affected `event_date` partitions from silver rows added since the last run (via the table's change feed or an `ingested_at` watermark) and recomputes those partitions (replace partition, or MERGE by key) instead of appending.
- **Close.** A day of gold is provisional until {{late_days}} days have passed plus a margin, then marked final; later corrections go through a restatement.
- **Layout.** Bronze partitioned by `ingest_date`; silver by `event_date` with clustering (Z-order or liquid clustering, if they name it) on `user_id`/`device_id`; target file sizes in the hundreds of MB; compaction of small streaming files.

**Competing designs to accept.** Keeping only the raw payload string in bronze and parsing everything in silver (simpler evolution, more compute). Streaming silver with a stateful deduplication bounded by a watermark (acceptable if they explain what happens beyond the watermark). Gold built with MERGE by session key instead of partition replacement. A data-contract registry per app version instead of the `field_map` table. Quarantine as a column flag on a silver "all events" table, if analysts only read a filtered view.

**Bottlenecks and failure modes.** Dropping invalid events (no evidence, no re-entry); automatic schema evolution all the way to silver (duplicate or misspelt columns become permanent); casting failures turning into nulls instead of quarantine; deduplication on an unbounded window (expensive) or none (replays double count); gold built by appending each run's new rows (late and replayed data double count); partitioning silver by user id (millions of tiny files); event date from a skewed client clock with no flag.

**Incident guidance.**
- *Local time without offset*: detect from a jump in `clock_skew_s` for one app version (a whole-hour offset) and the midnight spike. Contain: route that version's events into quarantine with `bad_timezone` (or flag them) until a rule exists; fix with a per-version transform (use received time and the device's reported offset where available), reprocess the affected bronze range into silver by key (MERGE update of the time columns), and recompute gold partitions touched by both the old and new event dates, keeping that window open for {{late_days}} days. Guardrail: skew distribution check per app version.
- *Quarantine jumps to 12%*: nobody watched the rate. Contain: alert on quarantine rate per reason and version against the baseline ({{invalid_share}}); add the rename to the field map, reprocess the three days of quarantined events into silver, recompute the funnel for those days and annotate the dashboard. Guardrail: contract tests on new app versions (a sample payload must map to silver before release) and an owner rota for the quarantine.
- *Bronze replay double counts sessions*: silver was idempotent but gold was append-only. Recompute the affected week's gold partitions from silver; change gold to recompute affected partitions (or MERGE by session key) and add a reconciliation of gold event counts to silver per day.

**Follow-up guidance.** (1) First copy wins by earliest `received_at` (or by `ingest_id` tie-break); a replay finds every key present and inserts nothing. (2) Bronze: value in rescued data; silver: cast via rule or quarantine with `cast_failed:duration`; gold sessions for that version lose durations or drop sessions — the alert should fire on the quarantine rate, not on gold. (3) Each run touches event dates of the new silver rows (usually today plus up to {{late_days}} days back); final after the window. (4) Reprocess quarantine through the same MERGE; gold recomputes the affected dates; quarantine rows marked reprocessed so a second run does nothing. (5) Bronze by ingest date; silver by event date with clustering on user/device; compaction; a user lookup prunes by date and skips files by clustering statistics.

**Rubric anchors.** 2: three layers named but silver deduplication, schema evolution and quarantine are vague; invalid rows dropped. 3: bronze with provenance and rescued data, per-layer evolution rules, silver key and idempotent MERGE, a quarantine table with reasons and re-entry, gold recomputed for affected dates. 4: also version-aware field maps and semantic-change detection, clock-skew handling, quarantine rate as an owned and alerted metric, a close for gold, and a layout argued from volume ({{daily_events}} a day).

**Strong signals.** Asks what the deduplication key is before drawing tables; treats quarantine as a product with an owner. **Red flags.** "Filter out bad rows"; automatic schema evolution into silver and gold; appending to gold; partitioning by user id.

## DBX-L3-02

**Reference architecture (one defensible design).**
- **Table.** `dim_account (account_sk BIGINT, account_id STRING, tier, segment, region, parent_account_id, owner_name, owner_email, owner_phone, valid_from DATE/TIMESTAMP, valid_to (exclusive; '9999-12-31' for the current row), is_current BOOLEAN, attr_hash, is_inferred BOOLEAN, source_extract_id, loaded_at)`. Tracked (type 2): tier, segment, region, parent. Overwritten (type 1, on all versions or on the current one only, stated): owner name, email and phone. `attr_hash` = hash of the tracked attributes.
- **Staging.** From the day's extract: keep the latest row per (`account_id`, `effective_date`) by extract time, then a deterministic tie-break (row number in the file); drop rows whose `attr_hash` equals the version in force on their effective date (no real change), but still apply type 1 attributes.
- **Ordinary change (MERGE with staged rows).** Source = changed rows twice: (a) `merge_key = account_id` to match the current row and set `valid_to = effective_date, is_current = false`; (b) `merge_key = NULL` so it never matches and is inserted as the new current version. `WHEN MATCHED AND t.is_current AND t.attr_hash <> s.attr_hash THEN UPDATE …`; `WHEN NOT MATCHED THEN INSERT …`. New accounts appear only in (b).
- **Back-dated change.** Effective date `e` falls inside an existing version `[from, to)`: that version is split into `[from, e)` and a new version `[e, to)` carrying the corrected attributes; if the correction applies to everything after `e` ("moved to enterprise on the 3rd" and later versions also changed other attributes), later versions get the corrected attribute too (rewrite the affected versions' tracked attributes and hashes) — the candidate should say which semantics they choose. Implemented as a per-account rebuild: read all versions of the affected accounts, merge in the corrections, recompute intervals, and replace those accounts' rows in one MERGE (delete-and-insert by `account_id` for the affected set). Invariant check after each load: per account, intervals contiguous, non-overlapping, exactly one current row.
- **Early facts (inferred members).** When usage arrives for an unknown `account_id`, insert a version with `is_inferred = true`, attributes 'Unknown', `valid_from` = first usage time. When the CRM row arrives, update the inferred version in place (type 1 on an inferred row is accepted practice) or close it, and say which; usage keyed to it then shows the real attributes.
- **Fact join.** Two options with stated trade-off: (1) `fct_usage.account_sk` fixed at load (fast joins; a back-dated change requires re-keying facts in the affected interval — at {{usage_rows}} a day over {{backdate_days}} days that is a large rewrite, limited by partition); (2) facts carry `account_id` and the usage hour, and reports join `ON f.account_id = d.account_id AND f.usage_hour >= d.valid_from AND f.usage_hour < d.valid_to` (no re-keying; as-of joins are heavier but prunable). A hybrid: surrogate key at load for current reporting plus a periodic re-key job, or option 2 for finance.
- **As-was versus as-is.** Finance revenue by tier: as-was (the version in force at usage time), and closed months are frozen — either snapshot the monthly result or keep corrections out of closed months by recording `known_at` (bitemporal: valid time and transaction time). Sales dashboards: as-is (join to current row by business key).

**Competing designs to accept.** A bitemporal dimension (valid_from/valid_to plus recorded_from/recorded_to) — the strongest answer for closed months. Rebuilding the dimension for affected accounts every day from a full history of CRM changes (event-sourced dimension) instead of incremental MERGE logic. Snapshotting the dimension daily (simple, larger) with facts joining on date. Using a declarative pipeline's built-in SCD type 2 support, if they still explain out-of-order and back-dated behaviour and the duplicate-key issue.

**Bottlenecks and failure modes.** MERGE failing (or picking arbitrarily) on duplicate source rows; type 2 on every column so cosmetic changes create versions; overlapping intervals after out-of-order loads; two current rows after a retried load; back-dated changes applied to the current row; inferred members never completed; surrogate-key re-keying across years of facts; closed months silently restated.

**Incident guidance.**
- *Owner phone format bulk edit creates millions of versions*: the change detection hashed all columns. Contain: stop the load; collapse consecutive versions with identical tracked attributes (rebuild affected accounts' intervals); fix `attr_hash` to cover tracked attributes only and apply type 1 updates separately. Guardrail: alert when the day's new versions exceed a multiple of the normal {{daily_changes}} change rate.
- *Back-dated tier correction applied to the current row*: history was edited, so the tier at invoice time is lost from the dimension. Recover the prior state from the table's version history (time travel) or the extract archive; rebuild the account's versions with a proper split; for finance, keep the closed month as reported and record the correction as a restatement decision. Guardrail: the load never updates tracked attributes in place; corrections go through the back-date path.
- *Retried load creates two current rows*: the load was not idempotent. Deduplicate per account (keep the version from the latest extract, recompute intervals); make the load keyed on `source_extract_id` (skip extracts already applied) and run the one-current-row and no-overlap checks before publishing; recompute revenue by tier for the affected days.

**Follow-up guidance.** (1) Before: one current row; source: two rows per changed account (match and insert); after: closed row plus new current row. (2) Split the containing version at the effective date and propagate the corrected attribute to later versions if that is the agreed semantics; facts in the interval change attribution (re-key or as-of join). (3) Inferred member with 'Unknown' attributes; completed when the CRM row arrives. (4) Finance shows the closed month as reported with a note; sales shows today's view; a restatement view shows the delta. (5) Re-keying touches facts across {{backdate_days}} days × {{usage_rows}} a day; an as-of join by business key avoids rewrites at query cost — choose per consumer.

**Rubric anchors.** 2: type 2 described but a MERGE that only updates, no handling of duplicates or back-dated changes. 3: correct staged MERGE, change detection on tracked attributes, half-open intervals with invariants, inferred members, a clear fact-join choice. 4: also back-dated splits with propagation semantics, bitemporal or snapshot treatment of closed months, idempotent loads keyed on the extract, and cost reasoning at {{accounts}} accounts.

**Strong signals.** Writes the intervals before and after a back-dated change; separates valid time from load time. **Red flags.** Updating the current row for a correction; `BETWEEN valid_from AND valid_to` with inclusive ends on both sides; no deduplication of the extract.

## DBX-L3-03

**Reference architecture (one defensible design).**
- **Layout.** Catalogs by environment × domain or business unit (`prod_claims`, `prod_policy`, `dev_claims` …), with sensitive data concentrated in dedicated schemas (`prod_claims.restricted`) where no schema- or catalog-level read grants are allowed; curated, non-sensitive schemas (`prod_claims.curated`) may carry schema-level grants to broad analyst groups. Catalog and schema owners are groups (e.g. the domain's data-owner group), never individuals. Pipelines write as service principals that own the tables they produce.
- **Groups.** Role groups (claims_handler_eu, actuary, fraud_investigator) and access groups (claims_readers) — grants go to access groups; people join role groups; role groups are members of access groups. Few grants, many memberships.
- **Row filters and masks.** Row filter on claims: `region IN (SELECT region FROM gov.region_access WHERE is_account_group_member(group_name))` style — driven by a mapping table of group → region, not user names. Masks on name, email, national id: return the value if the user is in the fraud group *and* (for strictness) the record is in an open investigation via a mapping table; otherwise a masked form. Filter and mask functions live in a governance schema owned by the governance team; changes are reviewed and versioned (code in a repository, deployed by a service principal).
- **Model for access questions.**
  - `securables (securable_id, type metastore|catalog|schema|table|column|function, parent_id, name, created_at, dropped_at)` — stable ids, names as attributes with history (`securable_names (securable_id, full_name, valid_from, valid_to)`), so a recreated table is a new id.
  - `principals (principal_id, type user|group|service_principal, external_id, display_name, status, valid_from, valid_to)`.
  - `memberships (group_id, member_id, valid_from, valid_to)` — direct only; nested expansion is derived.
  - `grants (securable_id, principal_id, privilege, granted_by, valid_from, valid_to)` from the grant/revoke event log.
  - `policies (securable_id, kind row_filter|column_mask, function_id, function_version, columns, valid_from, valid_to)`, `function_versions (function_id, version, body_hash, changed_by, changed_at, reviewed_by)`.
  - Derived `effective_membership (principal_id, group_id, as_of_date)` — transitive closure with a depth limit and cycle detection (recursive CTE with a visited path, or iterative expansion until no new pairs; cycles reported).
  - Derived `effective_access (as_of_date, principal_id, table_id, column_id NULL, can_read, row_filter_version, mask_version, masked BOOL, grant_chain)` — for each principal: groups as of the date → grants on the table, its schema, its catalog (inheritance) → requires usage on catalog and schema plus read on table (or inherited) → combine with policy versions in force and the principal's membership for the mask decision.
- **Freshness.** Recompute effective access incrementally when memberships, grants, policies or securables change (affected principals × affected subtree), plus a daily full rebuild for verification; store daily snapshots (or intervals) for the two-year reproducibility.

**Competing designs to accept.** Catalogs by business unit with environments as separate metastores or workspaces. Attribute-based access (tags on columns plus policies keyed on tags) instead of per-column masks, if they model tag history. Views per audience instead of row filters, when the number of audiences is small and they handle drift. Computing effective access on demand with recursive queries instead of materialising it, if they show it is fast enough and reproducible as of a date.

**Bottlenecks and failure modes.** Catalog-level read grants exposing future sensitive tables; masks that name users; filters edited without review; group cycles causing infinite expansion; name-keyed history broken by renames and recreation; effective-access built from current membership only (cannot answer "on 3 March"); service principals forgotten; identity sync failures leaving stale access.

**Incident guidance.**
- *Catalog-wide read grant exposes a new contact-data table*: inheritance did exactly what it promises. Contain: revoke the catalog-level grant and replace with schema-level grants on curated schemas; move the table to a restricted schema; use the audit events to list who read it during the three weeks. Guardrail: a policy check that rejects read grants at catalog level (and schema level on restricted schemas) to groups above a size, and a tag-based scan that flags new tables with contact-data columns in grant-inherited locations.
- *Identity sync fails for a day*: membership is stale in both the platform and the model. Contain: treat the sync as an incident with an alert on sync age; manually remove leavers from the fraud group; recompute effective access with the corrected membership and mark the day's snapshot as derived from stale data. Guardrail: sync freshness monitor and a deny-by-default for the fraud mask when the mapping table is stale.
- *Row filter edited without review returns all regions*: the function version changed without review. Roll back to the prior version; from audit events and the function's change time, list queries against the table in the window (by principal) and assess exposure across {{regions}}; require review and deployment through a service principal, and add a test that the filter returns no foreign-region rows for a sample of handler groups.

**Follow-up guidance.** (1) Expand their groups: if the project group has a read grant on the claims table and the row filter is driven by the region mapping, the extra group only grants other regions if it appears in the mapping; show the chain. (2) The schema-level grant covers the new table immediately; prevented by putting raw transcripts in a restricted schema and a check on table creation. (3) Recursive membership as of the date, grants as of the date with inheritance, mask version as of the date, and the fraud-group condition — the query lists principals with an unmasked path. (4) A recreated table is a new securable id; old grants were on the old id unless they were inherited from the schema (then they apply — say so). (5) Size ≈ principals × readable tables (much larger with columns); store per group, expand per user lazily, and update incrementally; daily snapshots for reproducibility.

**Rubric anchors.** 2: a list of grants and some views; no inheritance risk, no history. 3: layout with owners, role/access groups, filters and masks driven by membership, a model with stable ids, history and an effective-access derivation. 4: also cycle handling, as-of reproducibility, review and versioning of policy functions, guardrails on broad inherited grants, and service principals in scope.

**Strong signals.** Spots that inheritance covers future tables; keys history on ids, not names. **Red flags.** Masks or filters naming individual users; "grant on the catalog to keep it simple"; access answers from current state only.

## DBX-L3-04

**Reference architecture (one defensible design).**
- **Raw (`audit_raw`).** Append-only, one row per delivered record: `delivery_file`, `delivery_received_at`, `raw_json` verbatim, `event_id`, `event_time`, `workspace_id`, `service_name`, `action_name` (parsed for partitioning), `event_date` partition. Stored in a location with object lock (write-once retention) or at least versioning plus deny-delete policies for {{retention_years}} years; a daily manifest records file names, record counts and a hash chain (each day's manifest hash includes the previous day's), signed or stored in a separate account. Completeness: compare record counts per workspace and hour with any counts the platform exposes, and alert on gaps.
- **Normalised fact (`fct_audit_event`).** Grain: one row per `event_id` (redeliveries deduplicated by MERGE insert-if-absent, keeping the first `delivery_received_at`). Columns: `event_id`, `event_time`, `workspace_id`, `service_name`, `action_name`, `action_category` (from a mapping table: data_read_evidence, metadata_access, permission_change, sign_in, download, token, compute, job, other_unknown), `evidence_strength` (strong: credential issued for data files or query executed against the table; weak: metadata fetched), `actor_principal_key`, `actor_type`, `source_ip`, `user_agent`, `securable_key` (resolved), `result_status`, `request_params_restricted` (in a restricted table or column), `raw_ref` (pointer to raw row).
- **Action mapping.** `action_map (service_name, action_name, category, evidence_strength, valid_from, valid_to)`; unknown pairs land as `other_unknown` and are alerted daily so the map is updated; when updated, the fact is recomputed for those pairs (it is derived, rebuildable).
- **Identity.** `dim_principal` (type 2) keyed by the platform's stable user or service-principal id; names and emails as attributes with history; links to the bank's employee id from the identity provider; `principal_accountable_person` for service principals (owner, creator, or the job owner at the time) with history.
- **Objects.** `dim_securable` keyed by stable table id with name history (renames and drop-recreate produce distinct ids); events that only carry a name are resolved by name as of the event time.
- **Network.** `dim_network_range (cidr, classification corporate|vpn|cloud|partner|public, valid_from, valid_to)`; classification resolved at event time and stored on the fact (`network_class_at_event`) so last year's answer uses last year's list; the current classification is a separate lookup when asked.
- **Answers.** Views: `who_read(table_id, from, to)` = union of strong and weak evidence with the strength stated; `principal_activity(person, window)`; `permission_changes(on sensitive tags)`; `external_access`. Each answer carries `data_complete_through` (the latest hour with complete delivery) so answers for recent periods are labelled provisional.
- **Retention and tiers.** Raw: {{retention_years}} years, hot for 90 days, then cold/archive tier; fact: hot for 1–2 years, compressed columnar, partitioned by `event_date`, clustered by `securable_key` and `actor_principal_key`. Restricted access for request parameters; compliance team only.

**Competing designs to accept.** Keeping only the raw table plus views that parse JSON at query time for low volumes (level 1) — acceptable if they show the cost argument at higher volumes. A dedicated security analytics store (SIEM) fed from the fact, with the lakehouse as the system of record. Hash-chained manifests versus object-lock-only immutability; both acceptable with reasoning.

**Bottlenecks and failure modes.** Querying JSON across years; names as keys (renames, marriages, recreated tables); treating metadata fetches as data reads (over-reporting) or ignoring credential issuance (under-reporting); unknown actions silently dropped; network classification looked up at query time with today's list; deletion of raw evidence by lifecycle jobs; late events producing wrong "no access" answers.

**Incident guidance.**
- *Renamed action filed as unknown*: the category map did not know it. Contain: alert on any action with volume in `other_unknown`; map the new name, recompute the fact for the two weeks and reissue the monthly report with a note. Guardrail: a daily check that each strong-evidence category's volume is within a band of its baseline, and a release-notes review of audit schema changes.
- *Delivery outage then catch-up*: the earlier answer was given on incomplete data. Contain: mark answers with `data_complete_through`; re-run every compliance answer issued for the affected days once the backlog lands and send corrections. Guardrail: never answer "no access" for a period beyond the completeness watermark (usually {{delivery_delay}} behind, longer during outages).
- *Retention job deletes raw events*: the raw location lacked write-once retention and shared a lifecycle setting with derived tables. Recover from storage versioning, replicas or the platform's own retained copy if any; record the gap formally (with the manifest proving what is missing); apply object lock with {{retention_years}}-year retention, separate the raw location and its permissions, and make the manifest check alert on deletions.

**Follow-up guidance.** (1) One row per event id, first delivery wins; MERGE insert-if-absent. (2) Resolve the table's stable id (including its earlier name), filter strong and weak evidence categories, join principals as of event time, and attribute service-principal reads to the accountable person with the evidence. (3) Sign-ins, queries, credential requests, downloads, token creation, permission changes — with strong evidence of data access separated from metadata access. (4) The stored classification at event time answers April as it was; a reclassification is a new interval. (5) Storage: {{daily_events}} × a few hundred bytes compressed per event × days; hot and cold tiers; immutability by object lock plus a hash-chained manifest an auditor can verify.

**Rubric anchors.** 2: a single table of parsed events keyed by user name, no immutability or deduplication. 3: raw verbatim and immutable, a deduplicated fact with categories, history-aware identity and object dimensions, explicit read versus metadata. 4: also unknown-action handling with alerts, network classification as of event time, service principals attributed, completeness watermarks on answers, and a provable retention design.

**Strong signals.** Asks what a "read" event actually proves; keeps names out of keys. **Red flags.** Lifecycle deletion on raw evidence; answering "no access" without a completeness check; dropping events whose action is unknown.

## DBX-L3-05

**Reference solution** (PostgreSQL)

```sql reference
WITH done AS (                                 -- only completed updates are reported or compared
  SELECT update_id, dataset, started_at, rows_in
  FROM pipeline_updates
  WHERE status = 'COMPLETED'
), checks AS (                                 -- each failed check once (the log is at least once)
  SELECT DISTINCT f.update_id, f.record_id, f.expectation
  FROM expectation_failures f
  JOIN done d ON d.update_id = f.update_id
), judged AS (                                 -- the action in force when the update started
  SELECT c.update_id, c.record_id,
         (SELECT v.action
          FROM expectation_versions v
          WHERE v.dataset = d.dataset
            AND v.expectation = c.expectation
            AND v.effective_from <= d.started_at
          ORDER BY v.effective_from DESC
          LIMIT 1) AS action
  FROM checks c
  JOIN done d ON d.update_id = c.update_id
), per_update AS (
  SELECT d.dataset, d.update_id, d.started_at, d.rows_in,
         COUNT(DISTINCT j.record_id) AS failing_rows,
         COUNT(DISTINCT j.record_id) FILTER (WHERE j.action = 'drop') AS quarantined_rows
  FROM done d
  LEFT JOIN judged j ON j.update_id = d.update_id
  GROUP BY d.dataset, d.update_id, d.started_at, d.rows_in
), pct AS (
  SELECT *, ROUND(100.0 * failing_rows / rows_in, 2) AS failure_pct
  FROM per_update
)
SELECT dataset, update_id, rows_in, failing_rows, quarantined_rows, failure_pct,
       LAG(failure_pct) OVER w AS prev_failure_pct,
       failure_pct - LAG(failure_pct) OVER w AS change_pts
FROM pct
WINDOW w AS (PARTITION BY dataset ORDER BY started_at)
ORDER BY dataset, started_at;
```

**Explanation.** The completed updates are the driving set: they are the rows of the report and the only candidates for "previous", so the filter comes before `LAG`. Failures are reduced to distinct (update, record, expectation) checks, which makes the query immune to a redelivered event log at Very Hard and costs nothing at the lower levels. Each check is then given the action of the expectation version in force when its update started — the latest `effective_from` at or before `started_at`, inclusive — never the current version and never the version at `logged_at`. Counting distinct records gives failing rows; the same count restricted to `drop` gives quarantined rows, so a record that failed a `warn` and a `drop` check is quarantined once. The LEFT JOIN keeps clean updates (zero failures) in the report, and `LAG` over the completed updates of each dataset gives the trend; `change_pts` subtracts the two rounded percentages.

**Complexity.** One pass over failures for the completed updates (a hash join and a hash distinct), a lookup per distinct check into the versions (tiny, indexed by dataset and expectation), one aggregate per update and one sort per dataset for the window. In production the failure log is pre-aggregated per update and record (or per update and expectation, with care, see below), so the report reads a small summary table.

**Dialect notes (not executed here).** `COUNT(DISTINCT …) FILTER (WHERE …)`: Spark SQL 3 supports `FILTER`; Snowflake uses `COUNT(DISTINCT IFF(action = 'drop', record_id, NULL))`, BigQuery `COUNT(DISTINCT IF(action = 'drop', record_id, NULL))`, MySQL `COUNT(DISTINCT CASE WHEN … THEN record_id END)`. The correlated `ORDER BY … LIMIT 1` subquery is not portable (Spark SQL and BigQuery restrict correlated subqueries); the portable form joins versions with `effective_from <= started_at` and keeps the latest with `QUALIFY ROW_NUMBER() OVER (PARTITION BY update_id, record_id, expectation ORDER BY effective_from DESC) = 1` (Snowflake, BigQuery, Databricks SQL) or a row-number subquery (MySQL 8, older Spark). The named `WINDOW` clause exists in PostgreSQL, MySQL 8, Spark SQL and BigQuery; where it is not available, repeat the `OVER (…)` clause. Do the percentage in a decimal type so that rounding matches `ROUND(…, 2)` on exact values; in binary floating point a value such as 1.005 is stored just below the half and rounds down.

**Edge cases built into the data.** Records failing two or three expectations (one failing row); a record failing a `warn` and a `drop` expectation (quarantined once); a completed update with no failures (zeros, and it is the previous update of the next one); failed updates between completed ones (excluded, and skipped by the trend); failed updates with failures of a `fail` expectation. Hard adds actions that change over time, one exactly at a completed update's `started_at` (in force for that update), an expectation added later, and cancelled updates. Very Hard adds redelivered failures (same update, record and expectation, later `logged_at`), a version that takes effect while an update is running (the update keeps the action it started with), and an update still running.

**Common mistakes.** `COUNT(*)` of failure rows (checks, not records); counting every failing record as quarantined; reporting failed or cancelled updates; running `LAG` before filtering to completed updates; an inner join that drops clean updates; (Hard+) using the current action, or `effective_from < started_at`; (Very Hard) counting redelivered checks, or looking up the action at `logged_at`. Each has a diagnostic. Another frequent one: summing per-expectation failure counts to get failing rows — a record failing two expectations is counted twice. (Some pipeline event logs report passed and failed counts per expectation rather than per record; in this exercise that is why the per-record log exists; check current docs.)

**Follow-up guidance.** (1) Compare like with like: compute the rate over expectations present in both updates (an expectation-set fingerprint per update), or report a "new expectations" component separately from the change. (2) A further CTE with `LAG(change_pts)` (or a running count of consecutive breaches) and a filter on both above the threshold. (3) Aggregate at write time to one row per (update, record) with a bitmask or array of failed expectations, or keep per-(update, expectation) counts plus a per-update distinct-record count; partition by dataset and date; old raw failures expire after a retention period. (4) `quarantined_rows / rows_in` (30%) should page the dataset's owners regardless of gold looking normal; quarantine rate per expectation and change against the previous completed update are the alerting signals.

**Rubric anchors.** 2: right shape but counts checks instead of records, or loses clean updates, or uses the current action. 3: matches the expected result. 4: also explains like-for-like trends, why summing per-expectation counts overcounts, and how to pre-aggregate the log.

**Strong signals.** Asks which version applies before writing the join; filters before the window without prompting. **Red flags.** `LAG` over all updates followed by `WHERE status = 'COMPLETED'`; `SELECT DISTINCT *` on the log as deduplication (rows differ in `logged_at`); joining versions without a time predicate.
