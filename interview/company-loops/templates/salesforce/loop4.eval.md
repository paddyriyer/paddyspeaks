# Salesforce · Loop 4 — evaluator notes (hidden from candidates)

## SFC-L4-01

**Reference architecture (one defensible design; score others on the criteria).**
- **Ingest and normalise**: each source arrives as change events or as full extracts; extracts are diffed against the last extract per source (by source record id and a content hash of the normalised fields) so only real changes flow on. Normalisation is versioned and applied before matching: lowercase and trim emails, phone numbers to an international format, postal addresses parsed into components, names folded. A source record is stored with its org id, source id, source record id, normalised identifiers and its own consent signals.
- **Match graph**: per org, records are nodes; each match rule produces edges labelled with the rule id and rule version. Candidate generation uses blocking keys per rule (the normalised email; last name plus postcode) so comparisons stay near linear. Before an identifier value creates edges, its frequency in the org is checked: values shared by more than a threshold of records (a support mailbox, a call-centre number, "test@") are put on a per-org common-value list and do not link. Administrator "never merge" pairs are hard constraints: a component that would contain both is split along the weakest edges between them.
- **Profiles**: a profile is a connected component of the match graph (or, for stricter orgs, a component under the rules that require two identifiers). Incremental updates use union-find with deletion handled by recomputing only the affected component. Profile id survivorship: on merge, the id of the older (or larger) profile survives and the other is recorded as merged into it, with a redirect; on split, the part containing the profile's anchor record keeps the id and the other part gets a new id plus a "split from" link. Downstream segments subscribe to merge, split and redirect events.
- **Rule changes**: a new rule set is resolved into a shadow version of the graph and profiles; a diff (merges, splits, size distribution, largest components) is shown to the administrator and compared against alarms; cutover switches the read pointer atomically and emits the merge and split events. The old version is retained for rollback.
- **Explanation and unmerge**: because edges keep the rule and the matched values (normalised identifiers only), the system can show "merged because rule R2 matched email on records A and B". An unmerge records a never-merge constraint and recomputes the component.
- **Consent**: consent events keyed by (org, person identifier, purpose) with source, timestamp and explicit grant or withdrawal. A profile's effective consent per purpose is computed from all its records' consent under the org's precedence policy (default: most recent explicit choice, withdrawal never overridden by an older grant; this exercise's rule). Activation checks consent at send time against a low-latency consent store, not only at segment build, and exports to external tools are followed by suppression updates so a withdrawal reaches them within {{withdraw_minutes}} minutes. Consent events travel on their own priority path, never behind re-resolution.
- **Deletion**: a deletion request marks the person's source records, removes them from the graph, recomputes components, and fans out deletions to derived stores (profiles, segment memberships, caches, exports via the connectors' delete APIs), with a ledger that records each store's confirmation.
- **Isolation and quality**: every key starts with org id; matching never compares across orgs. Over-merge and under-merge are measured per org with metadata only: component size distribution, share of profiles with conflicting identifiers (two different dates of birth), unmerge rates, and sample review by the org's own administrators.

**Competing designs to accept.** Batch resolution on a schedule with a fast incremental path for new records; strict two-identifier rules for profiles with transitive matching only within a profile; a scored fuzzy matcher with thresholds per org, if explanations and overrides are designed; profile ids that never change (a new id per component version with a stable alias table) if downstream impact is handled.

**Bottlenecks and failure modes.** Giant components from common values; full re-resolution blocking incremental updates and consent; profile id churn breaking segments; extracts re-sent with changed normalisation; consent applied only at segment build time; deletions that miss exports and caches.

**Incident guidance.**
- *Phone rule merges 30,000 contacts*: stop activation for oversized profiles immediately (a size alarm), roll back to the previous rule version's profiles, add the number to the common-value list, and retract the merged profile from segments. Notify the org; the campaign's misdirected email is a privacy incident to report under its process. Prevention: shadow resolution with a diff and a component-size gate before cutover, and frequency checks on every new identifier rule.
- *Lowercased extract adds 12%*: the source's identifiers changed form, not meaning. Normalise on ingest so the extract would have matched; if it already flowed, re-run normalisation for that source and re-resolve the affected components; dedupe by source record id, which did not change. Prevention: an alarm on profile count change per source run and a contract on extract format.
- *Consent stuck for 9 hours*: consent must never queue behind resolution work. Apply the pending withdrawals immediately from the consent stream, suppress the person in every export, and audit who was contacted after opting out. Prevention: a separate consent path with its own latency SLO against the {{withdraw_minutes}}-minute bound and an alarm on consent lag.

**Follow-up guidance.** Push on what happens to a profile id on merge and split, how a never-merge pair survives a rule rerun, and where consent is checked (at send time). Ask how the design scales with {{records}} records: blocking keys and incremental components, not all-pairs comparison.

**Rubric anchors.** 2: one matching job that writes a golden record; no notion of edges, unmerge or consent precedence. 3: match graph with labelled edges, stable ids with survivorship, shadow re-resolution, consent as its own stream checked at activation, deletion fan-out. 4: also common-value detection, never-merge constraints, explanation from edges, metadata-only quality measures per org, and crisp incident handling with prevention.

**Strong signals.** Asks whether matching is transitive and what it costs; treats consent as a separate, faster path. **Red flags.** A fuzzy model with no explanation or override; consent copied only into a nightly profile; deleting the source record but not the exports.

## SFC-L4-02

**Reference architecture (one defensible design; score others on the criteria).**
- **Snapshot read**: the refresh reads a consistent point-in-time snapshot or a read replica of the org's production data, throttled per org so production work is unaffected; objects are copied in dependency order (parents before children) or with deferred reference resolution.
- **Classification**: each field has a masking policy derived from (a) the administrator's data-classification label, (b) the field's type (email, phone, date of birth) and (c) a detector run over a sample of values. A field that the detector flags but nobody labelled is masked by a conservative default (blank or generic replacement) and reported to the administrator; it is never copied in clear. The policy set is versioned and attached to each refresh.
- **Masking in the pipeline**: values are masked in memory between read and write. No unmasked value is written to sandbox storage, search indexes, logs or spill files; the pipeline's own logs carry only ids and counts. Masking is keyed and deterministic: `token = HMAC(sandbox_secret, field_class || normalised_value)`, used to select a replacement from a large dictionary (names), to construct a format-valid value (an email on a reserved test domain, a phone number in a reserved range, a postcode of the right shape) or to format-preserve. Using a field class rather than a field name means the same email masks identically in contact, lead and email-message fields, so lookups, duplicate rules and matching still work.
- **Uniqueness**: for unique fields, the deterministic token is checked against already-issued values for that field in the sandbox; on collision a counter is appended deterministically (`HMAC(secret, value || n)`) and the mapping is stored, so uniqueness holds and repeat refreshes give the same answer.
- **Secret lifecycle**: one secret per sandbox, stored in the platform's key management, never exported to the sandbox. Different secrets make sandboxes uncorrelated. Rotating the secret forces a full re-mask of every object; partial top-ups use the same secret as the full refresh they extend.
- **Free text and files**: free-text fields are either replaced by placeholder text of similar length or passed through a redaction step that replaces detected entities with their masked tokens (so "call Ana on +1…" becomes the masked name and number); attachments are excluded or replaced by placeholder files of the same type and size class, unless the administrator explicitly opts in per object.
- **Partial copies**: start from a sample of root records (for example 1% of accounts chosen by a hash of the id so it is repeatable), follow child relationships to a bounded depth and include referenced parents, with a cap per object; references outside the sample are nulled or pointed at a placeholder record.
- **Sandbox safety**: email deliverability off by default, outbound integrations' endpoints and credentials not copied, scheduled automations paused until re-enabled, SMS providers pointed at a sink.
- **Proof**: a per-refresh manifest (policy version, objects, fields and their policies, counts masked) and a post-refresh scan that samples values from the sandbox and checks them against production values by keyed hash on the production side, without exporting production values.

**Competing designs to accept.** Copy into an isolated staging area inside the production trust boundary, mask there, then publish to the sandbox (acceptable if the staging area is as protected as production). Format-preserving encryption instead of HMAC plus dictionary, if the key never reaches the sandbox. Synthetic data generated from statistics for some objects, if the candidate states what tests lose.

**Bottlenecks and failure modes.** Unlabelled fields copied in clear; copy-then-mask leaving real data in the sandbox; files dominating the time; collisions on unique fields; secrets rotated mid-series; automations reaching real people from a sandbox.

**Incident guidance.**
- *Unlabelled mobile-number field, SMS to 2,000 customers*: stop outbound messaging in the sandbox immediately, purge the field's values in that sandbox, treat it as a personal-data incident (notify the org; the org decides on notification to individuals). Prevention: detector-based fail-closed masking for unlabelled fields, outbound messaging disabled by default in sandboxes, and a check that new fields since the last refresh have a policy.
- *Overrun of the {{window_hours}}-hour window due to attachments*: do not open a half-loaded sandbox; mark it unavailable until complete. Exclude or placeholder files by default, copy objects in parallel by dependency level, and estimate duration before starting from object sizes so the window can be planned.
- *Secret rotated between full refresh and top-up*: tokens no longer agree. Roll back the top-up or re-mask everything with the new secret; prevention is a rule that a top-up must use the secret of its base refresh and that rotation triggers a full refresh.

**Follow-up guidance.** For the unique field, look for deterministic collision handling, not "probability is low". For free text, credit candidates who admit what testers lose. For auditors, look for a manifest plus a scan that does not move production values out.

**Rubric anchors.** 2: copy then run a masking script; random values; no plan for unlabelled fields. 3: masking in the pipeline, keyed deterministic masking per sandbox with formats preserved, fail-closed classification, outbound actions disabled. 4: also uniqueness under collisions, secret lifecycle with rotation rules, referentially closed partial copies with bounds, evidence for auditors, and crisp incident handling.

**Strong signals.** Separates consistency (deterministic) from correlatability (per-sandbox secret). **Red flags.** Unsalted hashes of emails; masking after copy; trusting labels alone; leaving production integrations' credentials in the sandbox.

## SFC-L4-03

**Reference architecture (one defensible design; score others on the criteria).**
- **Event contract**: a registry of event types with an allowlist of properties and types (ids, enums, counts, durations, feature ids), owned per event type, reviewed for content risk. Collectors validate against the registry: unknown properties are dropped and counted, string properties have length limits and pattern checks (emails, long free text) that quarantine the event and alert. Events carry `event_id, org_id, pseudo_user_id, user_kind (person | integration), event_type, feature_id, ts`.
- **Collection**: regional collectors write to a durable log partitioned by org id with a salt for the largest orgs; deduplication by event id within a window.
- **Limit path (exact and fast)**: a streaming job maintains per-org counters for each limit over the rolling window (API calls, async executions), with idempotent updates keyed by event id or by the authoritative counter emitted by the enforcing service. Thresholds (80%, 100%) trigger alerts within {{alert_minutes}} minutes; the alert path has its own freshness monitor. The daily statement is computed from the authoritative counts, not from the stream.
- **Analytical path**: events land in a columnar store partitioned by event date and org; daily and weekly aggregates per (org, feature) with exact distinct users per org (an org's view must match its user list) and mergeable sketches (HyperLogLog) per feature across orgs for product teams. Late data reopens partitions for a bounded period; reports show completeness per region and day.
- **Models**: logins (outcome, method, person vs integration), feature adoption (an org adopts when ≥ 1 person used it in the rolling 28 days), active users (people only), limit consumption against allocation by day.
- **Access**: the administrator view is filtered by org id at the query layer (row-level security), with names resolved inside the org's own boundary from the org's own user list. Cross-org views use pseudonymous ids only and suppress cells below a minimum number of orgs or users. Named-org views are restricted to authorised account teams, logged.
- **Skew and cost**: aggregates are incremental per day; work scales with events, not orgs × features, because only (org, feature) pairs with events are materialised.

**Competing designs to accept.** A single streaming system for both paths if exactness and replay are handled; exact distinct counts everywhere if cost is estimated and accepted; a lambda-style recompute of daily aggregates overnight with a streaming approximation during the day.

**Bottlenecks and failure modes.** Content leaking through free-form properties; runaway integrations distorting org metrics; hot partitions for the largest orgs; late regions making adoption look like it dropped; double counting after stream restarts; alert lag hidden by the dashboard looking fine.

**Incident guidance.**
- *Search text in a feature event*: drop the property at the collector by updating the allowlist, purge the stored values (partitions are by date, so rewrite the affected days), and verify with a scan; record it as a data-handling incident. Prevention: allowlist enforcement, pattern checks on strings, review of new properties.
- *Integration failing logins 40,000 times an hour*: separate integration users from people in every metric and exclude them from active-user counts; rate-limit or quarantine the org's events at the collector if they exceed a budget; recompute the affected week. Tell the org's administrator, whose integration is failing.
- *Limit alerts two hours late*: the counter path must have its own lag monitor; during a backlog, the enforcing service's own counts should drive alerts. Notify affected orgs, and backfill the missed alerts with an explanation.

**Follow-up guidance.** On weekly active users, look for exact per-org and sketch-based across orgs, with the reason. On the release effect, credit cohort comparisons (orgs eligible at the same time) and acknowledging that large orgs adopt differently.

**Rubric anchors.** 2: stores raw events with everything in them; one pipeline for alerts and reports; no isolation story. 3: allowlist at collection, two paths, idempotent ingestion, late-data handling, per-org isolation and suppressed aggregates. 4: also skew handling, precise metric definitions with integrations separated, alert freshness monitoring, a purge path, and crisp incident handling.

**Strong signals.** Starts from what must not be collected. **Red flags.** "We hash the record contents"; cross-org views showing users; alert latency measured only in good times.

## SFC-L4-04

**Reference architecture (one defensible design; score others on the criteria).**
- **Admission**: an enqueue API checks the org's rolling daily limit (a sliding window counter per org, exact or bucketed by minute) and rejects or warns at thresholds; jobs are written durably to a per-org queue partition with a job id, class (user-initiated, scheduled, bulk) and an idempotency key.
- **Queues**: per (org, class) logical queues stored in a durable queue or database table partitioned by org. A dispatcher keeps the set of orgs with runnable work in an in-memory structure ordered by virtual time (weighted fair queuing): each org's virtual time advances by worker-seconds consumed divided by its weight. Picking the next org is O(log active orgs) with a heap. Classes across orgs: user-initiated jobs have a reserved share of workers and a separate fair queue, so they start in seconds.
- **Caps**: each org has a concurrency cap (a maximum number of in-flight executions) proportional to its weight, so one org cannot occupy the pool even if others are idle for a moment; idle capacity is lent but reclaimed as other orgs arrive (by not starting new jobs, never by killing running ones).
- **Leases**: a worker takes a lease with an expiry and a fencing token; it heartbeats; if the lease expires, the job becomes runnable again with a higher token. Writes check the token (stale writers are rejected). Side effects carry the job's idempotency key, and email or callout sends are recorded in an outbox before delivery so a rerun sees they were sent.
- **Contention**: jobs declare (or the platform infers) the parent record they lock; the dispatcher serialises jobs per (org, lock key) and spreads others; lock failures back off with jitter and count against a retry budget.
- **Retries and poison jobs**: bounded retries with backoff; a job type that keeps hitting its CPU-time limit is quarantined and reported to the org, and its worker-seconds count toward fairness.
- **Observability**: per-org queue depth, oldest job age, worker-seconds used in the last hour and the org's share; per-class wait-to-start p50/p99; the org sees its own queue and why it waits (its cap, its share, or platform saturation).
- **Autoscaling**: on aggregate demand and wait across many orgs, not on one org's backlog.

**Competing designs to accept.** Deficit round robin over per-org queues with quanta in worker-seconds; separate pools per org size tier; shuffle sharding of orgs to worker groups to contain noisy neighbours (with a fairness story inside each group); token buckets per org feeding a shared queue.

**Bottlenecks and failure modes.** Global FIFO handing the pool to the fastest enqueuer; fairness by job count with long jobs; priority inflation; lock storms from one org; lease expiry under pauses causing double execution; retry storms; autoscaling that rewards a noisy org.

**Incident guidance.**
- *Three million jobs at 09:00*: the queue is FIFO or the org has no cap. Immediately cap that org's concurrency and move its backlog to its own queue; user-initiated work for others gets reserved capacity. Prevention: per-org queues, fair scheduling and caps; admission warnings for bulk loads.
- *Job type at CPU limit retried five times, a third of the {{workers}} workers*: fairness measured in job count missed it. Quarantine the job type after repeated limit hits, count worker-seconds in the fair share, and alert the org. Prevention: worker-seconds accounting and retry budgets per job type.
- *Worker restart, 18,000 jobs run twice*: leases expired and jobs reran; side effects were not idempotent. Stop the duplicate sends (outbox with idempotency key), identify affected jobs from the lease log, and inform the org. Prevention: fencing tokens, outbox for side effects, graceful drain on deploy so leases are released or completed.

**Follow-up guidance.** For the scheduler, ask for the data structure and per-dispatch cost with {{orgs}} orgs (a heap or calendar over active orgs only). For the GC pause, look for fencing tokens, not "longer leases".

**Rubric anchors.** 2: one queue, more workers, retries without idempotency. 3: per-org queues with fair sharing and caps, admission with the daily limit, leases and idempotent side effects. 4: also fairness by worker-seconds with weights, urgent class isolation, fencing tokens, contention serialisation, poison-job quarantine, per-org visibility and incident handling with prevention.

**Strong signals.** Defines fair before designing; distinguishes at-least-once execution from exactly-once effects. **Red flags.** "Kafka will handle it"; autoscaling as the answer to a noisy neighbour; priority set by the tenant across tenants.

## SFC-L4-05

**Reference architecture (one defensible design; score others on the criteria).**
- **Policy and selection**: per org and object, a policy (filter on a date field and status, plus exclusions) evaluated by a selector that runs in small, throttled batches outside the org's busy hours, using an index on the date field. The selector picks parent records and expands each to its family (comments, emails, attachments, history) so the family moves together.
- **Move protocol**: for each batch, a durable manifest (batch id, org, object, record ids, family counts, checksum) is written first; records are copied to the archive with the batch id; the archive copy is verified (counts and checksums); only then are the records deleted from the primary store in a transaction per family; the manifest moves to done. Every step is idempotent by (batch id, record id): a rerun after a crash skips already-copied records and never deletes unverified ones.
- **Archive store**: columnar files in object storage partitioned by org, object and close month, encrypted with the org's keys; a key-value index by record id (org, object, id → file, row group, offset, schema version) for single-record opens under two seconds; a stub in the primary store or a redirect table so live lookups to an archived parent resolve to the archive.
- **Access**: archived records keep the fields the sharing model needs (owner, account, record type, territory or other criteria fields). Opening or reporting on archived data evaluates access against the current sharing model with those fields (owner in the user's role subtree, matching sharing rules, team membership), so rule changes after archiving apply. Manual shares on the record are archived with it.
- **Schema**: each batch records the object's schema version; a combined view over live and archived data maps later fields to nulls (or their declared defaults) and deleted fields to a separate archived-only column set. Reports declare which fields are available across both.
- **Retention and holds**: a retention job per org deletes archive partitions or rows older than the retention period, re-checking legal holds at deletion time (holds stored as filters, evaluated per record) and honouring a grace period after a policy change (for example 7 days before any newly eligible deletion). Deletion requests for a person are applied to the archive by rewriting affected files and removing index entries, with a ledger.
- **Restore**: copy back to the primary store with the original ids (or new ids with a mapping), then remove from the archive using the same manifest protocol.
- **Reconciliation**: per batch and per month, counts of selected = archived = deleted from primary; a daily check that no id is present in both stores.

**Competing designs to accept.** A cheaper tier inside the same database (partitioned table on slower storage) for smaller orgs; an archive in a separate relational store when single-record access dominates; bulk export to a customer-owned store with a connector, if access control and deletion are addressed.

**Bottlenecks and failure modes.** Partial moves after crashes; orphaned children; duplicate archive rows; stale access decisions; schema drift breaking combined reports; retention deletion racing legal holds; deletion requests that miss the archive.

**Incident guidance.**
- *2 million cases copied twice*: the copy was not idempotent by (batch, record). Deduplicate the archive by record id keeping one copy per verified checksum, correct the combined reports for that month, and verify the primary store no longer has those cases. Prevention: manifest with idempotent copy and verification before delete.
- *Attachments left behind*: the selector moved parents without their family. Pause the policy, move the orphaned attachments into the archive with their parents' batch ids (or restore the parents), and make sure the deletion path covers both stores. Prevention: family expansion as part of selection and a reconciliation check for children whose parent is archived.
- *Retention cut from {{retention_years}} to 2 years, then a hold*: deleted data cannot come back unless backups are within the hold's scope; tell counsel exactly what was deleted and when (from the ledger). Prevention: a grace period after any retention change, holds re-checked at deletion time, and administrators warned about the volume a new policy will delete.

**Follow-up guidance.** For the access question, credit storing sharing-relevant fields and evaluating at read time; penalise copying a snapshot of who could see the record at archive time with no update. For the proof, look for manifests and reconciliation, not "we trust the job".

**Rubric anchors.** 2: a flag column or a nightly export with no deletion protocol or access story. 3: family-based selection, copy-verify-delete with idempotent reruns, a columnar archive plus an id index, retention and holds. 4: also access re-evaluated at read time, schema versions in combined reports, deletion requests reaching the archive, reconciliation proving exactly one place, and crisp incident handling.

**Strong signals.** Asks what a live record that points at an archived one should do. **Red flags.** Deleting first and copying later; retention deleting without a hold check; archived data readable by anyone with archive access.
