# Together AI · Loop 4 — evaluator notes (hidden from candidates)

All figures in these scenarios are hypothetical, and every rule (billing, notice,
retention, deletion targets, floors) is this exercise's, not a statement of any
company's terms. Score designs on the criteria, not on resemblance to the
reference; none of the references describes how any company's systems are
actually built, and none implies knowledge of its customers, hardware or capacity.

## TGA-L4-01

**Reference architecture (one defensible design; score others on the criteria).**
- **What is measured**: on the server, per request: `accepted_at`, `scheduled_at` (left the queue, first scheduled into a batch), `first_token_at`, `last_token_at`, input and output token counts, outcome, replica id, tenant id, model version id. Derived: queue time, prefill-to-first-token time, time to first token (= both), generation time and output tokens per second after the first token. The console labels time to first token as server-side, excluding network and the client's own processing.
- **Event and transport**: one compact event per request (no prompt or output text, enforced by the schema at the producer) to a partitioned log keyed by (model version, replica) so per-replica order is preserved; tenant id is a field, not the key, so a huge tenant does not create a hot partition.
- **Aggregation**: per (tenant, model version, minute): exact counts (requests, errors, input and output tokens) plus one mergeable sketch each for queue time, time to first token and output tokens per second (a relative-error sketch such as DDSketch or a t-digest; the candidate should state its error). Hourly, daily and model-wide views are merges of these sketches, never averages of percentiles. Event-time windows with a watermark; late events update their own minute.
- **Low-volume honesty**: if a tenant's window has fewer than {{min_requests}} requests, the console shows the count, the median if meaningful, the maximum, and "not enough requests for p95/p99"; it offers a wider window that does meet the floor. For larger samples, a percentile is shown with an interval from order statistics (the binomial interval on the rank), so a tenant sees how uncertain a p99 from 120 requests is. The floor is enforced in the shared query layer, not in each client.
- **Noisy neighbours**: each replica emits per-second state: requests in flight per tenant, input tokens being prefilled per tenant, queue length. Detection: for each model, when other tenants' queue time or time to first token exceeds its baseline, compute each tenant's share of prefill tokens and in-flight slots on the affected replicas in the same seconds; a tenant whose share jumped and whose bursts precede the rise is the suspect. Confirmation: the effect follows the tenant across replicas and disappears when its traffic falls (or when a limit is applied). Model-wide view for tenants: their own latency next to the model-wide aggregate, never another tenant's.
- **Actions**: per-tenant, per-model limits on concurrency or input tokens per second (this exercise's rule), fair queuing at admission so one tenant's queue cannot block others, chunked prefill or long-context requests routed to a separate pool (described generally), and an offer of a dedicated endpoint to the heavy tenant. Every limit change is recorded with evidence and communicated to the tenant before or as it applies.
- **Isolation and retention**: tenant scope taken from the verified API identity and applied in the query layer; per-request records retained briefly for the tenant's own lookups; minute aggregates longer; per-replica state short.

**Competing designs to accept.** Fixed-bucket histograms (log-spaced) instead of sketches, if bucket error is stated. Client-reported timings as an optional second view. Detecting interference by comparing each tenant's latency with a model-wide baseline per replica instead of attributing shares, if the candidate shows how a cause is confirmed before acting. Separate pools by request size instead of per-tenant limits.

**Bottlenecks and failure modes.** Averaging percentiles; a percentile computed from a handful of requests; partitioning by tenant (hot partitions for the largest tenants); measuring only end-to-end latency so queueing and prefill cannot be told apart; blaming the largest tenant by default; limits applied without telling the tenant; one tenant's data visible through a misconfigured filter; alerts on processing time instead of event time.

**Incident guidance.**
- *Long-context bursts from one tenant raise everyone's time to first token*: the per-replica state shows the tenant's prefill share at 30% and queue time rising in the same seconds; confirm across replicas. Mitigate with that tenant's per-model token limit or routing its long requests to a separate pool, tell the tenant with the evidence and offer a dedicated endpoint; then add fair queuing and a standing interference alert. Do not penalise the tenant retroactively.
- *A p99 from 9 requests reached the console*: the floor of {{min_requests}} lived in the UI code and not in the API path. Correct the console, reply to the tenant with their actual counts and the wider-window view, and move the floor into the shared query layer with a test that every path enforces it.
- *Pipeline 25 minutes behind; alerts fire for a period that has ended*: alerts evaluated on processing time. Suppress alerts whose window closed beyond a staleness limit, mark the dashboard as lagging, evaluate on event time with the watermark, and scale or shed the aggregation work (sketch merges are cheap; per-request writes are not) so that a peak near {{peak_rps}} requests per second does not lag again.

**Follow-up guidance.** For 12 requests, the right answer is counts and a maximum, not a p99. For attribution, push for evidence of cause (per-replica shares and timing) and a confirmation step. For the tenant whose users see worse numbers, look for the network and client components that the server-side time excludes, and an offer to accept client timings.

**Rubric anchors.** 2: end-to-end latency per model, averaged percentiles, no tenant scoping, "the biggest tenant is the noisy one". 3: stage timings, sketches merged per tenant and model, a low-volume rule, per-tenant limits with communication. 4: also cause attribution from per-replica state with confirmation, intervals on percentiles, the floor enforced centrally, event-time alerting with lag awareness, and crisp handling of every incident.

**Strong signals.** Splits queue time from prefill unprompted; asks how many requests a tenant has before promising a p99. **Red flags.** Logging prompts "to debug latency"; ranking tenants against each other in a view other tenants can see; throttling without evidence.

## TGA-L4-02

**Reference architecture (one defensible design; score others on the criteria).**
- **Signals**: requests in flight and queued per replica, and tokens per second being generated, against a target the customer sets (for example in-flight requests per replica). Raw accelerator utilisation is a poor signal for inference (batching makes it high while requests still queue, and low while memory-bound work is busy).
- **Decision rule**: scale up when the projected demand over the next {{load_minutes}} minutes exceeds what ready plus starting replicas can serve at the target; scale down one replica at a time only after {{idle_minutes}} minutes with no requests in flight on it (this exercise's rule) and only if the remaining replicas stay under the target; never below the minimum or above the maximum. Hysteresis (different up and down thresholds) and a cooldown after each change stop flapping; the candidate should note that scaling down a replica that took {{load_minutes}} minutes to load and paying for it again shortly after is the cost to weigh.
- **Lifecycle events**: the replica controller emits `requested`, `started`, `ready`, `draining`, `stopped` with replica id, endpoint id, time and a monotonically increasing sequence, written transactionally with the controller's state change (an outbox) so a crash cannot record a state without its event or the reverse. Requested-but-not-started replicas are visible to the customer as waiting for capacity and are not billed.
- **Metering**: intervals from `started` to `stopped`; each interval expanded once into the UTC minutes it touches (floor of start through floor of stop), deduplicated per (replica, minute) so overlapping or repeated events never bill a minute twice. Daily totals per endpoint are exact integers; money = replica-minutes × versioned price in integer minor units, rounded once per invoice line.
- **Reconciliation**: every few minutes, compare the controller's list of running replicas with the meter's open intervals. A replica open in the meter but absent from the listing for two consecutive checks is closed at the last time it was seen alive (heartbeat or listing), and the correction is recorded; a running replica with no open interval opens one from its first observation and is flagged.
- **Idle view**: per replica-minute, whether any request was in flight (from request start and end times); per endpoint and day: billed replica-minutes, idle replica-minutes, idle share, and the cost of idle minutes above the minimum versus at the minimum. A recommendation compares the current minimum with the traffic pattern ("your second replica at minimum was idle 91% of this month").
- **Customer surfaces**: replica count over time with reasons for each change, waiting-for-capacity periods, billed minutes per day that sum to the invoice, idle share, and the settings in force at each moment.

**Competing designs to accept.** Scheduled scaling for predictable peaks, with its cost shown. Scaling on tokens per second or queue wait instead of in-flight requests. Billing computed from periodic heartbeats per minute (each heartbeat marks a minute running) if the candidate handles missing heartbeats and the started-minute rule. Scale-to-minimum faster with a warm pool, if they say who pays for the warm pool (not hidden in the customer's bill).

**Bottlenecks and failure modes.** Utilisation as the only signal; no allowance for load time, causing late scale-ups and flapping; billing from the autoscaler's intended state instead of what happened; lost stop events billed for hours; minutes double counted when start and stop fall in one minute or events repeat; idle cost computed from a different source than the bill; waiting replicas billed.

**Incident guidance.**
- *Endpoint cycles between 1 and {{max_replicas}} replicas 30 times a day*: the rule reacts to bursts shorter than load time plus the idle period. Correct the customer's bill for the day if the platform's rule caused it (the decision belongs to the billing owners, with the evidence); add hysteresis, a cooldown and a scale-down that considers recent burst frequency; show the customer the cost of their settings and offer a higher minimum or scheduled scaling.
- *Lost stop events, 140 replicas billed for up to 9 hours*: reconciliation should have closed them within minutes. Close each interval at the last time the replica was seen alive, restate the affected customers' minutes before invoices go out (or credit after), notify them, and make stop events transactional with the controller state plus continuous reconciliation with an alert on drift.
- *Customer idle at minimum all month disputes the invoice*: the bill follows the stated rule, but the customer had no visibility. Show the minute-level evidence and the idle share; whether to credit is a billing and account decision; ship the idle view and a proactive notice when an endpoint's idle share stays above a threshold.

**Follow-up guidance.** For one replica's life, expect the five events and the billed minutes computed from start and stop under the started-minute rule. For bursts, the candidate should compute rough cost: each cycle bills at least the load time plus the idle period for each extra replica. For waiting-for-capacity, look for no billing, visible state, and a cap on outstanding requests.

**Rubric anchors.** 2: autoscaling on utilisation, billing from the desired replica count, no idle view. 3: demand-based signals with load time considered, lifecycle events as the billing source, minute expansion done once, reconciliation, an idle view. 4: also hysteresis with cost reasoning, transactional events, exact integer totals that match the invoice, recommendations from idle data, waiting-for-capacity handled, and crisp handling of every incident.

**Strong signals.** Separates what the autoscaler wanted from what happened before talking about billing; computes the started-minute rule on an example. **Red flags.** Billing from heartbeats without handling gaps; floats for money; treating idle cost as the customer's problem.

## TGA-L4-03

**Reference architecture (one defensible design; score others on the criteria).**
- **Registry**: `adapter_version(id, endpoint, customer_name, base_model_version, rank, target_modules, size_bytes, checksum, uploaded_at)`; attach and detach are events with times. Attach checks the base model version, rank limits and checksum; a load re-checks compatibility, so an endpoint upgrade cannot serve an adapter trained for the old base. Names are labels: reusing a name creates a new version id.
- **Tiers**: object storage (all versions) → host memory on each replica (a larger cache) → {{slots}} accelerator slots. Each move is a load event `(adapter_version, replica, tier, start, end, reason, result)`.
- **Placement and routing**: a router keeps which replicas hold which adapters in accelerator memory and in host memory. A request goes to a replica already holding its adapter (least loaded among them); if none, to the replica with the cheapest load (adapter in host memory) and lowest load. Hot adapters (by recent request rate) are replicated to more replicas; a request may be sent to a replica that does not hold the adapter if all holders are overloaded, accepting a cold load.
- **Eviction**: frequency with ageing plus recency as a tie-break (or a segmented policy that protects adapters seen repeatedly from one-off bursts), with customer pinning limited to a stated share of slots. When the working set exceeds slots × replicas, the report says so and recommends more replicas or fewer active adapters.
- **Cold-load measurement**: a request is cold if its adapter was not resident when it was scheduled; its cold wait is the overlap between its queue time and the load event it waited for. Requests queued behind a load on the same replica are marked as delayed by a load. Warm and cold latencies are reported separately.
- **Detach and replace**: detach marks the version as detached; the router stops sending new requests; in-flight requests complete; later requests for that name get a documented error unless a new version is attached under the name, in which case routing uses the new version id from the moment of attach.
- **Reports**: per adapter version per day: requests, input and output tokens, errors, warm and cold time to first token percentiles (sketches), number of loads; the customer's names shown beside ids. Totals across adapters plus the base model reconcile with endpoint totals. Billing remains replica-minutes for the endpoint (this exercise's rule).

**Competing designs to accept.** Static sharding of adapters across replicas (each replica owns a subset) with replication for hot ones, if rebalancing is described. Pure LRU with a protected segment. Loading adapters into accelerator memory on demand without host-memory caching, if load times are measured and acceptable. Batching only same-adapter requests, with the throughput cost named.

**Bottlenecks and failure modes.** Round-robin routing that makes most requests cold; eviction thrash when the working set exceeds slots; one-off bursts evicting steady adapters; adapters attached for the wrong base version; reports keyed by name that merge versions; cold waits not attributed, so the customer blames the adapter.

**Incident guidance.**
- *Even spread over {{adapters}} adapters, 45% cold*: the working set exceeds {{slots}} slots × {{replicas}} replicas. Short term: route by adapter affinity and stop replicating rarely used adapters; tell the customer which share is cold and why; recommend more replicas or a tier of adapters on another endpoint. Prevention: a working-set metric with an alert before thrashing, and an admission rule for bursts of one-off adapters.
- *Incompatible adapter after an upgrade*: compatibility was checked only on attach. Detach it with a clear error to the customer, add a re-check at load and at endpoint upgrade (block the upgrade or warn about every incompatible adapter), and alert on repeated load failures within minutes.
- *Report merged two versions with one name*: the report was keyed by name. Re-key by version id, regenerate the day's report, tell the customer exactly how the split changes, and show names beside ids.

**Follow-up guidance.** For the unheld adapter, expect a route decision, a load event, a cold wait and a report entry. For the 40% adapter, look for replication to more replicas and the speed of reaction. For sizing, a working-set calculation from traffic concentration.

**Rubric anchors.** 2: one cache per replica with LRU and random routing, reports by name. 3: registry with versions and compatibility, affinity routing, frequency-aware eviction, cold loads measured. 4: also hot-adapter replication, burst resistance and pinning limits, cold waits attributed from load events, versioned reports that reconcile with endpoint totals, and crisp handling of every incident.

**Strong signals.** Computes the cold share for a routing choice; keys everything by version id. **Red flags.** Inspecting adapter weights to diagnose; billing per adapter as if the endpoint were not already billed by replica-minutes.

## TGA-L4-04

**Reference architecture (one defensible design; score others on the criteria).**
- **Inventory and lineage**: `artefact(id, tenant, kind, created_at, retention_policy, state)` and `copy(artefact_id, location, kind, created_at, deleted_at, verified_at)`; every writer (upload, regional replication, backup, training node cache, endpoint load, download export) registers a copy before using it. Lineage edges: dataset → job → checkpoints → model or adapter → endpoint deployments.
- **Encryption**: each artefact (or each tenant's artefacts, with per-artefact data keys wrapped by a tenant key) encrypted with its own key in a key service; training nodes and endpoints receive keys only for the job or deployment. Destroying an artefact's data key makes every copy unreadable, including immutable backups and any stray copy.
- **Retention**: checkpoints expire {{retention_days}} days after the job ends unless kept; expiry uses the same deletion workflow.
- **Deletion workflow**: states requested → blocked (for example the model is deployed: the customer chose to undeploy as part of the delete, with confirmation) → keys destroyed → copies removed (regional copies, caches, exports) → verified (each copy's location checked absent; backups covered by key destruction) → receipt issued, within {{deletion_days}} days. The receipt lists artefact ids, copies and locations, times, the key destruction time, what is retained (billing records, job metadata with counts, the receipt itself) and why; it is signed so the customer can verify it later. Deleting a dataset shows the models trained from it and asks whether to delete them too.
- **Training nodes**: caches live in an encrypted scratch area with a per-job key; the key is discarded when the job ends or the node is reclaimed, and a sweeper on every node deletes scratch for jobs that are no longer running, reporting to the inventory.
- **No human access**: contents readable only by the validator and training workloads' identities; no console, support or engineering role can read them; every key use is logged; validation output schema allows only counts, line numbers, error codes and field names, and is tested to contain no customer text.
- **Support**: sees validation results, job configs, states and logs that carry no content; can offer the customer a local validator or extra named checks that report counts only.

**Competing designs to accept.** Per-tenant keys instead of per-artefact keys (simpler; deleting one artefact then relies on removing its copies and on backup expiry, which must fit within {{deletion_days}} days or be made to). Backups excluded for customer artefacts with durability from regional copies instead. Synchronous deletion with a background verifier.

**Bottlenecks and failure modes.** Copies made without registration (caches, exports, debug dumps); deleting the primary and forgetting replicas and backups; receipts issued before verification; a key service restore resurrecting destroyed keys; validator errors that echo content; deleted datasets surviving in derived files; support given read access "temporarily".

**Incident guidance.**
- *Tokenised caches of 300 deleted datasets survived on node disks*: crashed jobs skipped clean-up. Delete the caches now, verify, and correct the receipts that were issued too early (tell those customers plainly); fix: register caches as copies, per-job scratch keys discarded on job end, and a node sweeper independent of the job; receipts wait for verification of every registered copy.
- *Storage restore brought back 1,100 deleted datasets*: if their keys were destroyed, the restored objects are unreadable; delete them again and verify. If keys were not destroyed (per-tenant keys only), treat it as a breach of the deletion promise: delete, verify, inform affected customers, and replay the deletion log after any restore as a standard step.
- *Validator echoed line content*: stop the change, purge the messages from logs and console storage, determine which customers' content was exposed and to whom, tell them, and add an output-schema test that rejects any free text from input.

**Follow-up guidance.** For the dataset with three jobs, look for lineage shown to the customer and an explicit choice about the deployed adapter. For proving no human read a dataset, key-use logs and access policy, not promises. For "delete everything today", expect key destruction today (contents unreadable at once) and physical removal within {{deletion_days}} days.

**Rubric anchors.** 2: delete the object in primary storage and send an email. 3: an inventory of copies, retention and expiry, a deletion workflow across copies with a receipt, no human access. 4: also per-artefact or per-tenant keys for backups and stray copies, verified receipts, lineage-driven choices for derived models, a validator that cannot echo content, and crisp handling of every incident.

**Strong signals.** Asks where copies are made before designing deletion; treats the receipt as a verified claim. **Red flags.** Support reading datasets "to help"; receipts sent on request receipt; "backups are out of scope".

## TGA-L4-05

**Reference architecture (one defensible design; score others on the criteria).**
- **Pipeline with gates**: intake (download the publisher's public release, verify checksums and the publisher's revision, record the published licence and model card fields) → conversion (serving variants, precision choices, tokenizer and chat template packaged with them) → acceptance (tokenizer round-trips, chat template rendering for system, user, assistant and tool turns, deterministic outputs for fixed seeds, context length at its limit, throughput and latency targets on the serving variant, and a check against public evaluation sets with expectations set by this exercise) → review (licence recorded and reviewed by legal and product owners; the pipeline only blocks until the review is recorded) → pricing (price version set by owners) → release (version id published, aliases updated by a separate, explicit step). Each gate records durations, so the {{onboard_days}}-day target is measured and its slow step known.
- **Catalogue record**: `model_version(id, family, publisher_revision, variant, context_length, tokenizer_hash, template_hash, licence_ref, availability, state, deprecated_at, retire_at, replacement_id)`; aliases `(alias, version_id, valid_from, moved_by, reason)`. The API model list, documentation, pricing pages and billing read this record; nothing is typed twice.
- **Requests**: each request records the alias used (if any) and the resolved version id, so migration and incident questions are exact.
- **Deprecation**: states active → deprecated (announced, with retire date ≥ {{notice_days}} days later and a named replacement) → retired. Notices go to the contacts each tenant chose for technical notices, and delivery and opens are tracked; tenants without a reachable technical contact are flagged for outreach. Responses to deprecated versions carry a header or field saying so. Optional brownouts (short scheduled error windows) before retirement, announced in the notice. After retirement, requests get a documented error naming the replacement (or a redirect if the candidate argues for it and announces it).
- **Migration reporting**: per tenant and week: requests to the deprecated version, first call to the replacement, share moved; aggregate views for the platform; tenant-scoped self-service ("your calls to versions that will retire"); outreach lists for large tenants and automated reminders for the long tail.
- **Rollback**: a bad release is rolled back by moving aliases back (with history) and marking the version deprecated or withdrawn; tenants who pinned the version are told and offered the previous one; versions are never edited in place.

**Competing designs to accept.** Aliases that never move automatically (tenants must opt in), at the cost of slower adoption. A preview tier before general availability. Redirect on retirement instead of an error, if output differences are announced and measured. Licence review before conversion rather than in parallel.

**Bottlenecks and failure modes.** A version id whose contents change; aliases moved silently on release day; notices to contacts nobody reads; template and tokenizer bugs not tested; the model list, docs and prices maintained separately; retirement measured only by total traffic, hiding tenants who never moved; licence decisions made by the pipeline instead of the owners.

**Incident guidance.**
- *Chat template drops the system turn*: roll the affected version back or publish a corrected version with a new id, move the alias, and tell affected tenants which requests were affected (from request records). Prevention: acceptance tests that render every turn type and compare with the publisher's reference template output.
- *Alias moved on release day, 60 tickets*: tenants used the alias without knowing it moves. Move it back if the new version breaks formats; announce alias moves in advance with a date; show the resolved version in every response and in the console; recommend exact versions for production.
- *400 tenants still on the version on retirement day; 150 never saw a notice*: delay retirement for those 150 if the owners agree, since the notice period of {{notice_days}} days was not actually delivered; reach them through technical contacts and in-response warnings; fix contact selection and track delivery.

**Follow-up guidance.** For the release path, look for gates that run in parallel (conversion and licence review) and a measured slow step. For the tokenizer fix, a new version id and an announced alias move. For rollback, alias history and no in-place edits.

**Rubric anchors.** 2: models added by hand, versions mutable, deprecation by email. 3: a staged pipeline with acceptance checks, immutable versions and aliases, deprecation with notice and replacement, per-tenant migration reports. 4: also measured gates against the target, alias history with resolved versions on every request, verified notice delivery and in-response warnings, one record for API, docs and billing, licence review owned by the right people, and crisp handling of every incident.

**Strong signals.** Insists on immutable versions and resolved version ids before talking about deprecation. **Red flags.** "The latest alias always points to the newest model, automatically"; the pipeline deciding licence questions; deprecation success measured only by total traffic.
