# LinkedIn · Loop 4 — evaluator notes (hidden from candidates)

These are simulated scenarios. Score the candidate on sound design for a
professional network's public product domain, never on guesses about how any
company builds its search, ranking, notification or analytics systems. Ranking
is a scoring function the candidate is given. Penalise any design that infers
protected traits, uses member data beyond the member's visibility settings, or
shows anyone member-level data they would not see in the product.

## LNK-L4-01

**Reference architecture (one defensible design; score others on the criteria).**
- **Source of truth**: the posting service stores each posting with `posting_id, employer_id, source, external_job_id, status (open | closed), version, published_at, first_published_at, content…`. Every write increments `version` and emits a change event `(posting_id, version, op, payload)` to a log partitioned by `posting_id`, so all changes to one posting stay ordered.
- **Ingestion**: the posting form writes directly. Feeds are parsed into the same write API; a delta feed maps to upserts and closes; a full file is diffed against the employer's last accepted file. A **shrink guard** holds a file whose open-count falls by more than a set fraction (for example 20%) against the previous file and the employer's history, and asks the employer to confirm, instead of closing everything missing.
- **Normalisation (versioned steps)**: places resolved to place ids with coordinates and the containing region and country; remote eligibility as a list of countries; pay normalised to an annual range in a reference currency with the rate's date and the hours-per-year assumption stored, converted to the searcher's currency at query time; seniority and title to standard values. Each step stores its output and its version so a fix can be replayed.
- **Duplicates**: key on `(employer_id, external_job_id)` where available, otherwise a content fingerprint (normalised title, employer, location, description shingles). The canonical copy is the employer's own source; agency copies are linked and hidden, or shown once with the source named.
- **Index**: an inverted index with filterable fields (place ids at several levels, geo points for radius, workplace type, remote countries, seniority, pay range as min/max, posting status, version). A posting with several locations gets one document with multi-valued location fields (or one document per location with a group id to collapse results). Retrieval applies filters and returns a few thousand candidates; the given scoring function orders them.
- **Incremental updates**: the indexer consumes the change log and applies a change only if its version is newer than the indexed version (compare-and-set per document), so out-of-order delivery cannot resurrect old content. Closures go on a **priority path** (a separate topic or a priority lane) and are applied as deletes or a status flip; until segments merge, a small in-memory "recently closed" set is filtered at query time.
- **Full rebuild**: take a consistent snapshot of the posting store at log position P, build the new index offline, replay the log from P until the new index is within seconds of live, then switch traffic; keep the old index until the new one is verified (document counts, sample queries).
- **Serving and regions**: each region's replica consumes the same log; per-region lag is a first-class metric. A region whose lag exceeds the freshness target fails over its queries to another region or at least filters by a globally replicated closed-set.
- **Apply guard**: the apply button and the application API always check the posting store's status, so a stale results page can never submit an application to a closed posting; the member is told it closed.
- **"Posted" label**: shows `first_published_at` for the job (carried across reposts of the same external job id within a stated window), with a separate "reposted" marker; edits never reset it.
- **Freshness measurement**: every posting's publish time and its first-visible time per region are recorded (the indexer writes the time it applied version v; a synthetic canary posting per region is published and searched every minute). Dashboards show p50/p95 publish-to-searchable and close-to-gone per region and per source.

**Competing designs to accept.** One document per location with result collapsing instead of multi-valued fields. A search engine with near-real-time refresh plus a nightly rebuild, or no full rebuild at all if the candidate shows how they recover from index corruption. Excluding postings without pay when a pay filter is set, or including them with a "pay not stated" marker, if the choice is explicit to members.

**Bottlenecks and failure modes.** Bulk edits starving closures in one queue; full files that are partial; reposts or edits presented as new jobs; stale exchange rates; out-of-order updates resurrecting old content; regions drifting behind with no visibility; apply paths that trust the index.

**Incident guidance.**
- *Partial feed closes 120,000 postings*: stop applying that feed, restore the closed postings from the posting store's history (the closes are versioned writes, so reopen them with new versions and the original `first_published_at`), and tell the employer. Prevention: the shrink guard with employer confirmation, and a per-feed alert on a sudden fall in open count.
- *Bulk edit backs up the stream; closures delayed*: closures must not queue behind edits. Short term: drain closures first (separate lane or priority), and scale the indexer; the apply guard already stops applications to closed jobs, so confirm it held. Prevention: priority lanes, per-employer rate limits on bulk edits, and alerting on close-to-gone lag, not just average lag.
- *Every edit treated as a new posting*: a pipeline change reset the published date. Recompute labels from the stored first-published time, fix the rule so only a new external job id (or a repost after the window) is new, and add a test that an edit keeps the label. Count how many postings were mislabelled and for how long.
- *Exchange rates stale for nine days*: pay filters used old rates, so overlapping postings fell outside the filter. Re-run normalisation for affected postings with correct rates (the stored rate date makes them findable), alert on rate freshness, and fail safe: when rates are stale beyond a bound, widen the filter or show a "pay converted at an older rate" notice rather than excluding silently.

**Follow-up guidance.** Make the candidate trace a closure end to end and name every place the closed posting can still be seen (cached pages, each region's replica, alert emails). Push on the version compare-and-set and the rebuild replay from a snapshot position. For filters, insist on explicit semantics for missing pay and multiple locations.

**Rubric anchors.** 2: one nightly rebuild, or an index written directly by the form with no ordering, no story for closures. 3: versioned change log, incremental indexing with ordering, closures as deletes, a rebuild that converges, apply-time checks, explicit filter semantics, per-posting freshness measurement. 4: also priority lanes for closures, a shrink guard on feeds, honest "posted" labels across reposts and edits, per-region lag with automatic failover, replayable normalisation with stored rate dates, and precise handling of every incident.

**Strong signals.** Starts by asking which change is most harmful when late (closures) and designs for it. **Red flags.** "Search engines are near-real-time, so it is fine" with no measurement; trusting the index at apply time; closing every posting missing from a file.

## LNK-L4-02

**Reference architecture (one defensible design; score others on the criteria).**
- **Send path**: the invitation service checks a per-sender counter before accepting. The counter lives in a replicated key-value store keyed by sender, as a rolling window (for example per-day buckets for the last seven days summed, or a calendar week with a stated reset). The check-and-increment is one atomic conditional operation, so concurrent sends from several devices cannot exceed the limit. If the counter store is unavailable, fail closed for senders already flagged and fail open with a conservative local cap for others, and record every send in the durable invitation log so the counter can be rebuilt. Per-recipient protection: a separate counter of invitations received from new or low-trust senders per recipient per day, with a lower threshold.
- **Durable log**: every invitation and every outcome (accepted, ignored, "don't know", reported, withdrawn, expired) is an event in a log keyed by invitation id. This is the source for aggregates and for rebuilding counters.
- **Aggregate signals per sender** (computed hourly in a stream job and daily in batch): invitations sent in 1 day / 7 days; resolved outcome rates over invitations that have been answered or are older than N days (so pending invitations do not depress new members' rates), smoothed toward a population prior with a pseudo-count (Bayesian average); "don't know" and report rates per resolved invitation; withdrawal rate; share of invitations to members with no prior interaction of any kind recorded by the product (a coarse signal, not a graph analysis); account age, verification status, profile completeness. Cross-account signals: accounts created from the same network or device cluster in a short window, similar sending patterns, the same malicious link in notes; shared networks such as universities and large employers are discounted via known-network lists and by requiring several independent signals.
- **Decision layer**: a rule set or a model with thresholds produces an action ladder: no action → in-product nudge ("many of your invitations go unanswered; add a note") → lower weekly limit for 14 days → temporary invitation restriction with review → account review. Each action records the signals and thresholds behind it (explainable), the version of the rules, and an expiry. Automatic actions stop at lower limits; restrictions need a high-confidence rule or a reviewer.
- **Appeals and review**: a queue prioritised by impact (accounts with long history, verified members, restrictions first) and by confidence (borderline scores); reviewers see the aggregates and the action's reasons, not private messages. An appeal outcome becomes a label.
- **Measuring false positives**: appeal overturn rate, plus a small random sample of actioned accounts reviewed regardless of appeal (most people never appeal), plus a holdout of borderline accounts where only a nudge is applied, to estimate what enforcement prevents. Alert when the action rate moves without a matching move in reports from recipients.
- **Privacy**: only counts, outcomes and account or security signals; no message content beyond matching links against a malicious list; no protected traits and no proxies for them; signals are retained for a bounded period.

**Competing designs to accept.** A pure rules system first, with a model added later once appeal labels exist. Token-bucket limits instead of weekly windows. Enforcement that asks the sender for more friction (for example, adding a note, or confirming how they know the person) instead of lowering limits, if justified.

**Bottlenecks and failure modes.** Counter stores that fail open; outcome rates dominated by pending invitations; product changes that shift signals; legitimate bursts (events, recruiters) looking like abuse; rings that stay below per-account limits; review queues that cannot keep up.

**Incident guidance.**
- *Careers fair: 8,000 restricted*: pause automatic restrictions for the rule that fired, lift the restrictions in bulk for accounts with no reports, and tell those members. Root cause: rates computed from pending invitations and no allowance for event bursts. Prevention: only resolved or aged invitations in rates, smoothing, a burst rule that requires reports or "don't know" signals, and capacity planning for appeals (bulk reversal tools).
- *Ring of 30,000 accounts under the limit*: per-account limits cannot catch it; cross-account signals can (creation clusters, shared infrastructure, similar timing, identical notes or links). Act with lower limits for the cluster, review a sample, and restrict the high-confidence core. Prevention: new-account limits that grow with positive outcomes, and recipient-side counters.
- *Counter replica two hours behind*: the counter failed open. Rebuild counters from the durable log, apply temporary limits to senders who exceeded, and change failover so a lagging replica is not promoted for limit checks without reconciling from the log. Alert on counter-versus-log divergence.
- *"Don't know" presses double after a UI change*: the signal's meaning changed, not behaviour. Freeze or recalibrate the affected signal, reverse warnings issued since the change, and require product changes that touch a signal's source to notify its owners; monitor action rates against recipient reports so drift is caught in hours.

**Follow-up guidance.** Make the candidate define the outcome rate precisely (denominator, pending invitations, smoothing). Probe the counter's failure mode and multi-device races. On rings, push for signals that do not flag a whole campus. On false positives, insist on something better than appeal rates.

**Rubric anchors.** 2: a fixed limit and "ban accounts with low acceptance rates". 3: atomic counters on the send path, defined and smoothed aggregate signals, an action ladder with appeals, cross-account detection, no content reading. 4: also a stated counter failure mode with rebuild from a log, recipient-side protection, false positives measured by sampled review and holdouts, drift monitoring for product changes, discounting of shared networks, and precise handling of every incident.

**Strong signals.** Says early that most heavy senders are legitimate and designs the ladder around that. **Red flags.** Reading private messages; using demographic or protected attributes; automatic permanent bans; rates computed without a minimum count.

## LNK-L4-03

**Reference architecture (one defensible design; score others on the criteria).**
- **Stores**: subscriptions `(member_id, newsletter_id, status, mode: per_issue | daily_digest | weekly_digest, updated_at, version)`; member channel preferences and quiet hours with a time zone; an unsubscribe from any channel writes the same subscription row (one source of truth), so every channel reads the same state.
- **Publish**: an issue gets `issue_id`, `newsletter_id`, `published_at`, and optionally `corrects_issue_id`. A fan-out job enumerates subscribers in partitions (for example by hash of member id) and emits one **delivery intent** per (issue, member). Large newsletters run in their own lane with their own worker share so small newsletters are not delayed behind them.
- **Per-member scheduler**: each intent goes to a per-member queue (partitioned by member). At send time the scheduler re-reads subscription status and preferences (not the state at fan-out), applies quiet hours in the member's settings time zone, the daily cap of notifications, and digest mode (intents for digest members are added to the next digest). If the member already opened the issue in the app (a read event keyed by issue and member), the email is skipped; the read event can arrive late, so the email can wait a short window for read signals if the product wants that.
- **Ordering**: a correction intent is held until the original issue's intent for that member has been sent or superseded; a simpler rule is to send only the latest version of an issue to members not yet reached, and a correction only to members who received the original.
- **Sending**: every send has an idempotency key `(issue_id, member_id, channel)` recorded before the provider call; retries reuse it, and the send log marks the outcome. Email goes through providers with per-domain rate limits and backoff; transactional mail (password resets) uses a separate sending stream and reputation so newsletter problems cannot block it.
- **One-click unsubscribe**: the email link carries a signed token (member, newsletter) that updates the subscription row directly, effective for every channel before the next send.
- **Metrics for authors**: observed: issues sent, accepted by provider (delivered), bounced, clicks through the network's own tracked links, reads in the app, unsubscribes, new subscribers. Estimated: email opens, labelled as an estimate with a note about automatic image loading; the platform may exclude opens identified as automatic loads or report "opens" and "estimated human opens" separately. Authors see aggregates only; breakdowns (for example by subscribers' industry or region) only for groups above a minimum size, with no protected traits and no per-member lists.

**Competing designs to accept.** Push-based fan-out into per-member inbox rows versus computing a member's pending notifications at read time; for very large newsletters a hybrid (pull for in-app, push for email). A single channel per issue chosen by a per-member preference, if the candidate shows how they decide.

**Bottlenecks and failure modes.** Large fan-outs starving small ones; preferences cached at fan-out; per-channel preference stores that disagree; retries that duplicate; provider throttling that spreads to critical mail; open metrics distorted by clients; corrections overtaking issues.

**Incident guidance.**
- *Unsubscribe updated email only*: preferences were split by channel. Fix the write path so every unsubscribe updates the one subscription row; find members who unsubscribed through the email link in the affected period and apply it to all channels; apologise where they were notified again. Prevention: a test that an unsubscribe from each entry point stops every channel, and a check at send time.
- *Correction arrived before the original*: the original's fan-out was slow and the correction ran in a different lane. Hold corrections per member until the original is sent, or send members not yet reached only the latest version. Also: speed the large fan-out (more partitions, dedicated lane) and monitor time-to-last-delivery per issue.
- *Opens up 25 points overnight*: a mail client began loading images automatically. Annotate the dashboards, separate likely automatic opens (by client signature, open within seconds of delivery) from others, and steer authors toward observed metrics (clicks, reads). Do not "fix" the number silently.
- *Triple sends to 400,000 members*: retries were not idempotent. Stop the job, record idempotency keys before provider calls, and apologise if the volume warrants it. Move password resets and other critical mail to a separate stream and reputation so a newsletter problem can never throttle them; monitor complaint rates per stream.

**Follow-up guidance.** Make the candidate show exactly when preferences are read. Push on idempotency keys across a provider timeout. Ask for a precise open-rate definition and what is estimated. Ask how a breakdown avoids identifying one subscriber.

**Rubric anchors.** 2: loop over subscribers and send emails; open rate from the pixel taken at face value. 3: partitioned fan-out with idempotent sends, preferences read at send time, unsubscribe across channels, caps and digests, observed versus estimated metrics, aggregates for authors. 4: also lane isolation for large newsletters, ordering of corrections, separate streams for critical mail, cross-channel deduplication with its latency, minimum group sizes for breakdowns, and precise handling of every incident.

**Strong signals.** Treats the unsubscribe as the one promise that must never break. **Red flags.** Per-member open data shown to authors; preferences checked only at subscription time; one shared mail stream for everything.

## LNK-L4-04

**Reference architecture (one defensible design; score others on the criteria).**
- **Events and keys**: posting views `(view_id, posting_id, member_id or anonymous id, source, ts)`; applications `(application_id, posting_id, member_id, applied_via: onsite | offsite_click, ts)`; promoted clicks `(click_id, posting_id, campaign_id, ts, cost, validity)`; tracking-system updates `(employer_id, external_application_id, status, status_ts, received_at, integration_version)` mapped to platform statuses by a versioned, per-system mapping table.
- **Journey facts**: one row per (posting, member) applicant journey with touches (source, ts) before the application; outcome history as an SCD-style table of statuses with effective and received times. A hire is a journey whose latest status as of a date is "hired".
- **Attribution**: a written, versioned rule, for example position-based or last non-direct touch within a window, plus a "touched by" view (every source that touched the journey) so employers can see both "credited" and "assisted". The dashboard names the rule and version.
- **Spend**: a billing ledger of charges and later credits (invalid clicks) by campaign and day; invoices reference ledger entries. Analytics read the same ledger, so spend shown equals invoiced amount minus credits, with credits dated when issued and also attributed back to the original day for "as-of today" views.
- **Reporting as of a date**: reports are computed with an as-of parameter. Exports record their as-of time and can be reproduced; the dashboard shows "figures as of today" with a marker that recent cohorts are still maturing (hires arrive up to the tracking-system lag). Cohorts by application date make late outcomes land in the right period.
- **Status mapping quality**: per integration, expected distributions (hire rate per application, time to hire) with alerts when a mapping change shifts them; a new integration version runs in shadow before it counts.
- **Privacy**: tenant isolation by employer id in every table and query; breakdowns of applicants or viewers only for cells of at least the minimum size, over a fixed set of dimensions and hierarchies, with complementary suppression (suppress enough cells that differences cannot reveal a small group) or noise added to small counts; no protected traits; non-applicant viewers never listed. Peer benchmarks: medians or percentiles over at least ten employers, with no employer contributing more than a set share. Member deletion: journey rows are anonymised or removed within the deadline and aggregates recomputed; benchmarks already published are recomputed on the next cycle.
- **Serving**: a columnar warehouse with pre-aggregated cubes per employer and day for the dashboard, and a governed export.

**Competing designs to accept.** Multi-touch fractional attribution instead of a single credited source, if explained to employers. Differential-privacy noise on breakdowns instead of suppression. Real-time dashboards for views and applications, daily for outcomes.

**Bottlenecks and failure modes.** Status mappings that break silently; late outcomes shifting closed periods; spend and invoices diverging after credits; differencing across reports; redirect changes that lose source attribution; deletion that misses aggregates.

**Incident guidance.**
- *"Rejected" mapped to "hired"*: quarantine that integration's updates, revert to the previous mapping version, restate affected journeys, and notify the 30 employers that cost-per-hire figures were wrong for the period, especially the two who changed budgets. Prevention: shadow runs for new integration versions and distribution alerts on hire rate.
- *Differencing reveals two people*: the two reports passed the minimum separately. Restrict breakdowns to fixed hierarchies with complementary suppression (or noise), track which cells an employer has already seen, and remove the export option for small groups. Treat it as a privacy incident: assess, notify per policy, and fix before re-enabling.
- *Invalid-click credits after invoicing*: spend must come from the ledger. Show credits as separate lines dated when issued, keep "as invoiced" and "after credits" views, and recompute cost per application from the same ledger in both export and dashboard.
- *Referral parameter dropped by a redirect*: applications were misattributed to "direct". Detect with source-mix monitoring; fix the redirect; backfill attribution from server-side referrer data where available and label the rest as unknown rather than direct. Note that the effect on hires shows up only over the tracking-system lag.

**Follow-up guidance.** Ask for the grain of the journey table and how a late status lands. Push on a restatement policy employers can trust. Probe differencing with two concrete reports. Ask how spend in the dashboard equals the invoice.

**Rubric anchors.** 2: one big table joined at query time; last click wins without saying so; minimum counts per report only. 3: journey facts with touches, outcome history with as-of reporting, a stated attribution rule, ledger-based spend, tenant isolation, minimum group sizes, deletion propagation. 4: also versioned status mappings with shadow runs and distribution alerts, reproducible exports, protection against differencing, safe peer benchmarks, and precise handling of every incident.

**Strong signals.** Treats the tracking-system mapping as a data contract with tests. **Red flags.** Showing employers members who viewed but did not apply; demographic breakdowns by protected traits; cost per hire that silently changes past invoices.

## LNK-L4-05

**Reference architecture (one defensible design; score others on the criteria).**
- **Taxonomy as data**: `skill(skill_id, canonical_name, labels per language, parent, status, introduced_in, retired_in)` with ids never reused; `release(release_id, published_at)`; `skill_change(release_id, kind: add | split | merge | retire | relabel, from_ids, to_ids, rule)`. A release is the set of active skills at that release.
- **Crosswalk**: derived from change records: for each (old_id, new_release) the mapping to new ids, with a rule: merges are 1→1; splits are 1→n with either assignment per member from what the member themselves wrote (the original string, position titles and descriptions on their profile), a prompt asking the member to choose, or a "stay on the parent" fallback, plus population weights for reports when per-member assignment is not possible. Assignment never draws on behaviour the member did not choose to share as a skill.
- **Mappings**: `member_skill(member_id, entered_text, language, entered_at, removed_at)` stays as the member wrote it; `skill_mapping(text_norm, language, skill_id, release_id, method: dictionary | model | curated, confidence)` maps strings; the member's mapped skill is a join, never a copy written over their text. Low-confidence or ambiguous strings stay unmapped or go to curation; curated mappings override the model.
- **Consumers**: matching, course tagging and reports each declare the release they use; a new release is adopted within a migration window (for example two releases), and the platform serves mappings for any supported release. Matching between consumers on different releases goes through the crosswalk.
- **Removals**: a removal event updates the matching index incrementally (not only on release), within a day.
- **Trend reports**: each report states its release; history is restated into that release through the crosswalk, so a split does not look like a collapse. The release's own effect is measured by computing the same month under the old and new release and reporting the difference. Cells need at least 100 members; no protected traits; suppression or noise for small cells.
- **Quality**: per language, curated samples of mappings audited each release; alert on large mapping changes for high-volume strings; shadow-run new model versions and diff their mappings before release.

**Competing designs to accept.** Hierarchical reporting at the parent level for comparability, with children shown only from their introduction. Freezing reports at publication and publishing a bridge table instead of restating. Model-only mapping with human review of the head of the distribution.

**Bottlenecks and failure modes.** In-place updates that rewrite history; splits with no evidence; consumers pinned to different releases; release effects read as trends; wrong mappings for common strings; removals waiting for a release.

**Incident guidance.**
- *Split shows parent falling 70%*: the report did not restate history through the crosswalk. Republish with the parent's history mapped onto the children (or report at the parent level), annotate the release, and add a release-effect check that computes the same month under both releases before publishing.
- *Wrong mapping for a common abbreviation*: revert the mapping (curated override), recompute affected matches, notify affected members only if they were visibly affected, and tell recruiters' tools to refresh. Prevention: diff new mappings for high-volume strings per language, audit samples, and treat abbreviations as ambiguous by default.
- *Course tagging one release behind*: the merge removed the old id from the new release, and course tags were on the old one. Serve mappings through the crosswalk for pinned consumers, and require consumers to adopt within the migration window, with alerts on consumers falling behind.
- *Removed skills matched for nine days*: removals depended on the release snapshot. Make removals incremental events into the matching index with a freshness metric, and backfill the nine days.

**Follow-up guidance.** Make the candidate walk a split end to end with numbers. Ask how a report proves a trend is behaviour, not a release. Probe the member-facing promise: what the member sees never changes without their action.

**Rubric anchors.** 2: one skills table updated in place; trend reports on the latest taxonomy only. 3: stable ids, releases with change records, crosswalks, member text separate from mappings, reports in a stated release with restated history. 4: also evidence-based or explicitly ambiguous split handling, release-effect measurement, consumers pinned with migration windows, mapping audits per language, incremental removals, aggregate privacy, and precise handling of every incident.

**Strong signals.** Asks "comparable to what?" before designing reports. **Red flags.** Rewriting members' profile text; reusing ids; inferring skills a member did not choose and showing them as the member's own.
