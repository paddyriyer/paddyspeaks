## UBR-L2-01

**Reference solution**

```python reference
def smooth_surge(cells, k, cap, prev=None, max_step=None, weighted=False):
    raw = {}
    for cell, (demand, supply) in cells.items():
        if demand <= supply:
            raw[cell] = 100
        elif supply == 0:
            raw[cell] = cap
        else:
            raw[cell] = min(cap, 100 * demand // supply)
    # every axial offset within hex distance k, with its weight
    ring = []
    for dq in range(-k, k + 1):
        for dr in range(max(-k, -dq - k), min(k, -dq + k) + 1):
            d = (abs(dq) + abs(dr) + abs(dq + dr)) // 2
            ring.append((dq, dr, k + 1 - d if weighted else 1))
    out = {}
    get = raw.get
    for (q, r) in cells:
        s = w = 0
        for dq, dr, wt in ring:
            v = get((q + dq, r + dr))
            if v is not None:
                s += wt * v
                w += wt
        v = (2 * s + w) // (2 * w)                 # round half up, in integers
        if prev is not None:
            p = prev.get((q, r), 100)
            v = min(max(v, p - max_step), p + max_step)
        out[(q, r)] = min(max(v, 100), cap)
    return out
```

**Explanation.** Three passes. First every raw multiplier, once. Then, for each cell, the fixed list of axial offsets within distance `k` (3k(k + 1) + 1 of them: 7 for k = 1, 19 for k = 2, 37 for k = 3), each one a dictionary lookup, summing weight × raw over the cells that have data. The average is rounded half up with integers only: `(2S + W) // (2W)`. Finally the step limit around the previous value (100 when the cell is new), then the 100 and `cap` bounds. The offsets are generated by bounding `dr` so that `|dq + dr| ≤ k`, which gives each offset exactly once.

**Complexity.** O(N · k²) time for N cells, O(N) memory. The timing check is about 52 000 cells with k = 3: roughly 1.9 million lookups, under a second in CPython. Comparing every pair is about 2.7 billion distance checks.

**Dialect notes.** In SQL this is a self-join of the cell table to an offsets table (`JOIN offsets o ON TRUE JOIN cells n ON n.q = c.q + o.dq AND n.r = c.r + o.dr`) followed by `GROUP BY c.q, c.r`. In Spark the same join broadcasts the small offsets table. Libraries for real hexagonal indexes provide a "grid disk" or k-ring function that returns the neighbouring cell ids directly. Not executed here.

**Edge cases built into the tests.** Demand equal to supply; no drivers with and without requests; truncation of the raw ratio; a raw ratio above the cap; (+1, −1) as a neighbour and (+1, +1) as not (the square-grid mistake); a cell exactly `k` away and one `k + 1` away; an average of exactly half a hundredth; cells without data left out. At Hard: a rise and a fall limited by `max_step`, a move of exactly `max_step`, a cell missing from `prev`, and a previous value above the cap. At Very Hard: distance weights, and weights counted only for cells that have data.

**Common mistakes.** Chebyshev or Manhattan distance on `(q, r)`, which picks the wrong six neighbours; treating missing cells as 1.00x; `round()` (half to even) or floats; capping before the step limit, so a cell whose previous value was above a lowered cap is held above it; applying the step to the raw value instead of the smoothed value; forgetting that the step limit starts from 100 for a new cell.

**Follow-up guidance.** (1) Weight the centre more, require a minimum number of drivers before a cell's own ratio is trusted, or blend the cell's value with the neighbourhood's by how much data it has; measure on replayed intervals how often a real spike is damped. (2) Keep the per-cell raw values and the k-ring sums; when a cell changes by Δ, add Δ × weight to the sums of the cells in its own k-ring, which is O(changed · k²). (3) The step limit slows oscillation but does not remove it; add hysteresis (only move when the change exceeds a threshold), smooth over time as well as space, and watch boundary crossings. (4) Shadow mode: compute the new rule beside the old one on live or replayed inputs, compare distributions and downstream metrics offline, then a limited experiment with guardrails.

**Rubric anchors.** 2: correct for interior cells, but a square-grid distance or a rounding error, or a quadratic scan. 3: all rules correct with integer arithmetic and k-ring offsets. 4: also argues the offset generation is complete and duplicate-free, explains every boundary case unprompted, and gives a concrete incremental update and a safe testing plan.

**Strong signals.** Writes the hex distance and checks it on a known pair before coding; asks whether missing cells count. **Red flags.** "Just use round()"; floats for prices; scanning all cells "because N is small".

## UBR-L2-02

**Reference solution**

```python reference
def insert_rider(start, onboard, capacity, stops, pickup, dropoff,
                 max_wait, max_ride, seats=1, dwell=0):
    def dist(a, b):
        return abs(a[0] - b[0]) + abs(a[1] - b[1])

    n = len(stops)
    big = 1 << 62
    locs = [start] + [(s[2], s[3]) for s in stops]        # location 0 is the start
    dep = [0] * (n + 1)          # time the car leaves location i
    arr = [0] * (n + 1)          # time the car reaches location i
    load = [onboard] * (n + 1)   # seats taken when the car leaves location i
    slack = [big] * (n + 2)      # how late stop i may become
    for i in range(1, n + 1):
        _rider, kind, _x, _y, latest, size = stops[i - 1]
        arr[i] = dep[i - 1] + dist(locs[i - 1], locs[i])
        dep[i] = arr[i] + dwell
        load[i] = load[i - 1] + (size if kind == "pickup" else -size)
        if latest is not None:
            slack[i] = latest - arr[i]
    suffix = [big] * (n + 2)     # min slack of stops i..n
    for i in range(n, 0, -1):
        suffix[i] = min(slack[i], suffix[i + 1])

    def gap(i, x):
        """Extra time to visit x between location i and location i + 1."""
        if i == n:
            return dist(locs[i], x) + dwell
        return dist(locs[i], x) + dwell + dist(x, locs[i + 1]) - dist(locs[i], locs[i + 1])

    best = None
    for i in range(n + 1):                       # the pickup goes right after location i
        if load[i] + seats > capacity:
            continue
        a_pick = dep[i] + dist(locs[i], pickup)
        if a_pick > max_wait:
            continue
        # drop-off immediately after the pickup
        a_drop = a_pick + dwell + dist(pickup, dropoff)
        if a_drop - a_pick <= max_ride:
            if i == n:
                added = dist(locs[i], pickup) + dwell + dist(pickup, dropoff) + dwell
            else:
                added = (dist(locs[i], pickup) + dwell + dist(pickup, dropoff) + dwell
                         + dist(dropoff, locs[i + 1]) - dist(locs[i], locs[i + 1]))
            if suffix[i + 1] >= added and (best is None or added < best[0]):
                best = (added, i, i + 1)
        if i == n:
            continue
        # drop-off right after a later stop j: stops i+1..j move by d1, the rest by d1 + d2
        d1 = gap(i, pickup)
        low = big
        for j in range(i + 1, n + 1):
            low = min(low, slack[j])
            if low < d1 or load[j] + seats > capacity:
                break                                 # every later j fails the same way
            a_drop = dep[j] + d1 + dist(locs[j], dropoff)
            if a_drop - a_pick > max_ride:
                break                                 # the ride only gets longer
            added = d1 + gap(j, dropoff)
            if suffix[j + 1] >= added and (best is None or added < best[0]):
                best = (added, i, j + 1)
    return best
```

**Explanation.** Precompute the plan once: arrival and departure time at each stop, the load when the car leaves each location (location 0 is the start), and each stop's slack `latest − arrival`, with suffix minima. A stop `x` inserted after location `i` delays every later stop by `gap(i, x) = dist(i, x) + dwell + dist(x, i + 1) − dist(i, i + 1)` (no last term at the end of the route). For a pickup after location `i`: the car must have room when it leaves `i` and the pickup must be on time. The drop-off can follow immediately, which shifts every later stop by one combined detour. Otherwise the drop-off goes after a later stop `j`: stops `i + 1 … j` move by `d1 = gap(i, pickup)` and need slack ≥ `d1`; stops after `j` move by `d1 + gap(j, dropoff)` and need suffix slack ≥ that; the rider is in the car when it leaves every stop from `i` to `j`, so those loads plus `seats` must fit. Walking `j` forward keeps a running minimum slack and checks loads one at a time; both conditions only get harder as `j` grows, so the loop can stop. The ride time also only grows with `j` (triangle inequality, dwell ≥ 0), so that check can stop the loop too. Scanning `i` and `j` in increasing order and keeping only strictly cheaper candidates gives the specified tie-break.

**Complexity.** O(n) precomputation and O(n²) pairs at most, each O(1); O(n) memory. The timing check is a 600-stop route: under 0.1 s for the reference, while simulating each of the ~180 000 candidate routes takes tens of seconds in CPython.

**Dialect notes.** Production dispatchers usually work with travel-time matrices from a routing engine rather than Manhattan distances, and check far fewer stops per car; the same prefix and suffix structure applies. In a JVM or C++ implementation the same algorithm is the norm, often with the outer loop over candidate drivers run in parallel. Not executed here.

**Edge cases built into the tests.** An idle driver; a rider exactly on the way (cost 0); equal costs everywhere (tie-break); a full car that can take the rider only after a drop-off; `max_wait` exactly and one second over (and `None`); `max_ride` exactly and one second over with no alternative (`None`); `max_ride` forcing the drop-off before another stop. At Hard: a promised stop reached exactly on time, one second late, and a tight promise late in the route. At Very Hard: a party of two that needs two seats for the whole ride, dwell at an inserted stop delaying a promised stop, and dwell at the pickup counted in the ride time.

**Common mistakes.** Checking capacity only at the pickup, or forgetting the load when the car leaves stop `j`; shifting every later stop by the full detour even when only the pickup has been inserted before them; forgetting the end-of-route case, where there is no "next" term; returning the old-sequence positions instead of the new ones; counting dwell at the start; checking `latest` on departure; using `<` at the boundaries; treating the triangle inequality as an assumption to prune by without saying so.

**Follow-up guidance.** (1) Most time goes to travel-time lookups and to drivers that cannot work: filter by distance to the pickup, by free seats and by remaining slack before calling; cache travel times per request; stop early when a driver's lower bound on cost exceeds the best found. (2) The early exit on ride time used the triangle inequality; without it, keep checking the ride time for every `j` (still O(n²)) and make sure the detour formula uses the routing service's times consistently. (3) Serialise per vehicle: a conditional update on the vehicle's plan version (compare-and-set), so the second request is re-evaluated against the new plan. (4) Re-plan when insertions accumulate detours or a cheaper order exists; the promised times and the "no reordering of picked-up riders" rule constrain it, and re-planning is a local search or exact search only for small plans.

**Rubric anchors.** 2: correct by building and simulating each candidate route (O(n³)), or an O(n²) attempt with a capacity or shift error. 3: O(n²) with precomputed arrays, all checks correct, including the tie-break and `None`. 4: also proves each early exit, handles party sizes and dwell cleanly, and discusses latency budgets, concurrency and re-planning with concrete mechanisms.

**Strong signals.** Writes the detour formula and the shifted ranges on a small example before coding; states the monotonicity that justifies each `break`. **Red flags.** Reordering existing stops; ignoring riders already in the car; floats for time.

## UBR-L2-03

**Reference solution** (the fixed job)

```python reference
ALLOWED = {
    None: {"requested"},
    "requested": {"accepted", "cancelled"},
    "accepted": {"arrived", "cancelled"},
    "arrived": {"started", "cancelled"},          # a rider no-show is cancelled after arrival
    "started": {"completed"},
    "completed": set(),
    "cancelled": set(),
}
LIFECYCLE = {"requested", "accepted", "arrived", "started", "completed", "cancelled"}


def reconstruct_trips(events):
    by_trip = {}
    seen = set()
    for ev in events:
        evs = by_trip.setdefault(ev["trip"], [])
        if ev["event_id"] in seen:                   # a retransmitted copy
            continue
        seen.add(ev["event_id"])
        evs.append(ev)

    out = {}
    for trip, evs in by_trip.items():
        evs.sort(key=lambda ev: ev["seq"])           # the trip's order, not the phone's clock
        state, started_at, seconds, illegal = None, None, None, 0
        for ev in evs:
            t = ev["type"]
            if t not in LIFECYCLE:                   # location and other events: ignored
                continue
            if t not in ALLOWED[state]:
                illegal += 1
                continue                             # counted, never applied
            state = t
            if t == "started":
                started_at = ev["device_ts"]
            elif t == "completed":
                seconds = ev["device_ts"] - started_at
        out[trip] = {"state": state, "trip_seconds": seconds, "illegal": illegal}
    return out
```

**The planted bugs, their symptoms and their fixes.**
1. **Ordered by the phone's clock.** `evs.sort(key=device_ts)` mixes two phones' clocks. When the driver's phone runs slow, `accepted` sorts before `requested`, is illegal, and every later step is judged from the wrong state. Symptom: trips whose driver's clock is slow show up as never accepted, with high illegal counts. Fix: sort by `seq`.
2. **Retransmitted copies applied twice.** There is no deduplication by `event_id`, so the second copy of `accepted` is an `accepted → accepted` transition and is counted as illegal. Symptom: illegal counts rise with network flakiness, not with real problems. Fix: drop events whose `event_id` has been seen.
3. **Illegal transitions applied.** The code counts an illegal event but then sets `state = t` anyway (a missing `continue`). Symptom: a late cancel after completion turns a completed trip into a cancelled one; a stale `accepted` retry moves a trip backwards; a double-tapped start resets the start time. Fix: `continue` after counting.
4. **No cancel after arrival.** The table has `"arrived": {"started"}`, so a rider no-show cancellation is illegal and the trip stays `arrived`. Symptom: no-show trips stuck in "arrived" for ever. Fix: allow `cancelled` from `arrived`.
5. **Location events counted.** Every type that is not an allowed transition is counted as illegal, including `location`. Symptom: the illegal-event alarm tracks the location sampling rate. Fix: ignore types outside the lifecycle before the transition check.

Each bug has its own check that only it fails: a slow driver clock (1), a retransmitted copy (2), a stale `accepted` retry with a new id (3, also the double tap, the cancel after completion and the lost request), a no-show (4), and location events (5, also a trip with only location events). The reversed-delivery and two-trip checks pass on the original code because its phone clocks agree there: ordering by device time is wrong in general but right whenever the clocks agree, which is why bug 1 survives casual testing. Worth discussing with the candidate.

**Explanation.** A trip is a small state machine. The job must (a) collapse copies to one event, (b) order a trip's events by a sequence assigned in one place, (c) filter out events that are not part of the machine, and (d) apply only allowed transitions, counting the others. Durations are differences of timestamps from one phone, so a constant clock offset cancels; ordering across two phones has no such protection.

**Complexity.** O(n log n) for the per-trip sorts, O(n) memory for the groups and the seen-id set. The timing check is 200 000 events.

**Dialect notes.** In SQL the same rules are `ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY …) = 1` for copies and an ordered fold over `seq`, which plain SQL expresses poorly: a recursive CTE, or `MATCH_RECOGNIZE` where the engine supports it (Snowflake, Oracle). In Spark, `groupBy(trip)` and a sorted fold per group (`applyInPandas` or `flatMapGroupsWithState` for streaming). Not executed here.

**Edge cases built into the tests.** Reverse delivery; a slow driver clock; a retransmitted copy; a stale retry with a new id; a no-show; location events; a double tap; a cancel after completion; a lost request; a trip with only location events; two trips interleaved.

**Common mistakes.** Fixing the sort but deduplicating on `(trip, type)`, which also drops the double tap that should be counted; deduplicating after counting; adding `continue` but still updating `started_at` before the check; allowing a cancel from `started`, which the specification does not; raising an exception on an illegal transition; dropping trips with only location events from the output.

**Follow-up guidance.** (1) Emit a provisional state per trip when events arrive, with a version, and corrections as new versions; final states after a watermark plus a grace period; late events after that produce a correction record. Consumers read the latest version. (2) Bound the seen-id set by time: ids older than the longest retry window can be forgotten, or deduplicate per trip, keeping ids only until the trip is final plus a grace period. A copy arriving after that would be applied again, so the transition check must be safe for it, which it is for every terminal state. (3) Break down illegal counts by app version, platform and transition; a pipeline bug shows across all versions at once and around a deploy, an app bug follows the release's rollout. (4) Use the server's receipt time for the start and end events, or a monotonic elapsed-time counter from the phone, which a clock sync does not change; the cost is network delay in the server time, and support in the app for the monotonic counter.

**Rubric anchors.** 2: finds two or three bugs, some checks still fail. 3: all five fixed, all checks pass, each explained with its symptom. 4: also states the state machine and the invariants, adds a regression test per bug, and gives concrete answers for streaming emission and bounded deduplication.

**Strong signals.** Reproduces each bug with a three- or four-event trip before fixing it; asks which fields come from which phone. **Red flags.** "Sort by timestamp, it is what timestamps are for"; rewriting the job from scratch; making illegal events raise.

## UBR-L2-04

**Reference architecture (one defensible design; score others on the criteria).**
- **Scope.** The affected set comes from data, not complaints: trips whose recorded rule version is one of the faulty releases, in the affected cities and vehicle class, within the window, plus a guard band before and after it. Every trip in scope is recomputed; the diff decides who is affected.
- **Recompute (pure).** A replay service runs the same pricing code with the corrected rule version, reading only pinned inputs: the trip's stored pricing inputs (quote inputs for upfront trips; measured time and distance for metered trips), surge, promotions applied, tolls, taxes and currency rounding rules. Output per trip and component: `(trip_id, incident_id, run_id, component, charged_minor, corrected_minor, currency)`. Runs are versioned; a re-run with revised rules is a new `run_id`, never an overwrite.
- **Validate the replay.** First replay the trips with the *original* faulty rules: it must reproduce the charged amounts exactly. Any mismatch means the replay is not faithful (missing inputs, a code difference) and must be fixed before trusting the corrected run.
- **Diff and review.** Aggregate the per-component differences by city, currency, direction (over or under) and size; sample trips for manual review; finance and city operations sign off on a frozen `run_id`.
- **Policy.** Written down and owned: refund overcharges to riders; absorb undercharges (or not, if policy says otherwise); for upfront trips, compare with the quote the rider agreed to; driver earnings adjusted upward where they were underpaid and, typically, not clawed back; minimum thresholds per currency below which no adjustment is sent (with the totals still reported).
- **Exclusions.** Trips already refunded in full, disputed, or adjusted since the trip are routed to a manual or reduced path. The adjustment amount is computed net of what has already been returned.
- **Apply (idempotent).** One adjustment per `(incident_id, trip_id, party)` with that tuple as the idempotency key, sent through the normal payments and earnings APIs; a state table (`pending → sent → confirmed | failed`) is written before and after each call. Restarts resend only `pending` or unknown ones, and the downstream key makes a resend harmless. Notifications go out only after confirmation.
- **Audit and reconciliation.** Originals are never changed. The ledger gets adjustment entries referencing the incident; totals by currency reconcile to the signed-off diff; the run manifest records rule versions, code version and inputs.

**Competing designs to accept.** Recompute inside the warehouse with the pricing logic re-implemented in SQL (acceptable only with the reproduce-the-original check, since two implementations drift); a streaming job that recomputes as trips are read; a per-city phased rollout of adjustments. Any is fine if recompute and apply are separated and keys are deterministic.

**Bottlenecks and failure modes.** A replay that reads live rules or live surge; promotions that are a percentage of the fare (they must be recomputed, not copied); rounding per component vs on the total; currencies with zero or three decimal places; the payments API rate limit for {trips_affected} adjustments; notifications sent before money moves; a second incident on the same trips (the key includes the incident).

**Incident guidance.**
- *Differences in cities the bug never touched*: the replay is not faithful. Stop, run the original rules and find the input or code difference (for example a rounding change, a promotion rule or a later tax table), fix the replay, and re-run; never adjust trips on an unexplained diff.
- *Restart resends 12 000 requests*: the payments system rejected them as duplicate keys, which is the design working. Reconcile the state table with the downstream confirmations, mark them `confirmed`, and alert only on keys whose payload differs.
- *Support already refunded some trips*: compute the adjustment net of refunds already issued; exclude full refunds; report the excluded set to support so that agents do not refund again from the other side.

**Follow-up guidance.** (1) Recompute the promotion from the corrected fare by its own rule (percentage, cap); the rider's adjustment is the difference in what they paid; the promotion budget's accounting changes too. (2) The state table and the idempotency keys say exactly what was sent; on restart, query downstream by key for anything `pending` and resume. (3) A new `run_id` with the re-corrected rules; diff run 2 against run 1; send only the deltas with keys that include the run or a revision number, or net them in one follow-up adjustment per trip. (4) Signed-off diff frozen by `run_id`, adjustments keyed and linked to it, ledger entries reconciled in totals and by sample. (5) Taxes recomputed from the corrected fare with the tax rules in effect at the trip time; adjustments carry tax components, and finance confirms reporting.

**Rubric anchors.** 2: an UPDATE of the fares table and a loop of refunds; no replay check; no idempotency. 3: pure recompute with pinned versions, a reviewed diff, idempotent adjustments with deterministic keys, originals kept. 4: also the reproduce-the-original validation, explicit owned policies (upfront vs metered, riders vs drivers, thresholds), exclusions for prior refunds and disputes, reconciliation to the ledger, and a revision path for a second correction.

**Strong signals.** Asks whether trips were upfront or metered before designing; proposes replaying the faulty rules first. **Red flags.** "Charge everyone the difference"; adjustments without keys; overwriting charged amounts.

## UBR-L2-05

**Reference architecture (one defensible design; score others on the criteria).**
- **Polygon store.** A table of polygon versions: `(polygon_id, version, type, priority, city, geometry, effective_from, effective_to, published_at, change_reason, retroactive)`. Validation on publish: valid geometry, `effective_from < effective_to`, no unintended overlap within a type, and a diff against the previous version (area change, cells added and removed). A version is immutable once published.
- **Cell cover.** For each polygon version, cover it with cells at a fixed resolution (a hexagonal or square hierarchical grid) and label each cell `interior` or `boundary`. Very large polygons are covered at a coarser resolution for interiors plus finer boundary cells. The cover table `(cell, polygon_id, version, kind, effective_from, effective_to)` is rebuilt only for changed polygons.
- **Join.** Each trip point is mapped to its cell; join on the cell and on `effective_from ≤ event_time < effective_to`; `interior` matches are final, `boundary` matches run an exact point-in-polygon test. Pickups use the pickup time and drop-offs the drop-off time. Overlaps are resolved per type by priority, so a point can have one operating zone, one pricing zone and several geofences.
- **Boundaries and accuracy.** A documented rule for points exactly on an edge (for example inclusive for the lower-priority side) and for low-accuracy points: keep the raw assignment and also record a distance to the boundary and the reported accuracy, so that downstream teams can apply an owned tolerance, rather than snapping silently.
- **Runs and late trips.** The daily run processes trips by event date partitions, including late trips for older dates, and records in a run manifest which polygon versions it read. Output partitions are overwritten per event date; each row carries `polygon_id`, `version` and `match_kind`.
- **Corrections.** A retroactive correction is a new version with an earlier `effective_from` and `retroactive = true`. Affected trips are found from the cells whose assignment changes (the symmetric difference of the old and new covers) and the dates in range, and only those partitions are reprocessed. Published reports either stay as published with an adjustment in the next period, or are restated, per the owner's policy; both versions of the assignment are kept.

**Competing designs to accept.** A spatial SQL engine with a spatial index and `ST_Contains` (fine at {daily_trips} if it partitions by city and prunes with bounding boxes); Spark with a broadcast cell cover; a geohash or S2 cover instead of hexagons. The choice of grid matters less than the interior/boundary split and the effective-dated versions.

**Bottlenecks and failure modes.** Polygons with thousands of vertices making exact tests slow (simplify only for interior covering, never for the exact test; split very large polygons into tiles); skew when one city's airport receives a large share of points; joining with the latest polygons; invalid geometries or inverted effective intervals; late trips landing after a day was considered final; a correction that silently changes paid incentives.

**Incident guidance.**
- *A corrected airport boundary effective 45 days ago, incentives already paid*: reprocess only the affected cells and dates, produce the old-versus-new assignment diff, and hand it to the incentive owners: paid amounts are not reversed by the pipeline; any adjustment is a business decision made with the diff. Report both versions.
- *An event geofence with effective-to before effective-from*: the publish validation should have rejected it; add that check, fix the version, reprocess the event's dates, and alert when a geofence of an active event matches zero trips.
- *Late trips joined with today's polygons*: the join must use the trip's own time; fix it, reprocess the late trips' event dates, and add a test with a polygon that changed between the trip date and the run date.

**Follow-up guidance.** (1) Symmetric difference of covers × the 60 days, reprocess those partitions, publish a diff and keep both versions; published reports follow the restatement policy. (2) Tile the polygon and use finer boundary cells so that only a small share of points need the exact test; precompute an edge index per boundary cell. (3) The rule is a written choice: pickup time for pickup-area geofences, request time for pricing; record which timestamp each assignment used. (4) Measure the distance-to-boundary distribution and accuracy; propose a tolerance with the airport operations owner; run both rules side by side before switching. (5) The same versioned cover table loaded into the request-time service; a daily reconciliation compares the two assignments and alerts on disagreement above a threshold.

**Rubric anchors.** 2: a nightly cross join with `ST_Contains` against the latest polygons; no versions. 3: effective-dated versions, cell cover with interior and boundary cells, trip-time joins, recorded versions. 4: also targeted reprocessing for retroactive corrections with a restatement policy, explicit boundary and accuracy rules, publish-time validation, and handling of very large polygons and skew.

**Strong signals.** Asks which timestamp decides the version; separates the business decision about restating paid reports from the pipeline mechanics. **Red flags.** Joining with today's polygons; snapping points silently; overwriting polygons in place.
