# Netflix · Loop 4 — evaluator notes (hidden from candidates)

## NFX-L4-01

**Reference architecture (one defensible design; score others on the criteria).**
- **Sizing**: peak writes ≈ peak streams ÷ heartbeat interval. With {{peak_streams}} streams and a {{heartbeat}}-second heartbeat that is between a few hundred thousand and several million updates per second. A strong candidate does this arithmetic before choosing a store, and notices that most heartbeats only move a position forward a little.
- **Write path**: players send heartbeats to a stateless edge tier in the nearest region. Each update carries `profile_id, title_id (episode id for series), session_id, seq, position_ms, duration_ms, event_type (heartbeat | pause | seek | stop | explicit_restart | offline_sync), device_ts`. A session tier keeps the latest position per active session in memory and writes the durable resume point at most every heartbeat interval and always on pause, stop, seek and app close; a lost node therefore loses at most one interval. Every update also goes, asynchronously, onto a viewing-events stream for history, analytics and recommendations, which the play button never waits on.
- **Store**: a replicated key-value or wide-column store; partition key `profile_id`, clustering key `title_id` (series rolled up by `series_id` with the current episode). Row: position, duration, current episode, `session_id`, `session_start_server_ts`, `seq`, `activity_ts`, state (`in_progress | finished | hidden`), `hidden_at`.
- **Ordering and conflicts**: within a session, the highest `seq` wins. Across sessions, the most recent activity wins, where activity time is server-observed for online sessions (the server sees every session start) and, for offline plays, device time clamped to the download's licence time at the low end and to the upload time at the high end. An update that would move the position backwards within a session is accepted only with an explicit seek or restart event. Accept last-writer-wins only if the candidate says which clock and handles skew.
- **Finished and next episode**: finished when the credits marker is reached or 95% has played; for a series the row entry advances to the next episode at position 0; a finished film drops out of the row. These rules run on write so the row read is cheap.
- **Row read path**: a materialised row per profile (the most recent N in-progress entries, for example 40–80), maintained on write, read in one key lookup and filtered at read time against maturity settings and catalogue availability. "Remove from row" sets `hidden` with `hidden_at`; any later activity newer than `hidden_at` un-hides it. Viewing history is never scanned on the hot path.
- **Multi-region**: active-active with asynchronous replication of resume rows and a monitored replication-lag budget. Because asynchronous replication can lose the last few seconds on failover, the client sends its own last-known position for the title with the play request, and the service takes the newer of the two by the ordering rule. This guard makes failover honour the one-interval bound for the device that played last, and narrows the gap for other devices.
- **Measurement**: a "backwards jump" metric from clients: at each play, compare the returned resume point with the device's own last-known position and with the profile's most recent activity; report the share of plays resumed more than one interval behind, by device type, region and app version.

**Competing designs to accept.** A home region per profile with synchronous writes there and asynchronous copies elsewhere (simpler conflicts, worse failover). Event sourcing of all position updates with the resume row as a projection (excellent for recovery, more storage). CRDT-style registers keyed by (activity time, session id) with a deterministic tie-break. Writing every heartbeat durably, if the candidate sizes it and pays for it consciously.

**Bottlenecks and failure modes.** Write amplification from heartbeats; hot partitions from shared or test accounts that stream continuously; position regressions from stale devices, skewed clocks, offline syncs or buggy clients; replication lag at failover; rows that grow without bound if built by scanning history; coupling recommendations to the hot path.

**Incident guidance.**
- *Position 0 in the first heartbeat*: diagnose by app version and device type through the backwards-jump metric. Contain by ignoring a position-0 heartbeat at the start of a session when a later resume point exists, unless the event type is an explicit restart, and roll the app back or flag the behaviour off. Recover by recomputing resume rows from the position event log (or viewing history) up to the release time for affected profiles. Prevent with release canaries per device type watched on the backwards-jump metric, and server-side validation of event types.
- *Region failure with six minutes of lag*: members resume up to six minutes early on other devices. Short term: rely on the client-sent last-known position; after the failed region recovers, merge its unreplicated rows by the ordering rule rather than overwriting. Prevention: an alert and an objective on replication lag, capacity headroom so replication does not fall behind at peak, and optionally synchronous replication of pause and stop events only.
- *Offline backlog reorders the row*: the row ordered by arrival time instead of activity time. Fix the ordering to use clamped activity time, never let an older offline update override a newer online one or un-finish a finished title, and rebuild the rows of affected profiles from the log. Add a test that replays a multi-day offline sync.

**Follow-up guidance.** Make the candidate state the conflict rule in one sentence and test it against the offline-flight case. Ask what the play request sends, and whether the client is part of the consistency story. For the row at ten thousand titles, look for a materialised, bounded row rather than a scan with sort.

**Rubric anchors.** 2: one table updated on every heartbeat with last write by arrival, row computed from full history, no failover story. 3: sized write path with coalescing, per-session ordering, a stated rule for clocks and offline plays, materialised row with finished and hidden states, asynchronous multi-region with a lag budget. 4: also the client's last-known position as a failover guard, an event log for recovery, a backwards-jump metric by device and version, and crisp handling of every incident.

**Strong signals.** Computes the write rate first; separates resume points from viewing history; treats "never move backwards" as a measurable property. **Red flags.** "Strongly consistent across all regions" with no latency or cost estimate; trusting device timestamps blindly; scanning viewing history on every home page load.

## NFX-L4-02

**Reference architecture (one defensible design; score others on the criteria).**
- **Document model**: one document per title (and separate small documents for people and genres). Fields: ids and type; `names` as a list of `{lang, name, aliases, transliterations}`, plus the original-language name; cast and crew ids and names; genres; per-country `availability` as a compact list of `{country, start, end}` where start and end are UTC instants converted from the licence's local date and time with the time-zone database at ingest; per-country maturity normalised to a level; per-country popularity signals; coming-soon dates. With about 190 countries and a few windows each, a title's availability list is a few hundred small entries, fine for a nested or packed field.
- **Matching**: per-language analysers (tokenisation, case and diacritic folding, transliteration into Latin script for non-Latin names, and vice versa where useful); edge n-grams or a completion structure for prefix suggestions from TV remotes; bounded fuzzy matching for typos; query fields weighted toward the profile language, then original and English names.
- **Hard filters at query time**: `country = member's country AND start ≤ now < end AND maturity_level ≤ profile level`, applied inside the index query so they constrain candidates before top-K. Coming-soon titles match with a separate flag and never get a play action. A query that matches only unavailable titles returns related available titles (same people, genres or similar titles) rather than nothing.
- **Ranking**: first stage text relevance blended with popularity in the member's country; second stage reranks the top few hundred with the personalisation score (under 20 ms), with a timeout fallback to the first-stage order.
- **Updates**: catalogue, licensing and localisation changes flow as a change stream into an indexing service that applies partial updates within {{freshness}}. Because windows are stored as instants and filtered at query time, a title disappears at its boundary even if the stream is late. A periodic sweep compares the index with the source of truth.
- **Caching**: suggestion caches keyed by `(normalised prefix, country, language, maturity level)`, each entry expiring no later than the earliest window boundary among its results (or a short TTL of under a minute).
- **Rebuilds**: build a new index from a snapshot of the catalogue tagged with the change-stream position, replay the stream from that position until caught up, validate with a set of known queries per country and script, switch an alias, keep the old index for rollback.
- **Regions**: each region keeps its own replicas fed independently from the same change stream, so search survives a region loss; playback's own licence check remains the last line of defence.

**Competing designs to accept.** One index per region-group of countries (smaller documents, more copies to keep consistent). A separate availability service consulted at query time on candidate ids (cleaner ownership, more latency). A dedicated suggestion service for TV prefix typing separate from full search. Precomputing per-country result lists for the most common prefixes.

**Bottlenecks and failure modes.** Window boundaries computed in the wrong time zone; filters applied after truncation; caches that outlive a boundary; reindexing load during peak; one malformed localisation batch blanking names; per-language analysers that silently drop scripts; hot queries at a big launch.

**Incident guidance.**
- *UTC dates for local-midnight windows*: diagnose with a query of window boundaries per country against the licence source. Contain by hotfixing the conversion (store instants from local time and zone) and reindexing affected titles, which can be targeted by a sweep; meanwhile, a query-time guard against the licensing service for top results. Prevent with tests across time zones, including half-hour offsets and daylight-saving changes, and a monitor of "search result followed by licence error" per country.
- *Empty localised name*: the index accepted an empty field. Validate localisation batches per language (non-empty, plausible length, expected script) and reject the bad rows while keeping the previous value; always index the original and English names as fallbacks so a title stays findable. Monitor launch-day "no results" rates per language.
- *Kids autocomplete leak*: the filter moved out of the query and the cache bypassed it. Purge the suggestion cache, restore the filter inside the query, and include maturity in the cache key. Prevent with a continuous probe that runs a list of queries on kids profiles in every country and alerts on any result above the level.

**Follow-up guidance.** Ask what happens at 00:01 with the pipeline 20 minutes late; a strong candidate answers "the window filter hides it" without needing the pipeline. Push on whether filters run before top-K. For rebuilds, look for snapshot plus replay from a recorded stream position.

**Rubric anchors.** 2: a generic search index updated by events, filtering in the application, no time-window thinking. 3: per-country windows in the index, query-time filtering before top-K, per-language analysers and prefix suggestions, a change stream with freshness, alias-based rebuilds. 4: also instants converted from local time with tests across zones, cache keys and expiry tied to boundaries, two-stage ranking with a fallback, per-region independence, quality metrics per country and script, and crisp handling of every incident.

**Strong signals.** Treats availability as data with time, not as an event; asks about kids profiles in autocomplete unprompted. **Red flags.** Relying on deletes arriving on time; filtering after taking the top results; one global cache key without country or maturity.

## NFX-L4-03

**Reference architecture (one defensible design; score others on the criteria).**
- **Entities**: `asset` (film or episode); `source_version` (`asset_id, version, checksum, received_at, supersedes`); `recipe` (`codec, profile, resolution, bitrate, hdr_format, audio_codec, language, encoder_version, params`, identified by a hash); `rendition` (`rendition_id = hash(source_version, recipe)`, storage location, size, checksum, `state`, `created_by_task`); `qc_result` (`rendition_id, check, outcome, reviewer, at`); `quality_score` (`rendition_id, metric, metric_version, granularity (shot | file), value`), never overwritten; `live_set` (`asset_id, version, rendition_ids, created_at, effective_at`), immutable versions with a current pointer; `campaign` (target selector, recipes, goals) and `campaign_task` (`campaign_id, asset_id, recipe_id, source_version, state, attempts, compute_cost, output_rendition_id`).
- **Lifecycle**: `requested → encoding → encoded → qc_passed | qc_failed → approved → live (in a live set) → superseded → deletable → deleted`. The live-set writer accepts only `approved` renditions; the constraint lives in the writer and the manifest service, not in the scheduler.
- **Lineage**: re-delivered sources create a new `source_version`; a query finds every rendition and live set built from the old version, campaign tasks for it are cancelled or re-planned, and new tasks are created for the new version. Live sets keep serving the old renditions until replacements are approved, unless the old source is unusable.
- **Manifest path**: live sets are replicated to a read store (or cache) in every region and invalidated on version change; the manifest service reads the current live set per asset, never the catalogue's primary database.
- **Object store consistency**: upload the file first, then write the rendition record with its checksum; a sweeper deletes files with no record after a grace period and flags records whose file is missing or whose checksum differs.
- **Deletion**: a superseded rendition becomes deletable only when no live-set version that referenced it was current within the manifest cache window (24 hours) plus a margin, it belongs to no in-progress campaign, and no hold applies. Deletion is a soft delete (a recoverable period in object storage) before the bytes are gone.
- **Campaign queries**: progress by state; failures by recipe, encoder version and asset; compute cost by campaign from tasks; storage change from renditions created minus deleted; quality gain as bitrate saved at equal score, or score gained at equal bitrate, always within one metric version.

**Competing designs to accept.** An event-sourced catalogue with projections for live sets and campaign progress. A graph store for lineage with a relational store for states. Per-asset documents holding renditions, if the candidate keeps renditions immutable and live-set switches atomic.

**Bottlenecks and failure modes.** Mutable rendition rows that break cached manifests; publication rules enforced in the wrong place; quality scores mixed across metric versions; deletion before caches expire; catalogue and storage drifting apart; campaigns that cannot tell which work succeeded.

**Incident guidance.**
- *Live before QC*: roll back by pointing affected assets at their previous live-set version (instant, because versions are immutable) and invalidate manifest caches; find affected titles and plays by live-set version. Prevent by making the live-set writer and the manifest service refuse non-approved renditions, and alert on any live rendition without a passing QC record.
- *Deletion at 12 hours with 24-hour manifests*: stop the cleanup job, restore soft-deleted files, and change the rule to the cache window plus margin computed from live-set history. Monitor 404s on rendition fetches by age of manifest.
- *Metric version mix*: withdraw the reported gain; re-score a representative sample (or all) of the old renditions with the new version, or compare both with the old version. Prevent with dashboards that join on metric version and refuse cross-version comparisons.

**Follow-up guidance.** Ask how the candidate finds every file affected by an encoder bug in one codec profile: a strong answer is a query on recipe and encoder version, then re-planned tasks. Push on the exact deletion condition.

**Rubric anchors.** 2: a table of files with a status column updated in place, no lineage, deletion by age. 3: immutable renditions with recipes and source versions, lifecycle with QC gating, versioned live sets, campaign tasks with states and cost. 4: also enforcement of the publication rule at the writer and the reader, manifest-window-aware soft deletion, metric-versioned scores and comparisons, object-store consistency sweeps, and crisp handling of every incident.

**Strong signals.** Insists on immutability and full recipes; thinks about what cached manifests still point at. **Red flags.** Updating renditions in place; deleting by age alone; one quality number per rendition with no version.

## NFX-L4-04

**Reference architecture (one defensible design; score others on the criteria).**
- **Forecast**: per title and country for the next day, from recent viewing with decay, day-of-week patterns, release calendar and, for new releases, priors from similar titles and pre-launch signals, with an explicit uncertainty range. Per site, the country forecast is split by the site's share of that country's demand and by its audience's device mix into expected bytes per rendition.
- **Placement**: for each site, rank candidate files by expected bytes served from the site divided by file size. Two budgets: storage ({{cache_tb}} TB) and fill bytes (window length × agreed bandwidth). Files already present cost no fill bytes, so a greedy selection by value per byte, with hysteresis (replace a present file only if the newcomer's value exceeds it by a margin), fills storage while respecting the fill budget. Upstream sites are planned the same way with larger working sets so edge misses stay cheap. Candidates per site are limited to the top files by country forecast, so the per-site greedy is roughly M log M and sites run in parallel, ordered by window opening time.
- **Distribution**: each site receives a prioritised fill list (most valuable bytes first) and a delete list; caches fetch from upstream sites or peers in priority order during the window, rate-limited, resumable and idempotent, never evicting files being served; they report completion.
- **Intra-day correction**: hourly forecast refreshes from request logs; titles running far above forecast get a limited daytime fill budget at the most affected sites, and upstream sites absorb the rest.
- **Metrics**: byte offload per site (bytes served by the site ÷ bytes requested by its clients); fill efficiency (bytes later served from files filled tonight ÷ fill bytes); forecast error per title and country; member outcomes (delivered bitrate, rebuffering, start time) for plays served locally versus upstream. Request hit ratio is secondary.
- **Evaluation**: an offline simulator that replays request logs against candidate placements; then a controlled rollout to matched groups of sites, or alternating nights, with byte offload and member outcomes as decision metrics; the counterfactual for "is it worth it" is on-demand-only filling simulated on the same logs, or a small holdout of sites.

**Competing designs to accept.** Pure on-demand caching with LRU or LFU at edges plus overnight placement only for the top titles. Solving placement as an integer programme for regional groups with greedy at the edges. Placement by title popularity tiers if the candidate adjusts by file size.

**Bottlenecks and failure modes.** Surprise hits; new releases with poor priors; fill windows cut by maintenance; solver runtime across many sites; metrics that count requests; evicting files in use; daytime upstream fills saturating provider links.

**Incident guidance.**
- *Surprise hit at five times forecast*: use the intra-day path: refresh the forecast, push the hit's most requested renditions to the busiest sites within a daytime budget, let upstream sites carry the rest, and for the next night weight recent growth more heavily for titles in their first days. Monitor misses per title per region by the hour.
- *Fill window cut to 2 hours*: the prioritised list means the most valuable third arrived; the rest falls to on-demand. Re-plan that site's next night first; take provider maintenance calendars as an input; alert on fill completion below a threshold.
- *97% request hit ratio, lower byte offload*: revert or retune the policy; make byte offload and member outcomes the decision metrics; add file size to the policy's value function. Prevent with an evaluation checklist that rejects request-only metrics.

**Follow-up guidance.** Push on the value function (per byte, not per title) and on what happens when the window is short. Ask for a precise metric definition and its counterfactual.

**Rubric anchors.** 2: "put the most popular titles everywhere", request hit ratio, no fill budget. 3: per-site forecasts with device mix, greedy value-per-byte placement under storage and fill budgets, prioritised fill lists, byte offload as the metric. 4: also stickiness and hysteresis, new-release priors with uncertainty, an intra-day correction path, offline replay plus controlled rollouts with a stated counterfactual, and crisp handling of every incident.

**Strong signals.** Asks how big the files are relative to the cache; defines metrics in bytes; plans for a shortened window. **Red flags.** A global solver with no runtime estimate; ignoring device mix; claiming a hit ratio without saying what it counts.

## NFX-L4-05

**Reference architecture (one defensible design; score others on the criteria).**
- **Sizing**: with {{viewers}} viewers and, say, half voting, most within the first seconds of a {{window}}-second window, peak vote submissions are in the hundreds of thousands to millions per second, plus retries. Reactions are an order of magnitude more frequent but tolerate loss.
- **Client window**: open and close markers are carried as timed metadata in the stream; each client enables voting between them in its own playback timeline, so every viewer gets the same window relative to what they see. Each vote carries `poll_id, option, profile_id, session_id, client_seq, stream_position`.
- **Server bound**: a vote is accepted if its stream position lies between the markers and it is received before `live close time + maximum allowed delay + margin`; votes from sessions not currently playing the live stream, or claiming impossible positions, are rejected and logged.
- **Ingestion**: stateless edges in every region verify the signed token (profile, eligibility, session), then append the vote to a durable log partitioned by a hash of `profile_id` (never by option), and acknowledge only after the durable append. Retries carry the same `client_seq`.
- **Counting**: consumers per partition keep, per `(poll_id, profile_id)`, the vote with the highest `client_seq`, and maintain partial counts per option. Each region emits a watermark when it has drained everything received before its deadline; the final count is the sum of partition counts once every region's watermark has passed. The count can be recomputed from the log at any time.
- **Running counts**: partial sums published every few seconds to the control room, labelled provisional.
- **Reactions**: clients batch reactions every few seconds; edges aggregate per region and publish rates; sampled and lossy by design, never used for results.
- **Abuse**: eligibility and voting tied to authenticated profiles in active live sessions; limits per account and device; anomaly detection on bursts from few accounts, devices or networks; suspect votes stored with a flag and excluded under a rule published in advance, so the decision is auditable.
- **Audit**: keep the raw vote log, the deduplication rule, rejected votes with reasons, and the final tallies with a hash; an independent recount job reproduces the result.

**Competing designs to accept.** In-memory counters per edge with periodic durable snapshots, if the candidate shows exact recovery from a log. A server-time-only window with a generous grace period, if the candidate names the unfairness it creates. A managed stream service rather than a self-run log.

**Bottlenecks and failure modes.** The opening burst plus retry storms; hot partitions keyed by option; region partitions that delay votes past the close; stream markers inserted at the wrong time; double counting on retry; running counts mistaken for results.

**Incident guidance.**
- *Retry storm from one TV platform*: shed with admission control per platform at the edge, send retry-after hints, and switch that client to jittered backoff by remote configuration; because votes are idempotent, retries cannot double count. Decide with producers, under a rule agreed before the show, whether rejected viewers get a short extension. Prevent with load tests that include retry behaviour per client platform.
- *Region link lost for 20 seconds*: the edge's votes were durably logged locally and are forwarded when the link returns; the final count waits for that region's watermark, so the result is late, not wrong. If the delay threatens the reveal, producers decide by the pre-agreed rule; never reveal without every region's watermark or a stated exclusion.
- *Close marker 25 seconds late*: the stream position check is only as good as the markers. Count by the canonical window (open marker position plus the window length) rather than the late marker, and quantify affected votes. Since the margin is smaller than those votes, report it to producers with both counts and follow the policy set in advance. Prevent with a monitor comparing marker positions across feeds.

**Follow-up guidance.** Push on the fairness rule: a strong candidate defines the window in stream time and still bounds it on the server. Ask how the final count is proven, not just computed.

**Rubric anchors.** 2: a counter per option incremented by an API, server-time window, no deduplication. 3: separate vote and reaction paths, idempotent votes keyed by poll and profile, durable log before counting, stream-relative window with a server bound, final count after all regions finish. 4: also a peak estimate driving partitioning, watermarks per region, provisional versus final counts, auditable recount with flagged votes, pre-agreed policies, and crisp handling of every incident.

**Strong signals.** Asks how far behind live viewers are before designing; keeps an auditable log. **Red flags.** Keying the stream by option; trusting device clocks; revealing from running counts.
