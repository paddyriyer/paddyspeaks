# Airbnb · Loop 4 — evaluator notes (hidden from candidates)

## ABB-L4-01

**Reference architecture (one defensible design; score others on the criteria).**
- **Per-listing document, two parts.** Slowly changing attributes (location, capacity, property type, amenities, house rules, quality signals for ranking) and a compact calendar block: for each of the next ~365 local dates, a free bit, a check-in-allowed bit and a check-out-allowed bit; a `run[d]` array (length of the free run starting at night d, capped at the listing's maximum nights); a nightly price array in the listing's currency and its prefix sums; the listing's minimum and maximum nights (optionally per check-in date), advance notice, availability window, cleaning fee and discount rules; and the calendar version it reflects. Per listing that is roughly 365 × 4 bytes of prices, 365 × 8 bytes of prefix sums, a 365-entry run array and a few hundred bytes of bits: about 5 KB, so on the order of 50 GB for 10 million listings before replication, small enough to hold fully in memory across shards.
- **Partitioning.** Shard by geography using a hierarchical cell scheme (S2, H3, geohash or a quadtree) with cells split until each shard holds a balanced number of listings, so a dense city centre spans several shards and a rural area is one. Replicate shards for query throughput; hot cities get more replicas. A query fans out to the shards covering the viewport (usually one to a handful).
- **Query path.** (1) Shards intersecting the viewport. (2) Filter on guests ≤ capacity, property type, amenities with per-shard bitsets or posting lists. (3) Stay check in O(1) per candidate for check-in d and n nights: `run[d] ≥ n`, check-in allowed on d, check-out allowed on d+n, `min_nights ≤ n ≤ max_nights`, d at least the advance notice ahead of today in the listing's local date, d+n within the availability window. (4) Total: `prefix[d+n] − prefix[d]`, then the weekly discount for n ≥ 7 or the monthly one for n ≥ 28 (this exercise's rules), plus the cleaning fee, converted to the guest's currency with the day's rate; apply the price filter on the total (or per night, as stated). (5) A cheap first-stage score keeps the top few thousand candidates per query across shards; the ranking model re-ranks them; pins are the top few hundred by first-stage score within the viewport.
- **Update path.** The calendar service emits a change event per listing with a monotonically increasing calendar version, written through an outbox so no change is lost. Events go to a log partitioned by listing id; indexers per shard consume, coalesce several events for one listing into one update, rebuild that listing's calendar block (bits, runs, prices, prefix sums, a few microseconds) and swap it atomically; an event whose version is ≤ the stored one is ignored. Lag (event time to applied time) is measured per shard against {{staleness}} and alarmed. Bulk syncs from channel managers go to a separate lower-priority lane with per-source rate limits, so a guest booking never waits behind a re-sync; no-op changes (same state) are dropped by comparing with the current block. A periodic full rebuild from calendar snapshots catches drift.
- **Search versus booking.** Search is a hint; booking re-reads the calendar exactly and fails with a clear message if the nights are gone. The quoted price carries the calendar version and a quote id; checkout recomputes and, if it differs, shows the guest the new total before payment.
- **Stable results.** The first query stores the ranked candidate list (ids and scores) under a short-lived search session id; later pages read from it and re-check availability for that page only, dropping items now unavailable (and saying so) rather than re-ranking and shuffling pages. A pan or zoom starts a new query.
- **Dates.** Calendar dates are local dates of the listing with no time component; the index and the query use plain dates. Only "today" for advance notice needs the listing's time zone.

**Competing designs to accept.** A search engine (Lucene-based or similar) for attributes and geo, with availability and prices in a side store or a custom plugin, if the candidate shows what a calendar update costs (re-indexing whole documents at {{calendar_updates}} per second is expensive; partial or doc-value updates or a side structure fix it). Availability as precomputed "available stays" per (check-in, nights) for the most common lengths, with a fallback for others. A two-tier system: a fast approximate filter in search plus an exact availability service called for the top candidates. Converting totals per query versus caching per currency.

**Bottlenecks and failure modes.** Update lag in busy periods; bulk syncs starving ordinary updates; re-indexing whole documents for a one-night change; cross-shard fan-out for large viewports; skew between dense and sparse areas; cache keys that never repeat (dates × guests × filters); price mismatches from currency rates or rules applied differently in search and checkout; date shifts from time-zone conversion of calendar dates.

**Incident guidance.**
- *Update path 40 minutes behind during a rush*: confirm with per-shard lag metrics; scale indexers and apply the coalescing (only the latest state per listing matters), drop no-op events, and prioritise booking and block events over price edits. Short term, have booking-failure feedback evict the listing's dates from the index immediately (a fast path from the booking service). Prevention: lag alarms tied to {{staleness}}, capacity tests at holiday peaks, and separate lanes by change type.
- *80,000-listing re-sync*: move bulk syncs to their own lane with a rate limit per source and lower priority; diff against current state so unchanged nights produce no update; tell the partner about incremental sync. Measure the ordinary lane's lag separately so the target is visible.
- *Local dates shifted through UTC*: roll back the indexer change; rebuild affected listings from calendar snapshots (or the full index) and verify with a check that compares a sample of index blocks with the calendar service for listings in many time zones. Prevention: dates as date types end to end, a contract test with listings east and west of UTC, and an automated index-versus-source diff after each deploy.
- *Stale currency rate*: detect via the rate table's age; fall back to filtering on the listing's currency with a margin, or show a "price in your currency is approximate" note; fix the refresh and alert on rate age. Checkout always recomputes, so no guest pays a wrong amount, but the filter excluded listings, which is a ranking and fairness bug to report.

**Follow-up guidance.** On flexible dates: the `run` array answers "any n nights within a range" by scanning the range's check-in days (tens of lookups), or by a precomputed max-run over windows; the candidate should state the extra cost per listing. On divergence between search and checkout: rule differences, staleness, currency, taxes and fees added later; strong answers make the same price function serve both. On paging: a stored result list is the standard answer; re-querying with offset on a changing index is the red flag.

**Rubric anchors.** 2: a database query or one search index with a date-range filter, no account of how availability is represented or updated, no latency or freshness reasoning. 3: per-listing compact calendar with an O(1) stay check including the non-bit rules, geo partitioning, an update stream with versions and idempotent application, booking as the exact check, totals from the stated rules. 4: also coalescing and isolation of bulk syncs, lag measured against {{staleness}}, candidate budgets and ranking hand-off, stable paging, currency handling, local-date correctness, memory sizing, and crisp handling of every incident.

**Strong signals.** Separates what changes fast from what does not; sizes the index; treats calendar dates as dates. **Red flags.** Scanning a nights table per query; re-indexing full documents on every change without counting the cost; claiming search can be exact; converting calendar dates through timestamps.

## ABB-L4-02

**Reference architecture (one defensible design; score others on the criteria).**
- **Ingestion.** Search, view, wishlist and booking events from the stream land raw (partitioned by event date) and in a cleaned layer with bot score, visitor id, market mapping and the requested check-in, check-out and guests. Late events are accepted for a few days; aggregates are recomputed for affected days.
- **Demand tables.** `search_demand(market, night, observed_date, lead_days, unique_visitors, unique_visitor_searches_with_dates, views, saves)` where a search for nights [check-in, check-out) contributes once per night per visitor per observed day (deduplicated on visitor × market × night × observed day). A separate `checkin_demand(market, checkin_date, length_bucket, observed_date, unique_visitors)` answers "how many people want to arrive that day for how long". Bot handling: drop sessions above a high bot score, down-weight a middle band, and measure filter error with a labelled sample and by checking that filtered traffic does not convert to bookings.
- **Booking pace.** For each market × night, booked nights as a share of available capacity at each lead time, from calendar snapshots taken daily (point-in-time), against the same lead time a year earlier aligned by weekday and holiday calendar. Remaining supply per night.
- **Comparables.** For each listing, a set of similar listings (location radius or same neighbourhood, capacity, bedrooms, property type, quality and review signals), recomputed weekly. Signals over the set: distribution of listed prices per night, booked share, and booked prices, released only when the set has at least 10 listings and no single listing dominates; never shown at listing level. Correct for survivorship: compare listed and booked prices, and model probability of booking at a price rather than averaging sold prices.
- **Serving and training.** All signal tables are keyed by `observed_date` (or a knowledge timestamp) so a training row for a suggestion made on day T joins signals as known on T. The suggestion service reads the latest signals {{refresh}}; every suggestion is logged with its inputs' versions and the model version, and outcomes (accepted, price changed, booked, at what price) are joined later.
- **Measurement.** Interference makes a listing-level test misleading. Randomise by market or cluster of nearby markets (few units, low power, so use longer tests and variance reduction), or switchback over time within markets, or a host-level test with outcomes measured at market level as a sanity check. Report host earnings, occupancy, guest conversion and price paid, so a "win" for hosts that is only higher prices with fewer bookings, or a loss for guests, is visible. Observational comparisons of accepters versus non-accepters are confounded (hosts who accept differ) and are not evidence.
- **Feedback loops.** Train on outcomes where suggestions were randomised or perturbed (small, logged exploration), use market-level signals that change slowly, and cap how fast a suggestion can move day to day.

**Competing designs to accept.** Streaming aggregation for demand (if the candidate shows which signal needs it); batch daily with an hourly incremental layer; embedding-based comparables instead of attribute rules; market definitions from map areas rather than fixed markets, if the candidate handles overlap.

**Bottlenecks and failure modes.** Range expansion multiplies volume (a 30-night search becomes 30 rows): deduplicate before expansion where possible. Bot and scraper traffic. Silent upstream stalls read as demand collapses. Default-date changes in the product creating artificial demand. Leakage of future information into training. Competitor inference from small comparable sets.

**Incident guidance.**
- *Scraper triples one city's demand*: the per-visitor dedup should have capped it; investigate why (rotating visitor ids). Recover by recomputing the city's demand with the offending sessions removed and re-issuing suggestions; alert on demand jumps not matched by views or bookings. Prevention: anomaly checks per market, demand that requires engagement (views) as well as searches, and caps on per-day movement of suggestions.
- *Booking feed stalls two days*: a freshness check on every input, with suggestions frozen (last good values) when an input is stale rather than computed from zeros. Recompute once the feed recovers; tell affected hosts using automatic pricing if prices moved. Prevention: completeness checks against the booking system's own counts.
- *Default dates inflate demand*: tag searches by whether the guest chose the dates; count only chosen dates as demand; backfill the period with the tag. Prevention: a contract with the search team that events carry intent fields, and a change review for event semantics.
- *Accepters earned less*: this is selection, not evidence: hosts who accept may be the ones struggling. Do not switch off on that dashboard; answer with the randomised design (market-level) and its result, or run one. Explain to product why the comparison is confounded.

**Follow-up guidance.** For "as known on day T", accept a knowledge-time column or daily snapshots; push on how a late event changes T's value (it does not; it changes T+1's). For the event five months out: searches react first, then views, then booking pace; smoothing with a minimum duration, and a human-entered events calendar. For the feedback loop, look for exploration and logged propensities.

**Rubric anchors.** 2: counts raw searches per city, averages competitor prices, measures by comparing accepters with others. 3: deduplicated demand per night and lead time, booking pace with seasonal baseline, point-in-time signals, logged suggestions with outcomes, a randomised test that names interference. 4: also measured bot filtering, k-anonymous comparables with survivorship correction, cluster or switchback designs with power reasoning, explicit feedback-loop controls, freshness matched to need, and every incident handled.

**Strong signals.** Defines demand precisely before building; worries about interference unprompted. **Red flags.** Real-time everything with no reason; competitor data at listing level; accepting confounded comparisons as proof.

## ABB-L4-03

**Reference architecture (one defensible design; score others on the criteria).**
- **Label ledger.** `labels(label_id, entity_type, entity_id, source, assertion, reason_code, confidence, event_ts, known_ts, supersedes_label_id, ingest_batch)`, append only. `event_ts` is when the thing happened (the chargeback date, the review decision), `known_ts` when the platform received it. Reversals (an appeal overturning a decision, a merchant winning a dispute) are new rows that supersede earlier ones. Free text never enters; a separate, access-controlled store holds it for reviewers.
- **Resolution.** A versioned rule (owned by the risk data team with trust and finance sign-off) turns a set of labels into one outcome per booking as of a knowledge time: for example, confirmed fraud chargeback or upheld trust decision → fraud; won dispute or reversed decision → not fraud; service-not-received chargeback → not fraud for the payment-fraud model but a signal elsewhere; guest report alone → suspected (excluded from training or weighted). Each outcome records the rule version and the label ids that decided it.
- **Propagation.** Account-level labels are mapped to bookings by type: a fraudster's account marks bookings made by it; an account-takeover label marks only bookings made after the takeover time from the attacker's sessions, and the owner's earlier bookings stay clean (the owner is a victim).
- **Maturity.** For each label type, the empirical arrival curve (share of eventual fraud known by day k). Training and evaluation use bookings older than a maturity horizon (for example the day by which ~95% of fraud chargebacks have arrived, within the {{dispute_window}}-day window), or weight immature bookings; never treat unlabelled recent bookings as clean.
- **Training sets.** Built as of a cut-off knowledge time from the ledger and the point-in-time features, written as immutable, versioned datasets with the rule version and ledger watermark, so they can be rebuilt exactly. Retrains on the {{cadence}} schedule pick up new labels by rebuilding, not by mutating old sets.
- **Blocked traffic.** A small random allow-through (or a random sample routed to manual review) with logged probabilities gives outcomes for blocked-like traffic; train and evaluate with inverse-propensity weights. Alternatively, accept reject inference with explicit assumptions.
- **Reporting.** Monthly loss reports are computed from the ledger as of the publication time and stored; later restatements are a new version with a reason and a reconciliation of the difference; the report shows "as published" and "as of now" and the expected further change from immature months.
- **Quality checks per source.** Volume by day, reason-code distribution, lag between event and known time, share mapped to a known booking, and agreement rates between sources, with alerts on change.

**Competing designs to accept.** A bitemporal table instead of a supersession ledger; resolution in a feature store's label component; survival models for label arrival rather than a fixed horizon; manual-review samples instead of random allow-through when blocking cost is high.

**Bottlenecks and failure modes.** Mutable labels that make training sets irreproducible; immature negatives; selection bias from blocking; silent upstream code changes; bulk actions with high error rates; account-level labels smeared onto victims; extraction errors from free text.

**Incident guidance.**
- *Reason codes changed*: detect from the code distribution check; map the new codes, re-ingest three weeks of chargebacks, restate the month with an explanation. Prevention: alerts on unknown codes (fail closed into "unmapped", never "other"), a contract with the processor integration owner.
- *Bulk action partly reversed*: reversals supersede the 2,000 labels; rebuild affected training sets and compare the retrained model trained with and without them; consider down-weighting bulk-action labels until the appeal window passes. Prevention: label confidence by source, with bulk actions marked provisional.
- *Immature negatives*: stop treating unlabelled recent bookings as clean; evaluate on mature windows; compare recent precision with the maturity curve. Recompute the past retrains' evaluation to show the bias.
- *Negation errors in extraction*: roll back the extractor, re-derive labels from the stored free text, and add a labelled test set with negations; alert on week-over-week jumps in any label type.

**Follow-up guidance.** For the appeal reversal two months later: published reports get a restatement, already-built training sets stay as they were (reproducibility) and the next build uses the corrected outcome. For detecting silent source changes within a day: distribution and lag checks per source with a baseline.

**Rubric anchors.** 2: a labels table updated in place, latest label wins, recent unlabelled bookings treated as clean. 3: append-only ledger with event and knowledge time, a versioned resolution rule, maturity-aware training and evaluation, reproducible training sets, restatements recorded. 4: also blocked-traffic correction with logged propensities, careful account-to-booking propagation, source-level quality alerts, as-published versus as-restated reporting, and crisp handling of every incident.

**Strong signals.** Asks "when did we learn this?" for every label; separates victims from fraudsters. **Red flags.** Ground truth treated as known at booking time; overwriting labels; no awareness that the model's own blocks hide outcomes.

## ABB-L4-04

**Reference architecture (one defensible design; score others on the criteria).**
- **Write path.** A send request (with a client-generated message id for idempotency) goes to the thread's owner, chosen by hashing the thread id to a partition; the owner assigns the next per-thread sequence number, applies masking of contact details before booking confirmation, runs the fast safety classifier within {{hold_budget}}, writes the message durably to a store keyed by (thread_id, seq) (a wide-column or key-value store), and acknowledges the sender. A resend with the same message id returns the existing message.
- **Fan-out and sync.** After the write, an event goes to a delivery service that pushes to each participant's connected devices (persistent connections), sends a push notification through the platforms' push services, and queues email for participants who use it. Devices keep the last sequence seen per thread and sync "after seq N" on reconnect or on any notification, so a dropped push only delays, never loses. Delivery and read receipts are separate small events (participant, thread, up-to-seq) that only move forward.
- **Email.** Outgoing email has a per-participant, per-thread signed reply address; inbound mail is parsed, quoted history stripped, and the reply posted as that participant; unsigned or mismatched replies are rejected or held.
- **Translation.** On read, the client asks for the thread in its language; the service translates missing messages, caches by (message id, target language), and the client shows the original immediately if the translation is not ready. Translation never runs in the send path.
- **Safety.** Fast classifier and rules (known bad domains, payment-request patterns) inline within {{hold_budget}}: deliver, deliver with a warning, or hold for review. A slower model and link checks run after delivery; a later positive retracts the message for the recipient with a notice, records it for the safety team and may restrict the sender. Fail-open versus fail-closed under classifier outage is a stated policy (for example deliver with a warning).
- **Metrics.** From message metadata only (no text): for each inquiry or booking request, the first personal reply by any host-side participant, using server accept times; scheduled messages and automatic replies excluded (this exercise's rule). Response rate = share answered within {{response_window}}; response time shown as a median or a band, over a rolling window. Periods of platform-side delivery outage are excluded for affected hosts, recorded as exclusions.

**Competing designs to accept.** A log-based design (one partition per thread range, consumers materialise threads) if per-thread ordering survives rebalances; device-side translation; per-user inbox fan-out on write instead of read-time thread queries; inline-only scanning with a larger budget if the candidate quantifies the conversion cost.

**Bottlenecks and failure modes.** Ordering by device clocks; push treated as delivery; translation or scanning in the send path; hot threads during long stays; email loops and spoofed replies; metrics computed from device receipt times; message text leaking into analytics.

**Incident guidance.**
- *Translation slow, sends stuck*: take translation out of the send path immediately (feature flag), show originals; deduplicate resends by client message id. Prevention: dependency timeouts and a send path with only the essential synchronous steps.
- *Phishing campaign missed*: retract delivered messages found by the updated model with recipient notices, block the domains, restrict senders; measure how many were opened. Prevention: rules for newly registered and look-alike domains inline, faster model updates, and a kill switch to hold messages with links from new accounts.
- *Push outage hurts response metrics*: exclude the outage period for affected hosts from response metrics (recorded, with reason), and say so to hosts. Prevention: delivery health per region recorded alongside metrics, so exclusions are automatic.
- *Hold raised to 10 seconds*: measure the conversion and support cost against the harm caught; restore {{hold_budget}} with a targeted hold only for risky senders (new accounts, links, off-platform payment patterns).

**Follow-up guidance.** Look for sync-by-sequence for offline devices; for fairness, server times, local-hour context (an inquiry at 3 a.m. local time) and robust statistics; for long threads, pagination by sequence and media in object storage with references.

**Rubric anchors.** 2: one message table with timestamps, push equals delivery, scanning and translation synchronous. 3: per-thread sequence via a single writer, durable accept and fan-out with sync by sequence, translation on read, two-stage scanning within the budget, metrics from metadata. 4: also idempotent sends, signed email replies, retraction flows, outage exclusions in metrics, masking before booking, and every incident handled.

**Strong signals.** Separates "accepted" from "delivered" from "read"; keeps text out of analytics. **Red flags.** Ordering by device timestamp; translation in the send path; averages over a skewed response time.

## ABB-L4-05

**Reference architecture (one defensible design; score others on the criteria).**
- **Definitions.** `metric_definitions(metric, version, sql_or_code_ref, threshold, effective_from, owner)`. One implementation computes each metric for any cut-off; the daily progress view and the quarterly assessment call it with different cut-offs and the same version.
- **Inputs.** Clean fact tables with event and knowledge times: stays (completed), cancellations with who cancelled and the decision path (guest request, alteration, host action, platform action on host's behalf), first-reply facts per inquiry, reviews with submission and publication times, exception decisions with approval time and the bookings covered.
- **Cut-off rule.** The assessment uses inputs known by the cut-off (for example quarter end + 2 days). Reviews still inside their window and exceptions approved later count in the next assessment, unless they change the result, in which case a re-assessment runs (one clear rule, announced to hosts). Either rule is acceptable if consistent and explained.
- **Assessment records.** `assessments(host_id, quarter, version_no, definition_versions, cutoff, metric_values, inputs_snapshot_ref, result, reason, supersedes, created_at)`, immutable. `assessment_inputs(host_id, quarter, version_no, input_type, input_id)` lists exactly what was counted. Appeals and late exceptions create a new version; the old one stays and the reason is recorded. Manual overrides are inputs (an approved exception or an override record with approver), so recomputation reproduces them.
- **Status history.** SCD type 2 `host_status(host_id, status, valid_from, valid_to, assessment_ref)`; "status on date D and why" joins to the assessment version.
- **Publication.** Compute into a staged version; run checks (distribution against last quarter, sample audits, counts of status changes); then flip one pointer (published version for the quarter) at the announced time. The badge service and the search benefit both read the published version (or are pushed it with the version id) and report which version they applied; a reconciliation job compares them.
- **Host explanations.** The progress page and the result page list the counted stays, cancellations (with whether excused), reviews and replies behind each metric, from `assessment_inputs`.

**Competing designs to accept.** A bitemporal fact model instead of input snapshots; re-assessing automatically whenever a late input would change a result; rounding rules stated and applied once (for example ratings to two decimals before comparison), as long as it is explicit.

**Bottlenecks and failure modes.** Two codebases for progress and assessment; cancellation attribution through alterations; late reviews and exceptions; overwrite-in-place recomputes; consumers reading a copy that drifts from the published version; rounding disputes.

**Incident guidance.**
- *Guest-requested changes counted as host cancellations*: fix the definition (new version), re-assess affected hosts as new versions, restore badges and benefits from the corrected published version, and notify hosts with an apology; triage the appeal queue by auto-resolving the affected cases. Prevention: definition tests with alteration paths, and a pre-publication check on the change in failure rates by reason.
- *Late reviews*: publish the rule and show it in the progress page ("reviews for stays ending after D count next quarter"); give support one scripted answer from the same data.
- *Late exception for a weather event*: run a re-assessment for hosts whose excused cancellations change the result; publish as new versions; benefits switch immediately. Prevention: an exception backlog check before publication for known major events.
- *Search benefit from a stale copy*: consumers must read the published version id; reconcile and fix within hours; add a check that blocks publication-dependent jobs from reading an unpublished or superseded version.

**Follow-up guidance.** For the 4.795 rating question, look for an explicit rounding rule applied consistently in progress and assessment. For the alteration case, look for a definition based on who initiated the cancellation and the alteration history, not the last actor.

**Rubric anchors.** 2: a quarterly job that overwrites a status table; no versioning; late inputs ignored without saying so. 3: versioned definitions shared by progress and assessment, a clear cut-off rule, immutable assessments with counted inputs and supersession for appeals, status history. 4: also atomic publication consumed by badge and search with reconciliation, overrides that survive recomputation, host-facing explanations, and crisp handling of every incident.

**Strong signals.** Treats the assessment as a published, versioned record; designs for appeals from the start. **Red flags.** Recomputing history in place; separate logic for the progress view; no notion of when a late input counts.
