# Google · Loop 4 — evaluator notes (hidden from candidates)

## GOO-L4-01

**Reference architecture (one defensible design; score others on the criteria).**
- **Inside the log boundary** (where searcher identifiers exist): a join stage reads results-page records (page id, query, country, device, timestamp, list of (URL, position, result type)) and click records (page id, URL, timestamp). It keys both by results-page id, waits a bounded lateness window (for example 3 hours for the preliminary view, 24 to 48 hours for final), and emits one **attributed row per (results page, URL)**: query, URL, position, clicked flag, country, device, date. A clicked URL that has no matching impression is counted and alerted on, not silently dropped.
- **Privacy decision, also inside the boundary**: per (query, day), count distinct searchers exactly (or with a sketch biased toward withholding), and emit only a boolean "displayable" per (query, day). The reporting side never receives identities. Attributed rows for non-displayable queries keep their numbers but lose the query text (they are rolled into an "other queries" bucket per property), so totals stay correct and the gap is explainable.
- **Property attribution**: a lookup from host to candidate properties (domain properties keyed by registrable domain; URL-prefix properties in a trie or a sorted prefix table per host). Each attributed row fans out to every matching property. The fan-out is small on average and large only for a few organisations; precompute the host → property list and broadcast it to workers.
- **Two aggregation modes**: page mode sums attributed rows per (property, URL, query, country, device, date). Property mode first reduces per (results page, property): impression = 1, clicked = any URL of the property clicked, top position = min position, then sums per (property, query, country, device, date). Both are computed from the same attributed rows, never from each other.
- **Additive storage**: store impressions, clicks and **sum of top position** (plus impression count) so average position = sum / impressions is correct after any regrouping. Never store averages.
- **Serving store**: a columnar or key-sorted store partitioned by property and date, sorted by query (with a token or n-gram index for substring filters on large properties) and with per-property pre-aggregates by date, country and device for the charts. Large properties get their own shards; the long tail is packed together. p95 under 2 seconds comes from touching only one property's partitions.
- **Freshness and versioning**: a preliminary path (smaller lateness window, labelled) and a final path; every published (property, date) carries a version. A restatement writes a new version, flips a pointer atomically, and the API exposes the data version and a "last updated" per day so exporters can re-pull.
- **Retention**: {{history_months}} months of the reporting store; raw logs expire on the log system's own schedule.

**Competing designs to accept.** One big daily batch (simpler) if the candidate still provides the preliminary view, perhaps by a smaller incremental job. Streaming joins with a stated lateness window. Approximate distinct counts for the privacy decision if the error is pushed toward withholding (for example withhold when the estimate is within the sketch's error of the threshold). Precomputing only common groupings and querying detail rows on demand for the rest.

**Bottlenecks and failure modes.** Fan-out to nested properties multiplying volume; hot properties skewing the aggregation; per-page de-duplication done after grouping (double counting in property mode); averages stored instead of sums; rare-query rows exposed by exports or by differencing two overlapping date ranges; clicks arriving after the preliminary cut; restatements that silently change history.

**Incident guidance.**
- *Carousel counted as one position*: detect with a distribution monitor on positions by result type rather than waiting for owners. Fix the serving log or map positions in the join, recompute the 2 affected days from retained logs, publish new versions and an annotation on the chart. Prevention: a data contract on the position field with the serving team and a change review for any layout change.
- *Hot publisher*: salt the property key for the summation stage (the per-page de-duplication is keyed by results page, so it does not need the property as a single key), or give the largest properties a dedicated path. The preliminary view should never wait on one property; publish per property as each finishes.
- *Rare queries exported*: treat as a privacy incident: stop the export path, identify which owners received which rows, follow the privacy incident process for notification and deletion requests, and add a test that every export path applies the displayable flag. Root cause is usually a second code path that did not share the filter; the fix is one enforcement point in the store, not in each API.
- *Late click logs for one region*: the preliminary view must know completeness, not assume it. Track input completeness per region and hour, hold or label the affected slices, and recompute when the logs land. A CTR drop that coincides with a completeness gap is not a product signal.

**Follow-up guidance.** Make the candidate actually do the two-URL example in follow-up 1; most mistakes show up there. For the range threshold, a strong answer recognises that per-day decisions do not compose (a query with 6 searchers on each of 5 days may have 6 or 30 distinct searchers over the range), and that differencing ranges can reveal withheld rows; acceptable answers include per-range distinct sketches kept inside the boundary, or keeping the per-day rule and explaining why.

**Rubric anchors.** 2: counts impressions per URL, stores averages, no plan for overlapping properties or the privacy rule. 3: join within a lateness window, correct property-mode de-duplication, additive storage, privacy decision inside the log boundary, per-property storage layout, versioned restatements. 4: also hot-property skew, completeness tracking for the preliminary view, the range-threshold problem and differencing, and crisp handling of every incident.

**Strong signals.** Asks how one URL maps to several properties; stores sum of position, not average position; notices that totals and rows must differ and explains it to the owner. **Red flags.** Searcher ids in the reporting store; averaging averages; rare queries filtered only in the UI.

## GOO-L4-02

**Reference architecture (one defensible design; score others on the criteria).**
- **Three spend numbers**: (1) *auction-time spend*, held in memory on each auction server, approximate and conservative; (2) *reported spend*, a streaming aggregation of billable events shown to advertisers within minutes; (3) *billed spend*, the exact daily and monthly totals after invalid-click filtering and the budget caps, which drive the invoice.
- **Billable events**: impressions and clicks carry a unique event id and the auction id. A stream aggregator deduplicates on event id and maintains spend per (campaign, advertiser day) and per (campaign, month) in an idempotent state store. Clicks are joined to their impression for price (the auction set the price) and arrive late; they count on the advertiser day of the click.
- **Budget shares per region**: a budget service computes, for each campaign, the remaining budget for the day (min of the remaining daily cap at twice average, the remaining monthly cap, and the pacing target) and grants each region a share proportional to its recent traffic for that campaign, with a reserve held back. Auction servers in the region pull their region's share (or a slice of it) and decrement locally on each won auction, using the expected cost (for CPC, bid times predicted click-through rate) as in-flight exposure until actual clicks arrive. When a region's share runs low it asks for more; shares are rebalanced every few seconds.
- **Eligibility and pacing**: per campaign, a pacing controller compares actual spend with a target curve over the advertiser's day (shaped by historical traffic for that hour, not flat) and outputs a participation probability or a bid multiplier. The auction server combines it with the local remaining share: no share, no entry. Damping (a PI controller or bounded steps) avoids oscillation; small campaigns use coarser control.
- **Overdelivery bound**: worst case is roughly the spend that can accrue during the signal delay plus outstanding clicks on impressions already served. The design reduces it with in-flight exposure accounting, smaller shares for campaigns near their cap, and stopping eligibility before the cap rather than at it. Any spend above the caps is not charged (it is absorbed and measured as a platform cost metric).
- **Partitions**: a disconnected region keeps spending only its granted share; when it rejoins it reports actual spend, and the budget service reconciles. Shares are leases with expiry, so the service knows the maximum a silent region can have spent.
- **Time**: day and month boundaries are computed per advertiser time zone from the tz database; a 23- or 25-hour day gets a target curve of the right length. Budget changes publish through the same budget service within a minute.
- **Billing and reconciliation**: a daily batch computes billed spend from deduplicated events minus invalid clicks, applies the daily and monthly caps, and writes the invoice lines; invalid-click credits after the day closes are adjustments. Reported spend is reconciled with billed spend daily; differences beyond a tolerance alert.

**Competing designs to accept.** A strongly consistent counter per campaign per region with asynchronous cross-region sync (if the candidate measures latency and keeps it off the critical path). Bid shading instead of probabilistic throttling for pacing. Central admission per campaign for the few very large ones. Allocating budget shares by forecast rather than recent traffic.

**Bottlenecks and failure modes.** Remote calls on the auction path; overdelivery during signal delay on viral spikes; hot campaigns whose spend events concentrate on one partition; daylight-saving boundaries; double-counted events in the stream; invalid-click credits making reported spend fall; pacing that exhausts budget early or under-delivers at day end.

**Incident guidance.**
- *News spike on small campaigns*: overdelivery is bounded by shares and in-flight exposure; check that it stayed within the expected bound and that nothing above the caps was charged. Improve with traffic-anomaly detection that shrinks shares for affected campaigns and with faster signal propagation for campaigns near their cap. Report the absorbed cost as a metric.
- *Region partition*: the isolated region spends only its leased share; when it rejoins, the budget service reconciles actual spend and takes back or tops up shares. If other regions were granted the same budget again, the lease rules were wrong; the fix is that a share is never re-granted until its lease expires.
- *Delayed invalid-click filter*: billed spend is correct after the filter; reported spend should show credits as a separate line rather than as spend falling; pacing should not release a large block of budget late in the day at once (cap how much budget a credit can release per hour).
- *25-hour day*: the target curve and day boundary were computed as 24 hours; fix the boundary computation to use real local midnights from the tz database and add tests for both transitions. Affected campaigns under-delivered rather than overspent; communicate if the gap is material.

**Follow-up guidance.** Ask for the overdelivery bound as an expression (signal delay × spend rate + outstanding click exposure) and see whether the candidate's design actually shrinks it. Ask what the auction server does when its state is stale: the safe default is to stop serving a campaign close to its cap, not to keep serving.

**Rubric anchors.** 2: a central counter decremented on every auction, no distinction between reported and billed spend, UTC days. 3: local budget shares with rebalancing, idempotent spend aggregation, a pacing controller with a target curve, advertiser time zones, caps applied in billing. 4: also an explicit overdelivery bound with in-flight exposure, lease semantics under partition, credit handling in pacing, reconciliation, and crisp handling of every incident.

**Strong signals.** Separates the three numbers early; talks about leases and what a silent region can have spent; treats overdelivery as a measured platform cost. **Red flags.** Synchronous global counters on the auction path; charging above the cap; ignoring late clicks.

## GOO-L4-03

**Reference architecture (one defensible design; score others on the criteria).**
- **Schema**: every event carries playback session id, sequence number, event type, client timestamp, server receive timestamp, app version, device class, network operator (from the client or server-side lookup), serving location, video type (live or on demand), and **cumulative** session counters: play time, stall time, stall count, bytes, current bitrate, time-weighted bitrate sum. The (session id, sequence number) pair is the idempotency key.
- **Ingestion**: clients batch and retry; an edge collector stamps receive time and writes to a partitioned log keyed by session id, so one session's events stay together.
- **Session reconstruction**: a stateful stream job per session keeps the latest counters (highest sequence number wins, duplicates ignored). A session closes on an end event or after an inactivity timeout of a few heartbeat intervals ({{heartbeat_s}} seconds each); it then emits one session record. Late events within a grace period update the record (a correction); after the grace period they go to the daily batch only.
- **Metrics as numerators and denominators**: per slice and minute, the job emits sums of stall time, play time, time to first frame (with count), failures and starts, and bitrate sums. Rebuffer ratio = Σ stall / (Σ stall + Σ play). Because sums are additive, any rollup (network → country) is exact; quantiles of time to first frame use mergeable sketches.
- **Real-time path**: per-minute slice aggregates in a time-series store for the dashboards, from in-progress sessions' counter deltas so a two-hour live stream shows up while it plays.
- **Daily path**: a batch recomputes session records from the full log (with all late events), deduplicated, and writes reproducible per-session and per-slice tables, versioned by code and config. Experiment analysis reads only this path and uses session-level or viewer-level-bucket variance estimates (the delta method for ratio metrics).
- **Detection**: per slice, a baseline by hour of week; alerts only where volume makes the deviation significant; hierarchical localisation searches the dimension lattice for the smallest set of slices that explains the deviation (for example "serving location X" rather than six country-network pairs). "No data" from a slice that normally has traffic is itself an alert.
- **Time**: windows use server receive time adjusted by the client's offset (client time minus receive time, sanity-bounded); events with absurd client times are clamped and counted.

**Competing designs to accept.** Deltas in heartbeats with gap detection, if the candidate handles loss explicitly. Lambda (stream plus batch) or a single streaming system with replay from the log for the daily tables. Sampling viewers for the real-time path, with the full stream for the daily path. Pre-aggregating at the edge.

**Bottlenecks and failure modes.** Live-event surges; state size for tens of millions of open sessions; mean-of-ratios bias; alert storms from small slices; measurement changes looking like quality changes; missing data looking healthy; client clock skew.

**Incident guidance.**
- *Live surge*: the stream must scale by session-id partitions; the candidate should say how lag is detected and what operations see (a freshness indicator on the dashboard), and how the detection target of {{alert_minutes}} minutes is protected (for example a sampled fast path or prioritising the slice aggregates over session closes). Prevention: pre-scaling for scheduled live events and load tests at three times peak.
- *Stall semantics change*: localisation should point at a single app version; the response is to annotate, exclude or correct that version's stall counts, and fix the client. Prevention: an event contract with semantic tests in the client release process and a per-version monitor on metric definitions.
- *Sampling misconfig*: carry the sampling rate in each event and weight by it; per-platform volume monitors catch the jump. Dashboards built on weighted sums stay correct; the cost is ingestion load.
- *Late operator data*: absence must alert ("no data" versus "healthy"); when the data arrives the daily path includes it, and the real-time path shows the gap as missing, not green.

**Follow-up guidance.** For follow-up 4 look for awareness that shorter sessions can lower rebuffering mechanically and that the metric of interest might be watch time per session or abandonment, analysed per viewer bucket; a strong candidate asks why sessions are shorter.

**Rubric anchors.** 2: averages per-session ratios, closes sessions only on end events, static thresholds everywhere. 3: cumulative counters with an idempotency key, session timeout and late-event policy, ratio of sums, real-time and daily paths, baselines with minimum volume. 4: also hierarchical localisation, "no data" as a signal, clock handling, experiment variance for ratio metrics, and crisp handling of every incident.

**Strong signals.** Chooses cumulative counters unprompted; insists on ratio of sums; separates measurement change from quality change. **Red flags.** Storing viewer ids in the quality store; paging on every slice; trusting client clocks.

## GOO-L4-04

**Reference architecture (one defensible design; score others on the criteria).**
- **Collection**: the client sends probes with a rotating identifier and drops the first and last part of each trip near the origin and destination (a common privacy technique). The ingestion edge drops the network address before anything is written. Raw probes land in a log keyed by the rotating identifier with a short retention (hours).
- **Map matching**: a stream job keyed by rotating identifier keeps a short window of each device's probes and runs a sequence matcher (for example a hidden Markov model over candidate segments with transition costs from road connectivity). It emits **traversals**: segment id, map version, entry and exit times, travel time, a mode guess (vehicle, pedestrian, transit lane) and a quality score. Stopped vehicles and implausible speeds are flagged.
- **Segment aggregation**: re-key traversals by segment; per segment and window (at most {{update_every}} long), compute a robust speed (median or trimmed mean of traversal speeds, weighted by traversal length) from vehicle traversals only, and the count of distinct contributing identifiers. Within one window an identifier counts once; because identifiers rotate, the window is short relative to the rotation period, and a device whose identifier changes mid-window is at worst counted twice, so the threshold should be set with that in mind (or a client-side per-window token is used).
- **Publishing**: segments with at least {{min_devices}} distinct devices get a live speed; others get a blend of the last live value (decaying) and the historical speed for that hour of week. The result is written as an immutable snapshot (segment speeds + map version + window) and routing switches to it atomically.
- **Map versions**: aggregation runs against one map version; when a new version lands, a translation table maps old segment ids to new ones (split, merge, retire) and the historical baseline is migrated before the switch.
- **ETA accuracy**: navigation sessions record predicted ETA at start (and at checkpoints), route, map version and outcome. Trips are classified (completed on route, rerouted, abandoned, destination changed); accuracy is computed for completed trips as error and relative error, bucketed by trip length and road class, with abandoned and changed trips reported separately rather than mixed in. Only these fields are retained, without the track.
- **Retention and privacy**: raw probes deleted within hours, traversals aggregated and dropped after the window, only segment-level aggregates and trip summaries kept long term.

**Competing designs to accept.** Grid or tile cells (S2, H3) for coarse partitioning before matching, if matching still uses the road graph. Mean speeds with outlier filtering instead of a median. Running matching on the device. Differential privacy noise added to counts in addition to thresholds.

**Bottlenecks and failure modes.** Re-keying between device-keyed matching and segment-keyed aggregation; hot segments in dense cities and events; map version churn; pedestrians and parked cars biasing speeds; clock errors; empty rural segments at night; raw data retained longer than allowed.

**Incident guidance.**
- *Stadium crowd*: mode detection should exclude pedestrian traversals; if it did not, speeds drop to walking pace. Fix the classifier threshold or require consistency with vehicle-speed history; scale the city's partitions for the burst. Prevention: event calendars to pre-scale, and a monitor on the share of low-speed traversals per segment.
- *Map update mid-day*: switching versions must be atomic: aggregate against the new version only after translation tables and baselines are ready, and never publish a snapshot that mixes versions. Recovery: roll the snapshot back to the old version until the new one is consistent.
- *Local-time timestamps*: probes far from their receive time are clamped or dropped by a sanity check; a per-client-version monitor on (client time − receive time) finds the release. Ask the client team to fix and backfill nothing (the raw data is short-lived).
- *Rural threshold gaps*: live speed is absent, so road closures need another signal: closure reports, routing anomalies (devices turning back), or a lower threshold with added noise if privacy review allows. Communicate that absence of live data is not "free flow".

**Follow-up guidance.** For the 90-day raw retention request, a strong answer refuses raw tracks and offers alternatives: synthetic tracks, matched traversals without identifiers, sampled short snippets with consent and review, or replaying the live window into an evaluation harness.

**Rubric anchors.** 2: keys everything by segment, averages instantaneous speeds, keeps raw tracks. 3: device-keyed matching then segment aggregation, robust traversal speeds, distinct-device threshold, atomic versioned snapshots, historical fallback, short retention, ETA trip rules. 4: also identifier rotation in counting, map version translation, non-traffic filtering, completeness signals, and crisp handling of every incident.

**Strong signals.** Starts from the need for sequences in matching; asks what a segment id means across map versions; keeps privacy as a design input. **Red flags.** Joining probes to accounts; publishing speeds from one device; treating no data as no traffic.

## GOO-L4-05

**Reference architecture (one defensible design; score others on the criteria).**
- **Storage**: columnar, compressed files in a replicated distributed file system, organised by table, partition (date) and clustering order; a metadata service holds per-file statistics (row counts, min/max per column, partition values). The planner prunes partitions and files from metadata before any compute starts, and reads only referenced columns.
- **Planning**: SQL → logical plan → physical plan of **stages**; each stage is many parallel tasks over input splits. Aggregations are two-phase (partial per task, final after a shuffle on the group key). `COUNT(DISTINCT)` shuffles on (group key, distinct key) or uses an approximate function if the customer asked for one.
- **Shuffle**: tasks write partitioned intermediate data to a shuffle tier (memory-backed with spill to disk on separate nodes), not to their own local disk. Consumers read their partition from it. Because intermediate data outlives the producing worker, the scheduler can add or remove workers between stages and retry a failed task without re-running its upstream stage.
- **Joins**: broadcast when one side is measured (from statistics or runtime) to be small; otherwise hash-shuffle both sides. The plan is adaptive: after a stage finishes, actual sizes can change the join strategy and the number of partitions for the next stage.
- **Skew**: runtime detection of heavy partitions (from shuffle partition sizes) and of heavy keys (sampling); heavy keys are split across several tasks with the other side replicated for those keys; repartitioning of oversized partitions dynamically.
- **Scheduling**: two levels. Level 1 allocates slots among reservations (guaranteed minimums, lending idle slots first within the same customer, then to the on-demand pool, with fast preemption to reclaim) and the on-demand pool (per-project fair share and per-project concurrency limits). Level 2 allocates within a reservation across queries (fair share, priority for interactive queries) and across tasks (stage order, speculative execution for stragglers).
- **Fault tolerance**: a lost worker loses only running tasks; they are retried from shuffle data. A lost shuffle node triggers recomputation of the affected partitions from their upstream stage (or shuffle data is replicated for long-running queries).
- **Metering**: bytes billed are defined by what the query logically reads after pruning: the referenced columns of the partitions kept at plan time and of the blocks kept by clustering-based pruning (which may happen at run time). Each file or block is counted once per query in the query's job record, independent of retries, speculative copies and spills; the cache returns results for identical queries over unchanged tables and bills nothing. Every query's job record holds the pruned file list and the bytes figure, so a disputed invoice can be explained query by query.
- **Guardrails**: per-query maximum bytes billed, per-project daily quotas, and warnings for queries that scan without a partition filter.

**Competing designs to accept.** Local-disk shuffle with stage-level retries (simpler, slower recovery) if the candidate explains the trade-off. Separate clusters per large tenant. Static planning with good statistics instead of adaptive planning. Billing by slot time for on-demand instead of bytes, if they discuss predictability for customers.

**Bottlenecks and failure modes.** Skewed keys and straggling tasks; shuffle tier capacity and hot shuffle nodes; noisy tenants on the shared pool; reclaiming lent slots abruptly; mis-sized broadcast joins; metering drift when retries or caching are mishandled; metadata service load from millions of small files.

**Incident guidance.**
- *Unpartitioned scan every minute*: per-query byte limits and per-project quotas would have stopped it; in the moment, contact the customer, offer a temporary quota, and protect the shared pool with per-project fair share. Billing follows the published pricing, but a support process can review it. Prevention: require a partition filter option on large tables, warnings in the console, and cost-anomaly alerts for customers.
- *Skewed join for 6 hours*: runtime skew detection should split the heavy key; if it did not, the candidate explains why (no statistics, split disabled for that join type) and how they would surface "one task holds 40% of the stage" to the customer in the query plan view. Prevention: adaptive skew handling on by default and an alert on straggler ratios.
- *Shuffle rack lost*: affected partitions are recomputed from upstream stages; queries slow but succeed. Replicating shuffle data for queries past a runtime threshold and spreading partitions across racks limits the blast radius.
- *Month-end reclamation*: preemption of borrowed slots is correct behaviour; the harm is how abruptly it lands. Gradual reclamation, checkpointed stages so preempted work is not lost, and clear queue-time signals for on-demand users. Capacity planning should expect correlated month-end demand.

**Follow-up guidance.** Make the candidate trace the `COUNT(DISTINCT)` query concretely; vague "map-reduce" answers hide whether they know what is shuffled. For metering, look for "bytes are a property of what the query logically reads after pruning, not of how many times execution read it".

**Rubric anchors.** 2: a fixed cluster per query, no pruning story, FIFO across tenants, retries restart the query. 3: storage-compute separation with metadata pruning, stages with a decoupled shuffle, broadcast versus shuffle joins, reservations honoured with lending, task-level retries, metering on pruned logical bytes that retries cannot inflate. 4: also adaptive replanning and skew splitting, two-level scheduling with preemption semantics, shuffle-tier failure handling, cost guardrails, and crisp handling of every incident.

**Strong signals.** Explains why the shuffle tier decouples workers; computes bytes billed from pruned logical reads; talks about stragglers and speculative execution. **Red flags.** Billing from executed bytes (retries double-bill); no tenant isolation; assuming statistics are always right.
